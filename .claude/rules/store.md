# The file-backed store

Moved from CLAUDE.md "Key Algorithms". Read before changing anything in `internal/state`.

- **The server refuses to start on data it cannot write** (operator decision 2026-10-04, "test permissions on load"). `checkDataWritable` (internal/state/writable.go), run by `Store.init` before the WAL replay, creates and removes a scratch file in the data folder, `competitions/`, `.wal/`, every competition folder and its `history/` and `events/` (`matchHistoryDir`, `scoreLogDir`), and `branding/`/`sponsors/` when present (`state.BrandingDirName`/`SponsorsDirName`, which the upload handlers use; they write there by path and follow a link, so a `branding/` or `sponsors/` that links out of the data folder is not refused at startup); every folder that fails is named in `ErrDataNotWritable`, so a folder the server cannot write is found at startup rather than as a score write failing mid-match. Folders only: every save writes a temporary file and renames it, which needs only the folder.
- **Every store file access goes through an `os.Root` on the data folder** (`dataRoot`, internal/state/data_root.go; operator decision D9, 2026-10-31: no `#nosec`, the OS keeps each read and write inside the folder). Its methods take the paths the store builds (`compPath` and the rest) and put the store-built path and the by-path operation word back into the root's own errors, so messages read as before. A data folder that is itself a link is followed; a link inside it that points out of it, or is written as an absolute path wherever it points, is refused ("path escapes from parent"). So startup refuses a `competitions/` or `.wal` that is a file or such a link, naming it in `ErrDataNotWritable` with the remedy `writeRemedy` picks from the error alone: the link remedy only for the root's "path escapes from parent" (`isPathEscape`; `os` exports no sentinel for it, so the text is matched, pinned by `TestDataRoot_RefusesASymlinkOutOfTheDataFolder`), the file remedy for ENOTDIR, write access for anything else. The check probes only the competition folders `ListCompetitions` lists, so a link under `competitions/` does not block startup. Seeds are read as bytes through it (`Store.readSeedsRaw` feeding `helper.ReadSeedsRaw`, never `helper.ReadSeedsFileRaw`, which opens by path for the CLI's `--seeds` file); pinned by `TestDataRoot_RefusesASeedsFileThatLinksOutOfTheDataFolder`. The `wal` subpackage knows only its folder's path, so it keeps one call by path: `os.MkdirAll` of `.wal` in `wal.BeginTx` (`Store.init` has already made and checked that folder through the root); every target it writes, removes or reads goes through the store's root-backed functions (`directWriteWAL`, `directRemoveWAL`, `directReadWAL`, passed to `BeginTx` and `Scan` as `WriteFn`/`RemoveFn`/`ReadFn`: the read records what a target held at Commit and checks a log at Scan, `fileDigest`, and tells Commit whether a failed log write left the log, `logMayStand`), and `Scan` and `Done` use an `os.Root` on `.wal`. Do not add a file call by path in `internal/state`: add a `dataRoot` method instead. `NewStore` makes the data folder absolute (`filepath.Abs`) before anything uses it, so every path the store builds, and every path a log records, is the same however the folder was typed (`-f`, `TOURNAMENT_DATA_DIR`, the `.` default) and whatever folder the process started in; the folder kept as typed made a log written under `data` refuse every step when restarted as `/abs/data`, and `.` refused every write (`insideDataFolder` built the prefix `./`, the paths cleaned to `competitions/...`; `TestNewStore_AStoreOpenedOnTheCurrentFolderCanWrite`). A relative step an earlier build wrote is resolved against the process's folder (`storePath`, `TestNewStore_ALogWithRelativePathsReplaysUnderTheAbsoluteSpelling`). A step outside the folder wraps `errOutsideDataFolder`, and startup then says why rather than asking for access to be fixed: for an absolute log, that it was written under another data folder path, naming the data folder; for an earlier version's relative one, that it names its files relative to the start folder, quoting the first relative path as the log records it (`walRestartCause`/`walRestartRemedy`; storePath's resolved path in the wrapped error is against the CURRENT folder, so it is not the cure) (`TestNewStore_ALogWrittenUnderAnotherDataFolderNamesTheCause`). Scan reads the file of EVERY step through `ReadFn`, a step with no `Before` (an earlier build's log) included (`wal.staleStep` judges staleness only where `Before` is set), so such a log naming a path outside the folder is marked Unchecked and refuses startup the same way, rather than failing its Apply unrecorded at every start (`TestNewStore_AnEarlierBuildsRelativeLogStartedFromAnotherFolderRefusesStartup`, `TestWALScan_ChecksTheFilesOfALogFromBeforeTheField`). A log whose startup Apply fails and that names no competition folder (`walCompetition` empty, so no record could retry it) refuses startup too, naming the same cause (`TestNewStore_ALogNamingNoCompetitionThatCannotApplyRefusesStartup`).
- **A name that reads as a bracket placeholder is refused at the roster save, in any case** (operator decision D12, 2026-11-01). `RefuseReservedNames` (participants.go) asks the roster rule `helper.IsReservedRosterName` (reserved.go: the "Pool A-1st" and "Winner of r1-m2" shapes, case-insensitive, on the title-cased name) and answers `ErrReservedName` naming the name; `saveParticipantsNoLock` asks it of every roster write through `refuseRosterWrite` (participants.go, every roster floor in one place), so the paste box, an add, an edit, a check-in and an import are refused alike, and a roster already holding such a name is refused on its next save until it is renamed. `updateParticipantNoLock` also asks `refuseRosterWrite` before its seeds.csv rewrite, which lands (inside a transaction, is staged) ahead of the save; the CLI asks it through `createRoster` (cmd/shared.go), and the draw asks it of the loaded roster (`runDrawPipeline`, engine/competition.go, a 400 naming the name; D22), since a roster written by hand or by an earlier release never crossed the save. The bracket rule, `helper.IsReservedParticipantName` with `IsPoolFinalistPlaceholder`/`IsWinnerOfPlaceholder`, compiles the same patterns case-SENSITIVELY and must stay so: it tells a stored slot from a competitor, and a competitor stored as "Pool A-1St" before the roster rule ignored case must never be reread as a placeholder.
- **The draw and the seeds take the roster's spelling on load** (operator decision D24 (b), 2026-11-02). An earlier release stored a pasted name raw (`kenshinkan 2nd`) and read it with a rule that upper-cased after a digit, so the draw and seeds.csv hold `Kenshinkan 2Nd` while the roster now reads and stores `Kenshinkan 2nd` (D22, `upgradeRosterTextLocked`). `upgradeDrawSpellingLocked` (legacy_upgrade.go, run in `EnsureLegacyUpgraded` after every id repair) gives each copy matched BY ID (`RosterIndex.LookupByID`) the roster row's text where the two differ only by letter case (`takeRosterSpelling`, `strings.EqualFold` and not equal), and nothing else: pools.csv members (name, dojo, zekken), seeds.csv rows, and the sides and winner of every pool-matches.csv and bracket.json match not fought. Fought is `ResultRecorded` (match.go: running or completed, and for a knockout match both sides named, so a bye the draw completed converges; the status-only gate the engine's result gate `hasRecordedResult` also asks) OR `HoldsScore` (match.go: a point, foul, flag or overtime on the match, or a bout row with a result, `SubMatchResult.HasResult`), because a match sent back to the queue is `scheduled` and keeps its bouts (bc-sbq), whose rows copy the match's names (a team-named bout `Winner`, the representative-bout row's sides); a bout row with fighters seated and no result is not fought. A fought match, its bout rows and the history keep their names (D18). A name the roster still holds as `2Nd` (D23) leaves its copies equal, so it never moves. Each file is written only when its text changes, so a crash between files converges on the next load and a second load writes nothing. Award recipients carry no id and are not moved. An id-less seeds.csv row is given its id once by `backfillSeedRow`: exact (name, dojo) first, then `caseFoldRosterMatch` (one roster row equal ignoring case; a row with no dojo takes the one roster row holding its name exactly, else, when none does, the one whose name alone equals it ignoring case, and its dojo with it; a hand-edited roster read can hold case twins, which leave the row alone); this is the one-time id backfill, not a case-blind resolver, since the row is resolved by id alone afterwards.
- **Store Transactions** (`internal/state/transactions.go`): `Store.WithTransaction(compID, fn)` holds the per-comp lock once across multiple load/save operations. Use the `StoreTx` handle inside `fn`. Do NOT call public Store methods (they would deadlock the non-reentrant mutex). Every file a transaction writes is staged in the WAL (operator decision D5 (a), 2026-11-12, "all files in the log"): pools.csv, and a participant edit's participants.csv, seeds.csv and the roster save's side writes to team-members.yaml and lineups.yaml (`rosterIO`), each read back by the transaction's own loads, and the v2.0.0 squads.yaml adoption (`upgradeTeamMembersFilenameLocked`, through `rosterIO`'s `remove`), whose team-members.yaml write and squads.yaml removal are staged together (operator decision D6 (b), 2026-11-12): the WAL has a delete step (`FileIntent.Delete`, staged by `storeTx.txRemoveFn`, applied in order with the writes on commit and replay, an absent file counting as removed), and the transaction reads a staged delete as the file being absent (`storeTx.removedFor`, `rosterIO.stagedRemoved`). A log holding a delete is written as version 2 (`wal.logVersionSteps`: the steps under `steps`, and under `intents` one step naming no file, which a build before the delete step fails to apply before writing anything, logging it and keeping the log); a pure-write log keeps the previous format (plus a `before` key that release ignores); EVERY step records what its file held at commit (`FileIntent.Before`, operator decision 2026-11-12, W1 (a)), and Scan marks stale (`WAL.Stale`, `wal.staleStep`) a log whose file holds neither that nor the step's result, since another writer changed it (one an older build kept after a downgrade, or a file edited outside the app; a log THIS process kept is finished before any later write can overtake it, see the kept-log bullet below): startup sets it aside (`WAL.SetAside`, `<name>.json.stale`, logged at ERROR, never replayed) and the backup settle skips it (`pendingCompWALsLocked`); Scan itself renames nothing. A log Scan cannot check refuses startup naming the file (`wal.ErrLogUnchecked`; the operator fixes access and starts again, and the log then replays with its stale guard): the log file itself unreadable for any reason but a vanished file (W2 (d), 2026-11-13), which Scan returns as its error since nothing says which files it touches, or a named file unreadable (W2 (b)), which Scan hands back marked `WAL.Unchecked` with its steps (never applied), so `Store.init` refuses on any such log before replaying anything while `pendingCompWALsLocked` (a kept-log settle, a backup, a restore) refuses only on one touching its own competition (`walTouchesComp`), and an unreadable file of competition B never refuses A's writes, as does a log of a version this build does not know (`wal.ErrUnknownLogVersion`). A log whose content does not parse is handed back marked `WAL.Invalid` (no steps); `Store.init` logs ONE `slog.Error` ("a change saved just before the restart may not have landed; check the last results entered before the restart and re-enter any that is missing") and sets it aside as `<name>.json.invalid` (`SetAside`, which no later Scan reads, so the next start says nothing), and a failed rename refuses startup exactly like the `.stale` one; the backup settle (`pendingCompWALsLocked`) skips an invalid log and never renames it, while an unreadable log file fails the backup's Scan too (the snapshot errors, a 500) and fails a kept-log settle (the write is refused), and a log whose named file is unreadable fails them only for the competition it touches. A Commit whose log write fails removes the log (it can fail after the rename, at the folder sync), so the failure is an abort, and the staged bodies the savers published are invalidated (`TestStoreTx_SavePoolsCommitFailureLeavesCachesClean`); if the log cannot be removed, Commit answers `wal.ErrCommitLeftLog` and WithTransaction `ErrTxCommitted` (W3 (a)). A participant edit and its draw cascade (`engine.ReplaceParticipantInDrawTx`) are one transaction. A transaction parses lineups.yaml ONCE (`storeTx.lineups`, stage 6 review 8, m4: a lineup save parsed it four to five times): every lineup read answers a copy of it, the transaction's own lineup writers replace it with what they staged (`keepLineups`), and any other staged write of the file drops it (`txWriteFn`); pinned by `TestStoreTx_LineupsAreParsedOncePerTransaction`, measured by `BenchmarkLineupSave` (a save on 50 teams: about 45 ms before, 14 to 25 ms after). The pools.csv it staged is parsed once the same way (`storeTx.pools`/`poolsParsed`, dropped by a staged write or delete of the file; `TestStoreTx_StagedPoolsAreParsedOncePerStagedWrite`), and the round-lineup settlement it runs at commit reads the roster through the transaction's `rosterIO` (`roundLineupStage.rio`), so a participant edit's staged roster is what it reads (`TestStoreTx_RoundLineupStageReadsTheStagedRoster`).
- **A log this process kept is finished before the competition's next write or read** (operator decision K1 (c), 2026-11-13; `internal/state/wal_kept.go`). `WithTransaction` records the competition in `Store.keptWAL` on every path that leaves its log in `.wal` (Commit's `wal.ErrCommitLeftLog`, a failed Apply, a failed Done), and `Store.init`'s replay records the competition a log names when its Apply or Done fails there (`noteKeptWALOf`), so a log the replay kept converges on the same settle (pinned by `TestNewStore_ARecordIsMadeForALogTheReplayCannotApply`: a log naming a file under a missing folder of the competition passes the startup write check and fails its Apply); once a competition is recorded there, the replay leaves that competition's later logs in `.wal` (`walCompetition`), since applying them over the kept one would leave it stale and the next start would set it aside with its change lost, and the settle lands them all in id order (`TestNewStore_ACompetitionsLaterLogsWaitBehindOneThatCannotApply`). A kept log that can never land (a folder it names was removed outside the app) refuses the competition's writes until the operator restores the folder or renames the log so it no longer ends in `.json`; nothing sets it aside by itself. `PendingWALError.Log` names the log, so the refusal (`ErrKeptChangeUnsettled`'s text) and the WARN (`wal` key) say which file. Every writer of a competition's files takes the write lock through ONE helper, `lockCompWrite` (WithTransaction, the direct savers, the roster, seeds, lineup, team-member, history, score-log and delete paths, `EnsureLegacyUpgraded`), which takes it through `lockComp`, so a writer that waited through `DeleteCompetition` never holds an orphaned mutex: with no record it is one `sync.Map` lookup; with one, it settles through `settleCompWALsLocked` (the backup's replay, stale guard included; it clears the record on success, whichever door settled) before the caller reads anything. If the settle fails (the disk still refuses, or Scan fails) the lock is released and the write is refused with `ErrKeptChangeUnsettled` (NOT `ErrTxCommitted`, which would tell `undoAfterFailedTx` the new write committed; NOT `PendingWALError`, the backup's 409), which `internalError` answers like `ErrTxCommitted`: a 500 with the disk-fault log line; the record stays so the next write retries. The RLock readers (`loadCached`, `loadParticipants`, `LoadSeedsRaw`, `LoadCompetitorStatus`, `LoadScoreLog`, `LoadMatchHistory`) call `settleKeptWALBeforeRead` BEFORE taking the read lock (an RWMutex cannot be upgraded): a failed settle there lets the read go on. The read doors wait between tries (operator-facing: a disk that keeps refusing must not queue every viewer, display and SSE refetch behind a failing settle on the exclusive lock): the record (`keptChange`, atomic fields, read lock-free) holds the store clock's time of the last failed settle (`failedAt`, a `time.Time` under `atomic.Pointer`, never Unix nanoseconds, so `time.Now`'s monotonic reading is kept and a wall clock stepped back cannot stretch the wait; `TestStore_TheReadWaitIsMeasuredOnTheMonotonicClock`), and `settleKeptWALBeforeRead`, `EnsureLegacyUpgraded` and `LoadSquads`'s adoption skip their try for `keptSettleReadBackoff` (5 s) after it (`keptSettleDue`/`keptSettleWaits`; EnsureLegacyUpgraded and the adoption stay unstamped, so a later read does them), while a write always tries. The three read doors take the lock through `lockCompWriteForRead`, which asks the wait again once the lock is held: readers that all saw a settle due queue on the lock, and only the first tries it (`TestStore_ConcurrentReadsTryAFailedKeptChangeOncePerWait`). LoadSquads logs a refused adoption at Debug; the settle has already warned once. The first failed settle of a run is logged at WARN (`keptChange.warned`), the rest at Debug, and the landing after a warned run at Info; pinned by `TestStore_AReadWaitsAfterAFailedSettleAndAWriteStillTries` and `TestStore_LoadSquadsReadsOnWhileAKeptChangeCannotBeWritten` (LoadSquads degrades to the empty read on a refused adoption, never a 500). The caches keep the staged bodies on `ErrTxCommitted` (they are the committed change; the settle drops them once the files land), because no cache choice can make the roster (dropped at staging, re-read from the file) agree with the draw while the change has not landed: only landing it does, which the read-path settle does as soon as the disk allows. Never add a `getCompLock(...).Lock()` writer: take `lockCompWrite`. Overrides.json is outside this (store-wide `s.mu`, never in a log). Pinned by `wal_kept_settle_test.go`.
- **Cache invalidation: never key a cache on mtime alone** (`internal/state/store.go`): filesystem mtimes come from the kernel coarse clock (~1ms granularity), so two writes inside one tick are indistinguishable and an mtime-keyed cache serves pre-write data (mp-n6ke: stale standings vs fresh matches injected a phantom tiebreaker bout and stalled bracket advancement; mp-p7n was the same class). Each `fileCache` therefore carries a monotonic `version` counter, exposed as `Store.FileVersion(compID, filename)`; `engine.CalculatePoolStandings` requires BOTH version and mtime to match (the counter catches same-millisecond in-process writes, mtime still catches out-of-process edits). **If you add a writer for a file some cache derives from, call `s.bumpFileVersion` AFTER the bytes land**: an extra bump only costs a recompute, a missed bump serves stale data, and bumping before the write lets a reader stamp OLD bytes with the NEW token. Existing bumps sit at the chokepoints every writer funnels through (`savePoolMatchesLocked`, `saveOverridesLocked`) plus draw deletion and transaction abort. Two further rules follow from the counter being the cache key: **every read path must validate it, not just the fast path** (the `CalculatePoolStandings` single-flight loser returned the winner's entry unvalidated, and the winner stamps *pre-compute* tokens, so it could predate the loser's own write), and **the counter must stay monotonic for the life of the process, including across a competition being deleted and recreated** (IDs are name slugs, so `DeleteCompetition` calls `discardCompCacheBodies` to clear the cached bodies while leaving the counters climbing, rather than `compCache.Delete`, which reset them to 0 and let a recreated competition match its predecessor's stale entry). Prefer a deterministic counter over a sleep, which only hides the race.
- **Only `saveCompetitionChangedLocked` may create the competition directory** (`internal/state/overrides.go`, `competitor_status.go`, `team_lineup.go`): `saveOverridesLocked`, `saveCompetitorStatusLocked` and `saveTeamLineupsLocked` each used to `os.MkdirAll` before writing, so a write landing after `DeleteCompetition` rebuilt `competitions/<id>/` around a lone `overrides.json` / `competitor-status.yaml` / `lineups.yaml`. That orphan survives the delete (`ListCompetitions` returns every directory under `competitions/`) and, because IDs are name slugs, a same-named recreation adopts the dead competition's data. **Locking cannot fix this**: the write does not have to interleave with the delete to resurrect the directory, only to run after it (the two status/lineup writers take the very lock `DeleteCompetition` holds, so they cannot interleave at all, and still resurrected it). `atomicWriteFile` opens its temp with `O_CREATE` but never creates the parent, so once the `MkdirAll` is gone a write to a deleted competition correctly fails with ENOENT. Creating the directory is competition *creation*'s job and `saveCompetitionChangedLocked` is the sole legitimate `MkdirAll` site (plus `Store.init` for the root/WAL folders); do not strip that one, and do not reintroduce the pattern in a new per-competition writer. The interleaving half is closed separately: `overrides.json` is the one competition file whose writers serialize on the store-wide `s.mu` rather than the per-competition lock, so `DeleteCompetition` takes **both**, in the order compLock then `s.mu` (`s.mu` is a sink: nothing holding it acquires a comp lock, so the edge cannot close a cycle). **Do not "tidy" this by moving overrides onto the per-competition lock**: `computeStandingsFrom` runs inside `WithTransaction`, which already holds that lock, and reads overrides via `e.store.LoadOverrides`, so it would self-deadlock the live scoring path on a non-reentrant mutex.
- **The restore journal ensures crash safety across multi-path restore swaps** (`internal/state/restore_journal.go`, `restore.go`): A restore stages every file it moves in under `.restore/<token>/new/` and creates `.restore/<token>/old/` for moved-out paths (`backup.RestoreDirName`), fsyncing every file and directory (deepest first). Staging is never placed under `competitions/`, because `ListCompetitions` returns every directory in `competitions/`. The restore writes `.restore/<token>/journal.json` (`restoreJournalName`, format `restoreJournalV1`) atomically via `writeRestoreJournal` and fsyncs the token directory so the journal is durable before the first live rename. `runRestoreJournal` executes each step (`restoreMoveOut` or `restoreMoveIn`) in order, skipping steps already completed (a move out is done when `old/<path>` exists, a move in when its source `new/<path>` is gone), and fsyncs every directory touched by the renames. After the swap succeeds, `finishRestoreToken` removes the journal file, fsyncs the token directory and the data folder (`s.folder`), removes the token directory (releasing moved-out files), and fsyncs the parent `.restore/` directory (`s.restoreRootDir()`). If a crash interrupts a restore, `recoverRestoresLocked` rolls it forward at startup: it runs at the very end of `Store.init`, under `s.mu.Lock()`, after `checkDataWritable` and WAL replay, but before `NewStore` returns and runs `sweepLegacyUpgrades` or anything lists `competitions/` or loads a cache, so readers always observe the restored tree. If `recoverRestoresLocked` finds a token directory without a journal (meaning the process died during pre-checks or staging before any live path was touched), it removes the staging directory. Because `init` holds `s.mu`, recovery uses `s.root` primitives only, never a locking `Store` method.
- **Pending committed WALs must be settled before taking a snapshot or performing a restore** (`internal/state/backup.go`, `restore.go`): The WAL (`internal/state/wal`) records write and delete steps. When a transaction's `Apply` fails after commit, committed intent files remain on disk (`ErrTxCommitted`), which `Store.init` replays on startup. If a backup or restore does not settle that committed WAL first, the next restart would replay old pre-backup or pre-restore write intents over the restored files. Therefore, `snapshotOneCompetition` checks `hasPendingCompWALLocked(compID)`: if pending committed WALs exist, it acquires the competition's write lock (`lockComp`) and `s.mu.Lock()`, settles the WAL via `settleCompWALsLocked(compID)` (`w.Apply()` then `w.Done()`), and reads the competition's files under those same write locks without releasing in between. Similarly, Step 4 of `Store.Restore` calls `settleCompWALsLocked(id)` for every affected competition under write locks before any safety snapshot or swap. If `Apply` or `Done` fails during `settleCompWALsLocked`, it returns a `*PendingWALError` wrapping `ErrPendingWALUnsettled` and naming the competition, which aborts the snapshot or restore with HTTP 409 `pending_write_unsettled` rather than proceeding on an inconsistent or about-to-be-overwritten state.
- **Restore follows a strict, single lock hierarchy across the entire store** (`internal/state/restore.go`): In Step 3 of `Store.Restore`, locks are acquired in the exact order: `s.compRenameMu.Lock()`, then `s.courtCheckMu.Lock()`, then the write locks of all affected competitions in sorted competition ID order (`s.lockComp(id)` for IDs in `w.replaced`, `w.removed`, `w.created`), then `s.mu.Lock()`, and finally `s.tournamentMu.Lock()` (for a tournament-scoped restore). This order cannot deadlock because: (1) no other code path in the application ever holds two competition locks concurrently, and restore takes them in deterministic sorted order; (2) every holder of `courtCheckMu` (`WithCourtExclusivityLock`, used in scoring and match start paths) takes `courtCheckMu` before acquiring any competition lock, and never acquires `compRenameMu` inside it; (3) every holder of `compRenameMu` acquires it before any competition lock; (4) `s.mu` is always acquired after competition locks (as in `DeleteCompetition`); and (5) `s.tournamentMu` is always acquired after `s.mu` (as in all `tournament.md` writers). A future path must never acquire `compRenameMu` inside `courtCheckMu`, which would introduce an inversion cycle.
- **Snapshot locking and password stripping** (`internal/state/backup.go`): `Store.Snapshot` reads either the entire tournament (`ScopeTournament`) or a single competition (`ScopeCompetition`). For `ScopeTournament`, tournament-level files (`tournament.md`, `branding/`, `sponsors/`) are read together under `s.mu.RLock()` and then `s.tournamentMu.RLock()`, and competition IDs are listed via `listCompetitionsLocked()`. It releases those locks before reading each competition one at a time via `snapshotOneCompetition(id)` under that competition's read lock (`rlockComp`) and `s.mu.RLock()` (upgrading to write locks if pending WALs require settling). A whole-tournament snapshot is therefore not a single point-in-time snapshot across all competitions, and competitions created during the pass may be omitted. In `snapshotTournamentFilesLocked`, `tournament.md` is processed by `serializeTournamentWithoutPassword`: the `Password` field is cleared and the top-level YAML `password` mapping key is stripped. No archive (manual download, before-restore safety copy, or scheduled backup) ever stores the admin password on disk or in memory. If `tournament.md` is missing when snapshotted, a placeholder tournament with name "New Tournament" and venue "Venue TBA" without a timestamp is archived so that fingerprint calculation remains deterministic across days.
- **The restore cache ritual drops cached bodies while preserving monotonic version counters** (`internal/state/restore.go`, `store.go`, `backup.go`): In Step 7 of `Store.Restore`, `restoreCacheRitualLocked` runs after the renames (even if a rename failed). For replaced or created competitions, it clears `s.legacyUpgraded` and `s.bracketRoundsRefusalLogged`, calls `discardCompCacheBodies(id)`, and keeps the `compMu` entry alive (since the restore holds that mutex). For removed competitions, it clears `s.legacyUpgraded` and `s.bracketRoundsRefusalLogged`, calls `discardCompCacheBodies(id)`, and calls `compMu.Delete(id)` while holding the lock. For a tournament restore, it sets `s.cachedTourn = nil` and `s.tournMtime = 0`. `discardCompCacheBodies` calls `invalidate()` on every `fileCache` entry, which clears `data = nil`, `mtime = 0`, and advances `version.Add(1)` (`bumpFileVersion`) after the bytes land on disk. This invalidates cached parses and downstream caches like `engine.standingsCache`. It MUST NEVER call `compCache.Delete(id)`, which would reset versions to 0 and allow a recreated competition sharing the same ID slug to match stale cache entries. In addition, when locking competitions, `lockComp` and `rlockComp` perform a mutex identity re-check: because `DeleteCompetition` (or restore removal) calls `compMu.Delete(id)` before unlocking, a waiting goroutine might wake up holding an orphaned mutex, so both helpers verify that `s.getCompLock(id) == mu` after acquiring the lock and loop until the held mutex matches the active map entry.
- **Pending number prefix collisions are persisted in `prefixes-pending.json`** (`internal/state/restore_journal.go`, `restore.go`, `internal/mobileapp/handlers_backup.go`): When a restore detects that a restored competition's number prefix collides with one kept in place or with an earlier restored competition, that competition ID is added to `w.plan.PrefixesPending`. In Step 6 of `Store.Restore`, before writing the journal, `writePrefixesPending` atomically writes `prefixes-pending.json` (`prefixesPendingName`) under `.restore/` (`s.restoreRootDir()`) and fsyncs the directory. Making this durable before the journal ensures that if a crash occurs anywhere during the directory swap, the unresolved prefixes remain recorded on disk. After the store returns and releases all locks, Step 9 runs `ResolveRestoredPrefixes(store, eng)`: it reads `store.PrefixesPending()`, invokes `ReassignRestoredPrefixes` to assign non-colliding prefixes, and removes resolved IDs via `store.RemovePrefixesPending(ids)` (which deletes `prefixes-pending.json` once empty). `ResolveRestoredPrefixes` also runs at server startup before serving requests, so any prefix reassignment interrupted by a crash completes on the next start.
- **Backup fingerprint calculation zeroes volatile stamp fields and skips logging directories** (`internal/state/backup_fingerprint.go`): `state.Fingerprint` computes a SHA-256 hash over the sorted paths and normalized contents of files captured in a snapshot. To prevent writes that change no real tournament data from triggering spurious scheduled backups, `FingerprintStampedFiles` defines the list of files and Go struct field names zeroed at all depths: in `pool-matches.csv`, fields `ModifiedAt`, `GroupStamps`, and `ScoreVersion`; in `bracket.json`, fields `ModifiedAt`, `GroupStamps`, and `ScoreVersion`; in `competitor-status.yaml` (`competitorStatusFilename`), field `RecordedAt`; in `team-members.yaml` (`teamMembersFilename`), field `ModifiedAt`; and in `lineups.yaml` (`teamLineupFilename`), fields `Stamps` and `History` (along with trimming removal markers via `IsRemovalMarker`). In addition, `FingerprintSkippedDirs = []string{"history", "events"}` skips `history/` and `events/` subdirectories entirely, because every score, decision, or check-in write appends log entries even when no state changes, whereas every genuine change also modifies `pool-matches.csv` or `bracket.json`. Any new stamp field (a field whose value advances on a write that changes nothing else) MUST be added to `FingerprintStampedFiles`. The test `TestFingerprintDoors` in `internal/mobileapp/backup_fingerprint_doors_test.go` exercises every HTTP write door to verify that no-op writes move only normalized stamp fields or skipped directories and leave `state.Fingerprint` unchanged, while genuine changes alter the fingerprint.
- **Known, accepted: legacy upgrade rewrites on release startup trigger a scheduled backup** (`internal/state/store.go`, `legacy_upgrade.go`, `backup_fingerprint.go`): On the first server start following a software release, `sweepLegacyUpgrades` (called from `NewStore`) rewrites legacy file formats or schema discrepancies across existing competition directories. Because these upgrade routines write real byte modifications to disk, `state.Fingerprint` changes legitimately, causing the scheduled backup job to take an automatic backup copy on its next due tick even though no operator made a manual edit. This behavior is expected and correct.
