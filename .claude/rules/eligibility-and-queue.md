# Competitor eligibility and the match queue

Moved from CLAUDE.md "Key Algorithms". Read before changing withdrawals, bars, reinstatement, starting a match or sending one back to the queue.

- **Competitor Eligibility** (`internal/state/competitor_status.go`, `internal/engine/eligibility.go`): a kiken/fusenpai decision auto-writes a `CompetitorStatus{Eligible: false}` for the loser; `engine.StartMatch(compID, matchID)` is the pre-flight gate that returns `*IneligibleCompetitorError` (matches `errors.Is(err, ErrIneligibleCompetitor)`). Maps to HTTP 409, with `reasonHuman` (`reasonHumanForBarredCompetitor`/`barredCompetitorSentence`, `mobileapp/errors.go`) composing one operator sentence naming the competitor, the match (`engine.OperatorMatchLabel`), and what to do, e.g. "Alice withdrew in Pool A · Match 1 and cannot fight again. Record the fusensho for Carol." (kiken-injury: "...Reinstate Alice if they can fight again, or record the fusensho for Carol."). Kiken-injury (FIK Art. 30) sets `CompetitorStatus.Reinstateable: true`; the admin can call `POST /api/competitions/:cid/competitors/:pid/reinstate` to restore eligibility. Kiken-voluntary (Art. 31) and fusenpai are not reinstateable. A withdrawal decision against a competitor ANOTHER match already barred is decided by ONE rule, `engine.alreadyBarredRefusal` (bc-kfup), asked by both T105 halves (`checkConcurrentIneligibility` before the write, the K2 check-and-set in `recordIneligibilityFromDecision`): a kiken is refused with `already_ineligible` (a competitor withdraws once), while a fusenpai is their default loss on a remaining match and records NO new `CompetitorStatus`, so the existing one keeps naming the match where they withdrew. Do not re-add a fusenpai refusal there: StartMatchTx refuses to start that match, so the fusenpai is the operator's exit. Clearing the match that DID record the bar moves it onto such a chained fusenpai rather than lifting it (`standingWithdrawalOf`, fusenpai only: a kiken still on record beside a later bar was lifted by a reinstatement before that bar existed, since a second kiken is refused), and a reopen that clears it lands `scheduled` because `reopenTargetStatusTx` judges the bars the restore will leave (`restoredStatus`, shared with the restore). Accepted as it is (operator decision 2026-09-26): a fusenpai recorded before a reinstatement still carries the bar on, so a competitor who withdrew injured, had a no-show recorded on another match, was reinstated, and then has a later withdrawal cleared as a mistake is barred again by that earlier no-show; the editor names the no-show match, where clearing the fusenpai lifts it. Telling the two apart needs the time of each reinstatement, which is not worth storing for this. Do not report it as a new defect. `engine.BarredSides(statuses, matchID, sideAID, sideBID)` is the ONE extraction point for "is this side barred by a match OTHER than the one being checked" (the `st.MatchID != matchID` undo-path exemption lets a match always be re-scored past its own prior kiken/fusenpai); it replaced three hand-copied loops (`StartMatchTx`, `checkEligibilityExcludingMatch`, `annotateEligibility`). A SCHEDULED match with a barred side carries a READ-ONLY `ineligibleSides` stamp (`state.IneligibleSidesAnnotation{A, B string}`, both `omitempty` decision-code strings) on `MatchResult`/`BracketMatch`, computed at REQUEST TIME ONLY by `mobileapp.annotateEligibility` (`handlers_match.go`; never persisted, `yaml:"-"` on the pool side); a stamped match also has its `queuePosition` zeroed and so omitted from the wire (`stampCourtQueuePositions`, over `state.CourtQueuePositions`, which skips a barred scheduled match), so it is skipped exactly like an unqueued match. `web-mobile/js/ineligible_match.jsx` is the ONE JS owner reading this stamp: `isBarredMatch`/`awaitedDefaultWin` skip such a match from Up next, Finish + Start Next, the TV next line, the lobby, and on-deck alerts, and drive the operator's one-tap `Record fusensho for <opponent>` (`POST /decision {decision: "fusensho", decisionBy: <barred side>}`, which does not touch the barred competitor's own `CompetitorStatus`) and, for a kiken-injury, `Reinstate <name>`. The same request-time pass stamps a COMPLETED match a kiken, fusenpai or fusensho decided with `withdrawnStatus` (`state.WithdrawnStatusAnnotation`: the withdrawn side's status now, eligible / the match that bars it / reinstateable), which `RecordedWithdrawal` words its clear from instead of fetching statuses. The viewer payloads load statuses whenever a match needs either stamp (`anyMatchToAnnotate`), and the `/decision`, `/score` and bulk-score writes stamp the result they push (`stampWithdrawnStatus`), so a pushed row and its refetch read the same. **Recording a withdrawal changes only that match** (operator ruling 2026-09-26, "do not cascade"): the post-kiken Remaining matches panel that offered to close the competitor's other matches was removed, and each of them is closed from its own notice when it comes up. Do not re-add a cascade from one match's editor. Recording one on the court console still starts the court's next match in the same competition (mp-nwds item 7, the operator's request; the Scores tab no longer does, bc-adna), through `start_match.jsx`, the start queued `after` the decision or finish it follows (`writeQueueKey`, stage 3 review 11, X1), and the court console reads a match it finished here as finished until its feed says so, with the winner the finish names and, for an engi finish, which names none, the side its flags decide, its counts laid on with it, so the court row never shows a finished match without its winner (`withOwnStatusMove`, `finishWinnerOf`, stage 6; the twin of `startedFrom`: a pool match moves on at once too, offline included; a refused or discarded finish puts it back; a decision reads the side that did not withdraw) and pins the match its pending start began (`startedFrom`, `pickedKey`; a start the server refuses LATER, or the operator discards from the held-writes list (it settles `{discarded: true}`, which `classifyStartOutcome` reads as ok), takes both pins back, `startMatch`'s `unpin`, so the console shows what the server holds, stage 3 review 12, Z1; a finish read so ends on a feed copy stamped after the finish's own stamp, which the finish's answer carries, never on this device's own earlier taps, Z2; the finish, the decision and the send back are read from the outbox through ONE owner, `API.ownStatusMove` (api_client.jsx: the last status move among the match's queued entries in replay order, a start or a reopen after it ending it, else the last one the server answered, kept for the page with its stamp and score version until the feed shows it or a copy past either, `forgetOwnStatusMove`, and dropped when the tournament no longer holds the match (`forgetOwnStatusMovesNotIn`, given the tournament's matches with the court's feed, never the court's alone: the moves are the tab's, so opening another court kept them and a match moved to another court is not gone, stage 6 review 10, m4) or its draw is generated or discarded (stage 6 review 9, F7); `subscribeOwnStatusMoves` re-reads), never from the page's state, so a reload or the console mounted again with the move still queued shows it (stage 6 review 8, M4, which retires the Z5 limit); pinned by `own_status_move.test.jsx` and the console's remount cases), the decision as recorded riding on the pending answer `onAfterDecision` reads (`withLocalDecision`, admin_scoring_shared.jsx; X3) (one start at a time; a refused start is shown on the refused match, on the console's Up next or queue row, with one toast: an error `editMatchScore` already toasted is marked (`markToasted`, write_result.jsx) and the host does not toast it again. The notice is bound to the refused match, not to Up next, by one rule the console asks (`startRefusalStands`, start_match.jsx): it stays while that match is `scheduled` on the court, and across an empty list, which says nothing about the match and goes when it leaves `scheduled`, when a non-empty court list no longer holds it, when the operator starts a match, or when an eligibility change in its competition is broadcast; Up next moving on does not drop it. A refusal because another start was still out is kept, in the past tense (`startWasBlockedByStartMessage`), on the refused match once that start has gone out: `landed` on the start's record, set by the console's `startMatch` for a start that landed or was queued offline, never for a pick whose deferral of the running bout failed, nor for a start the server refused: a `clock_skew` answer, or a superseded one that holds the `result` group (`heldGroups` non-empty: a different result is stored and nothing of the start was written). A superseded start with NO `heldGroups` is an echo-hold (a start names only `result`, and the server lists a held group only when it differs from the stored one, `reportHeld`/`HeldEcho`): another device's start of the same match landed first and the match is running, so `classifyStartOutcome` answers it `{ok: true}` like a landed start: no sentence, no toast, a pick pins the panel, and a refusal waiting on it is worded in the past tense. The two refusals answer `{ok: false, msg}`, so the console takes them as refused starts: the sentence (`START_CLOCK_SKEW_MESSAGE`, or `START_SUPERSEDED_MESSAGE`, composed by `notSavedText` from `SUPERSEDED_REASON` and `SUPERSEDED_ADVICE` under the "Not started" lead, which never invites a retry, start_match.jsx) is stored on the refused match and toasted once, and a pick does not pin the panel on that match; a pick first asks `GET .../start-check` (`CheckStartAfterSendBack`, the same `startSidesGateTx` the start runs, with the pick's own court skipped, lock-free); a refusal there (a 409, a 401, a 404 for a match or competition the server no longer holds, or another 4xx the outbox would not retry on, `_serverKeepsRetrying`, which leaves out 429 and 403: a definite answer, so the operator is never asked to send the bout back for a start that will fail) leaves the running bout running and shows on the picked match, and a Send back or court move tapped while the pick is out is refused with a toast naming it (`refusedWhilePicking`, `courtChangeWhileStartingMessage`); only a start refused after an accepted check (a race, `clock_skew`, superseded) leaves the court idle with the running bout in the queue. With no answer, or offline or with unsent writes of the pick's competition that move a match's status, court or sides or a bar (`START_CHECK_WRITE_KINDS`, api_client.jsx: a lineup, member or time write does not count), the console asks the operator whether to send the running bout back and start the pick or keep it running (operator ruling 2026-10-27); the answer is carried out on the court as the latest render holds it (`deferAndStart` reads `latestRef.current`), and a court that changed while the question was open (the running bout finished or another started, or the pick no longer waiting) is judged again from the top; a start the server later refuses after "send it back" leaves the court idle as before. The refused match is never started on its own; if the blocking start fails instead, its own refusal stays. Accepted: the `result` group's projection also holds `CorrectionReason`/`ResultSource`, so a start over a match running under a different source or reason answers `heldGroups: ["result"]` and shows the refused sentence on a running match; the notice drops once live data shows it running (`startRefusalStands`), the toast stays. The console reads `startPatch`, `winnerSideLR` and `teamMatchMarks` by ES import (`start_match.jsx`, `side_marks.jsx`), and admin_shiaijo.jsx still must not import bracket.jsx); it skips the withdrawn competitor's matches through `sideBarredByDecision`/`involvesCompetitor` (`ineligible_match.jsx`), because the list shows them barred only after it refreshes. **A court that already runs a bout is a warning on the admin views, not a refusal** (bc-adna, operator decision D1): `/score` and the reopen still answer `court_busy` (`CheckCrossCompCourtBusyOnStart` for `/score` (under `WithCourtExclusivityLock`) and `CheckCrossCompCourtBusy` for the reopen (kachinuki.go), and the in-competition gate in `StartMatchTx`/`checkCourtExclusivityTx`) unless the request carries the request-only `forceCourt` (on `ScoreRequest` and `engine.ForceOptions` beside `StartOnly`, never on `MatchResult`, never stored; stripped for an anonymous self-run caller in `enforceSelfRunPolicy`). The court gates judge only a write that MOVES a match into running; a write to a match already running, and a finish, no longer ask the court, so a forced start never wedges the console. A forced start runs `startSidesGateTx` without the court half, so a barred side or a competitor fighting elsewhere still refuses it. The organiser's screens (the Scores tab and page, Pools, Bracket, which pass `allowCourtForce`) word the refusal as "Shiaijo <court> is already running a bout" with **Start anyway** / **Cancel**, and the reopen dialog gains **Reopen anyway** beside **Queue it and reopen**; the court console never passes `allowCourtForce`, so its own `court_busy` handling (pick another bout, send back, the blocker's `label`) is unchanged. Two bouts running on one court is accepted: the court's score table shows both and both can be scored, the TV board (`findRunningOnCourt`) shows the first it finds, and the court's operator sends one back to the queue.
- **A send back the outbox holds shows at once** (stage 6 review 7, operator rules "never blocks the UI" and "screens display what the operator changes"): the court console reads a match it sent back (the Send back confirm, and the send back a pick of another bout makes) as queued until its feed shows it scheduled (`withOwnStatusMove`, `ownStatusMoveHolds`, admin_shiaijo.jsx, read from the outbox's ONE owner `API.ownStatusMove` like a finish, stage 6 review 8, M4: never page state, so a reload or the console mounted again with the send back still queued shows it queued, with no editor): the bout leaves the live slot and the editor and shows in the queue, offline included, its start pin (`startedFrom`) dropped; a refused or discarded send back puts it back, and once answered a feed copy stamped after the send back's own stamp (started again elsewhere) ends it. A queued send back is also published at once on the court's channel (`_publishSendBack`, api_client.jsx: the bout as `scheduled` with its score, a court-less match publishes nothing, a refused or discarded send back publishes it running again; each names the status it moves from (`ifStatus`), and the display applies it only to a copy in that status (`applyPatchToTree`), so a bout it already holds finished from another device stays finished; a running court move's copy names the new court and its put-back the old one, since the display keeps a match's court when a patch names none, `mergeMatchPatch`), so a display on the same machine shows the bout back in the queue. Pinned in `admin_shiaijo.render.test.jsx` ("a send back still queued shows at once", its remount case) and `own_status_move.test.jsx` (the reload).
- **Send back to queue keeps the score** (operator ruling 2026-09-26, bc-sbq). `RevertMatchToQueue`/`requeueBracketMatch` clear only the verdict and the audit notes; points, penalties, overtime, bouts, flags and rep-bout fighters stay, the operator removes a wrong mark themselves, and the button is always offered (picking another bout sends a scored one back the same way; a confirmed running court move is a third send-back door: it goes through the same requeue body (`requeuePoolMatch` / `requeueBracketMatch`, internal/engine/scoring.go) and writes its history line through `recordRequeueHistory` naming the new court, so it keeps the score exactly like the Send back button and a pick of another bout). Starting the match again keeps them: the SPA's `startPatch` sends the request-only `startOnly` flag and `engine.keepQueuedScore` copies the stored score onto that write, because the wire cannot say "no score sent" (the start's empty arrays are the bytes of an operator clearing every mark, which must still clear, so the editors' own Start stays unflagged; `startOnly` with any status but `running` is a 400, since the stored score is swapped in after validation). A display of the court shows the kept score too: the court bridge's copy of a start-only write carries no scoreline field and states the flag counts the started match holds (`_broadcastPatch`, api_client.jsx, `START_BROADCAST_DROPS`), because the display reads a result naming a status that omits a count as 0 (`mergeMatchPatch`) and a key present as undefined wipes the copy it is merged onto (bc-evts stage 4 review 2, G1). The start's representative-bout winner is derived AFTER that swap (`deriveDaihyosenWinner`, scoring_tx.go), so it comes from the bouts the start keeps, never from rows it discards. While queued, every display shows the match as NOT STARTED through `matchShowsScore` (match_shows_score.jsx, a leaf every display ES-imports), which `IndividualScore`/`TeamScoreboard` apply to themselves; the score editors are the one exception. A queued knockout match's kept points do not make it "fought" (`bracketMatchStartedOrDecided` reads status and winner only), so correcting or reopening the match that feeds it re-seats it with its points and asks nothing when it starts. A FINISHED later match that a confirmed correction reopens keeps its points, bouts and flags too, only its verdict goes (`reopenDisplacedBracketMatch` through `reopenBracketMatchKeepingTheFight`, both the knockout and the pool-requalification doors). Engi flags are saved as they are entered (each flag a tap event since bc-evts stage 4, replayed into the match's `flags` group): a running engi write is not judged on the flag total (`engiRunningWrite`, scoring_tx.go) and the bracket write carries flags, so a send-back or switch keeps them.
