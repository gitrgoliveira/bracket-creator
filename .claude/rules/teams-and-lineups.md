# Team matches, lineups and kachinuki

Moved from CLAUDE.md "Key Algorithms". Read before changing team scoring, team members, lineups or kachinuki.

- **Team credit for a match-level decision**: when a completed, non-kachinuki team match is decided by a match-level kiken, fusenpai or fusensho (`domain.IsDefaultWinDecisionStr`: kiken/kiken-voluntary/kiken-injury/fusenpai/fusensho), every numbered bout with no result of its own is credited to the OTHER side, one individual victory and two points, the same figures a fusensho bout scores. `state.DefaultWinCreditSide(status, decision, decisionBy, att)` decides which side is credited (from `decisionBy` when set, else `domain.AttributeWinnerSide`); `state.SubBoutEffectiveResult` fills a credited bout's `Winner`/ippons (maru) without touching its `Decision`, so a credited bout carries no per-bout Kiken/Fus. mark of its own. These two functions are format-agnostic; kachinuki is excluded one level up, at WRITE time, not inside them: `state.NeedsDefaultWinBoutPadding`/`PadDefaultWinBoutPositions` (which synthesize the empty placeholder rows the credit functions act on) are gated on `!comp.IsKachinuki()` in `RecordMatchResultWithIneligibilityTx` (`engine/scoring_tx.go`), so a kachinuki encounter is never padded and so is never credited in practice. The same rule feeds the wire summary (`MatchResult.TeamResult()`/`BracketMatch.TeamResult()`), standings accrual (`accrueTeamSubResults`, `engine/scoring.go`), and the Excel export (`internal/export/builder.go`); the JS mirror is `web-mobile/js/team_default_credit.jsx`, consulted only when the server's own `teamResult` is absent. A score-sheet correction (`incoming.Decision` empty or `hikiwake`) over a stored kiken, fusenpai or fusensho keeps it, provided it SAW the ruling (a correction reason, `clearWithdrawal` or a basis holding it): a finish from a device that did not is a rival of the ruling and the replay refuses it `match_closed` before `preserveWithdrawalRuling` is asked, and one that displaces the ruling (it is the first result by stamp) keeps nothing (`displacesStoredResult`; see the closed-match rule in `.claude/rules/match-writes.md`). In a team match a match-level default-win decision merges by bout: the numbered bouts scored on a device that never saw it keep their scores and it credits only the bouts still without a result. `engine.KeepsWithdrawalRuling(storedStatus, storedDecision, incoming)` was widened from the old withdrawal-only check (`domain.IsWithdrawalDecisionStr`) to `domain.IsDefaultWinDecisionStr`, so a stored fusensho survives a correction exactly as a kiken/fusenpai does. The one correction that REPLACES the ruling is one sent with the request-only `clearWithdrawal` (`state.MatchResult.ClearsWithdrawal`, `json:"-"`, set by the `/score` handler; the editors' **Remove kiken** / **Remove fusenpai** / **Remove fusensho** in `RecordedWithdrawal`, the label naming the recorded decision): the payload is the real result, a win or a draw, the match stays completed and never takes the court, and `restoreIfWithdrawalRemoved` lifts the bar (operator ruling 2026-10-03: "an operator can fix a mistake, but the fix must leave the match resolved"). **Clear <decision> and reopen** (e.g. **Clear kiken and reopen**) stays beside it for a match with fighting left. Kachinuki is not offered the Remove button: a finished kachinuki encounter has no Save correction.
- **A fixed-order team bout row records NO fighter name, never the team's** (operator ruling 2026-09-17, bc-dnst: "the storage is the main source of truth"). The bout settles at the MATCH level, so when no lineup names a fighter the row knows no per-fighter identity and `buildPatch` writes `sideA`/`sideB` EMPTY. It used to write the team name there, which is not a person: every display then had to filter it back out, and the ones that did not showed the team's name where the competitor goes. Nothing needed the copy, because attribution reads the MATCH-level name first (`state.SubBoutWinnerSide`, whose `sub.SideA` arm is guarded against `"" == ""`; the JS `teamIVScore` fallback mirrors it) and the server's own quick-score path already wrote this shape. **The DAIHYOSEN row is the exception and keeps the team names**: the hantei mark is placed on the winner's side by comparing the winner against THAT row's `sideA`/`sideB` (`placeHt`), so blanking them drops the mark from the wire. The server keeps them too: `engine.AddDaihyosen` stores the match's team names on the row when the bout is added, and `seatBracketSide` (bracket_seat.go, the ONE owner of seating a knockout side) keeps the row's `sideA`/`sideB` equal to the match's on every seat, and carries the row's `Winner` to the new name when the side keeps its team and the Winner names the side by its old name, the row's own or the match's (a rename: `nameRepBoutRow` with `another` false and `matchOld` the match's name before the seat, since a row's side name can be blank or stale; the carry also runs when the row already reads the new name; `ReplaceParticipantInDraw` seats a side matched by id through it, `renameBracketSide`, and renames an id-less side's row name without clearing a pick), judging "another team" by id when both sides carry one and by name otherwise; a side given another team loses its representative pick there, dated after the pick it clears. `resolveBoutSideName`'s `teamNameA`/`teamNameB` filter stays for rows written BEFORE this rule; it is legacy handling, not a live guard.
- **A lineup vacancy is never flagged on the score sheet** (operator ruling 2026-09-16, bc-dnst). Team sizes are unregulated and a vacancy is legitimate play, so the sheet must not tell the operator to complete a lineup. The "SHIRO/AKA: Lineup incomplete, add the remaining players" notice was REMOVED with its predicate and its CSS; it never blocked anything, but it read as a requirement. Pinned by `team_editor_vacancy_not_flagged.render.test.jsx`, which exists because a removed warning otherwise leaves no failing test behind. Do not re-add it in any form.
- **Team Lineups & Kachinuki** (`internal/domain/team_lineup.go`, `internal/engine/kachinuki.go`): TeamLineup pins position→player for a round or a specific match (mp-825). Team sizes are unregulated and vacancies are never enforced: `TeamLineup.Validate`/`validateFive` (the FIK 5-person back-fill/DQ rule) were REMOVED (mp-gmcg); only the key-only `ValidatePositions` check remains. Kachinuki ("winner-stays-on") is operator-led: `engine.MaybeAdvanceKachinuki` is append-only (adds the next pairing; NEVER auto-finalizes; the roster snapshot is advisory) and the encounter ends only on an explicit `status: completed` score write, which strips trailing unscored auto-appended bouts. Both win rules, exhaustion and taisho-defeated, record `decision: "kachinuki-exhaustion"`; a drawn pool/league encounter is `hikiwake`. Whether a tied pair fights on in encho is the operator's call, on ANY bout and in ANY phase: the app records what happens and never decides how a match is run (operator ruling 2026-09-26). A taisho-only rule (bc-kten: the editor withheld Encho from any pair but the two taisho, and the server refused a new encho on such a pair) was built on 2026-09-25 and reversed the next day; do NOT re-add a pairing gate or a server refusal for encho. Whether a tied pairing must produce a result (e.g. the taisho must be defeated) is likewise OPERATOR DISCRETION, never derived from pool-vs-bracket (the phase-independence rule lives in `allowNumberedEnchoFromStore` (`handlers_match.go`) and `subBoutNeedsNumberedEnchoAllowance` (`validation.go`); do NOT re-scope numbered-bout encho by match-ID phase; that was tried and reverted). Only the knockout END stays blocked while tied (the bracket needs a winner, `validateBracketCompletion`). A kachinuki encounter never carries a match-level encho (operator ruling 2026-09-24, bc-kheb): one bout fought on in encho does not put the encounter in overtime, so (E) lives on that bout's row only. `state.Competition.ClearKachinukiEncounterEncho(matchID, ...)` is the one owner, and it leaves a pool representative bout or tie-break bout (`Pool X-DH-N`, `Pool X-TB-N`, the `state.IsPoolDaihyosenMatchID`/`IsTiebreakerMatchID` grammar) alone at all three sites below: that match IS one individual bout, whose overtime lives at match level: `applyKachinukiMerge` strips the field on every score write (logged, never refused, since an older client's queued write inherits it), the engine's decision write (`recordDecisionTx`) drops it before the decision's circles are counted, and the load repair `upgradeKachinukiEncounterEnchoLocked` clears what older releases stored, gated on the config.md marker `kachinuki_encounter_encho_cleared`, which `POST /competitions` sets on a competition created as kachinuki (it has nothing to repair) and which a match file the repair cannot read leaves unset, so a later start retries. The team editor sends none (`encounterEnchoCount`) and offers no match-level overtime stepper on a kachinuki encounter. Daihyosen does not exist in kachinuki → `POST .../daihyosen` returns 400. Mistakes: `POST /api/competitions/:id/matches/:mid/reopen` (a kachinuki match, or any match a kiken, kiken-injury, fusenpai or fusensho decided; a 400 otherwise) flips a completed match back to running, clearing winner/decision but keeping the bout log -- EXCEPT a kiken, fusenpai or fusensho whose `decisionBy` side is STILL barred by a withdrawal recorded on a DIFFERENT match: `engine.reopenTargetStatus` (`kachinuki.go`) sends that one to `scheduled` instead of `running`, because going straight to `running` would strand the operator behind the eligibility gate with no way to start it (clearing the match that recorded a bar moves that bar onto a chained fusenpai rather than lifting it); once the bar is gone, the competitor reinstated or the match that recorded it cleared, the identical reopen goes to `running` like any other decision; a reopen that lands `scheduled` takes no court, so neither court gate applies to it (the target status is decided before either gate runs); in a knockout, when the winner of the match being reopened or corrected went straight through a bye (a hidden, unnumbered match the draw leaves with one empty side, so nobody can open or reopen it directly), the write takes that winner back out of it (or re-seats the new one) and answers for the first real match past it (`propagatedDownstreamOf`), rather than refusing; a POOL reopen in a mixed competition is never refused for a seated knockout, because the write that finishes it runs the pool requalification check (`engine/pool_requalify.go`); `POST .../matches/:mid/requeue-blocker-and-reopen` atomically frees the target's court (requeuing the blocking match) and reopens under one court-lock hold; `DELETE .../matches/:mid/kachinuki-bout` removes the current trailing unscored auto-appended pairing. The live bout is the highest-position numbered row (`lastNumberedBout`), never the slice's last row: Record bout numbers its pairing one past it (`nextKachinukiBoutPosition`), and the removal, the un-record and the roster read all name that row. Record bout marks the bout it closes recorded (`SubMatchResult.Recorded`, wire `recorded`, the server-only merge group `recorded`), with or without a next pairing; removing a pairing Record bout appended clears it, and a write that adds an overtime period to the bout, or changes its result (winner side or decision), clears it too unless it is older than the mark or unstamped (`mergeHold.unrecordReopenedBouts`; an unstamped write cannot be ordered after the Record bout); Remove clears it only when the advance line that appended the removed pairing also set the mark; the advisory line's roster (`engine.KachinukiRoster`) keeps both fighters of the last bout on until it is recorded as a win (a running score is no result), and it answers Record bout's own decision on the stored match, asked quietly through the one `decideKachinukiAdvance` the advance writes from, over the same queues and retirements (`readKachinukiQueues`, built once per read): `nextPairing` (a tap would append; false on a recorded live bout greys Record bout out, but only from a read for the current bout log and lineups, never from an older answer the closing keeps) and each side's `exhausted` (the loser of a recorded win whose LINEUP has nobody left; never after a draw or without a lineup). A recorded last bout with no pairing after it reads closed (read-only, with the no-fighters-left line) exactly when those flags say so; the sheet never re-derives them from the queues. A bout copy never moves the mark (`state.CopyGroup`), and the merge re-applies the stored `recorded` group once every hold and displacement is done, so a mark a payload carries never lands; the sheet does not send it. Every numbered bout row of a team match shows the fighter's squad number and, when the position is unnamed, a typeable name box (operator ruling 2026-09-15, bc-dnst). The number belongs to the squad member, not the row: team order can change between matches, so picking a different member into a position moves that member's number onto the row. A fresh team's seeded blank slots are members with a number and no name, so an unnamed fixed-order position shows the number of the blank member seeded for it, and a name typed there names that member through `resolveMemberIdsForPositions` (rename, never a new mint while a blank slot with that number exists), so the name stays attached to the number it was shown with. A team's squad is seeded with team size + 2 numbered slots (`SquadReserveSlots`, two reserves), and the row's list shows every slot with its number, blank ones by number alone, so any number the team can field can be picked and then named; a picked slot is written by id (`buildInlineLineupWrite` with a member) and a name typed into it renames that member (operator ruling 2026-09-15, bc-dnst). That makes a picked-but-unnamed slot a real placement everywhere: every lineup writer (the score sheet row, the Up Next "Enter lineup" panel, the Lineups page) sends the position with an empty name and the member id rather than dropping it; `TeamLineup.OrderedMembers` counts a position occupied when it carries a name OR an id, so such a fighter is on the kachinuki roster; and `AdvanceKachinuki` decides which side stayed on through `domain.SubBoutAttribution`/`AttributeWinnerSide` (ids first), because the client records a nameless winner as its TEAM name plus the member id and a name comparison alone can never see it stay on. A lineup may not place one member id at two positions: `memberPlacedElsewhere` (lineup_resolver.jsx) is the ONE client predicate, asked by every writer before it writes (`buildInlineLineupWrite`, the panel's save, the Lineups page's add path) and rendered as the list filter `rosterWithoutPlacedElsewhere` on every picker, so the offer and the refusal ("<name> is already at <position>", worded once by `alreadyPlacedNote`, the position named by `lineupPositionLabel` on every surface; a change to a position takes a refusal down) never disagree; `ErrLineupDuplicateMember` from `ValidatePositions` (a 400 naming the two positions) is the server backstop. A lineup that already held a duplicate before this guard existed is repaired by clearing one of the two rows. Under kachinuki only the FIRST row is a lineup position; every later row's pick rides the bout itself (`pickManual` with the member id, never a lineup PUT), the list there is unfiltered because the fighter who stayed on legitimately repeats, and a name typed over a picked blank member renames that member and keeps its id. Which side stayed on is decided through `domain.AttributeWinnerSide`, whose id tier names a side when the winner id equals THAT side's id even if the other side carries none (JS mirror `attributeWinnerSide`, result_slot.jsx), with the same name-only residue `RetiredPlayersFromBoutLog` keeps for a row no id can settle. Before the draw a team has no number, so the Lineups page, the one operator surface for a team's people, labels a slot through `squadSlotLabel` ("Slot 3"), a sibling of `squadMemberLabel` in the same owner; spectator surfaces keep `squadMemberLabel` and stay bare before the draw. The competition Settings page's Squad members section was REMOVED on 2026-09-15 by operator decision (bc-dnst): the Lineups page is the one home for a team's people, and its "Team members" list's "Clear name" control (beside Rename) is where clearing a member's name now lives. The Lineups page's "+ Add" confirm is derived from the resolver's own three outcomes (an existing member is selected with no confirm, a blank slot is named, else a member is minted). A rename or a clear reaches every stored lineup: `RenameTeamMember`/`ClearTeamMemberName` rewrite the name of every lineup position holding that member by id (`renameMemberInLineupsLocked`), because the score sheet and the export read the lineup's stored name; fought bouts keep their frozen names. The Excel export indexes lineup positions by member id as well as by name (`memberKey`, `resolveKachinukiBoutPosition`) so a nameless fighter still gets its position label. Positions are ordered in ONE way, `domain.ComparePositions` (the FIK names in fighting order, then numbered positions by number, then any other by name), which the roster walk (`OrderedMembers`), the export and the member-id load repair share; a text sort put Chuken before Senpo and "10" before "2".
- **A team carries the lineup of its previous team match** (operator ruling 2026-10-05: "by default, a team carries the previous team match lineup. You can have a different team lineup in every team match"). `engine.LineupInForce` (`internal/engine/lineup_in_force.go`) is the ONE owner: the match's own lineup (read whole, even one that holds no position), else the latest lineup the team had before it in match order (an earlier match's, or its starting lineup, which comes before every match); a match the draw does not hold gets its own lineup or the starting lineup. A lineup saved for a later round is never read (see the migration bullet below). A lineup is matched by the team's participant id only, never by its name; an id-less side has none. Discarding a draw removes the lineups saved for its matches. Match order is the pool-match number, then the knockout by round and position, the 3rd-place match last; `state.TeamMatches` is the one list of a draw's team matches (a bye, a pool daihyosen or tie-break bout, and a league's or Swiss competition's vestigial bracket are none), for the rule and the migration alike. The kachinuki roster, the Kachinuki Detail export and every client surface (through `GET .../lineup-in-force/:matchId` and `resolveMatchLineup`) ask it; no surface derives a round to read a lineup. The Lineups page edits each team's starting lineup (stored as its round-0 entry) and any match's own lineup; **Use the previous match's lineup** removes a match's own lineup so it inherits again. **Copy from previous match** was removed because carrying over is the default; do not re-add it. A match the Lineups page has chosen that the team is no longer in (a correction seated another team) stays chosen, locked, Use the previous match's lineup included, with a notice naming it (`notInMatch`), rather than the page silently editing the starting lineup. The at-court lineup panel follows the match it was opened for: its host keeps the match's key and reads the row every render, so a side given another team gets that team's editor and a match that leaves the data closes the panel.
- **A lineup save names the positions it changed** (operator decision 2026-10-07, "Only changed positions"). `PUT .../match-lineups/:matchId` and `PUT .../lineups/0` take `changed` (`LineupRequest.Changed`), and the server lands only those positions (`domain.TeamLineup.ApplyChanges`), under the competition's lock, on the base it reads there (`lineupSave.base`): the match's own stored lineup, else the lineup in force there (`engine.LineupInForceFrom`, the one rule over what the transaction loaded, since the store's own reads would wait on the lock it holds), else empty; for the starting lineup, its stored entry, else empty. The answer is the whole lineup as stored. So two devices changing different positions both keep their change in either arrival order, a save sent later from a device that was offline included; the same position keeps the later arrival (accepted with that decision; do not report it as a new defect). A save without `changed` replaces the whole lineup, which is how a save queued by an older build replays. An empty `changed`, or a changed position `positions` has no entry for, is a 400; a member at two positions of the composed lineup is the existing duplicate 400 naming both. `web-mobile/js/lineup_save.jsx` (a leaf) is the client owner: `changedLineupSave` builds the body every writer sends (the Lineups page, the panel, and the sheet's name box through `buildInlineLineupWrite`), a cleared position as an empty name with no id, and `joinQueuedLineupSave` joins a save into a queued save of the same lineup (the union of `changed`, the later value per position; a queued entry with no `changed` stays whole with the change applied), for `_placeWrite`. Every lineup save is an outbox entry, answered at once and never awaited (bc-evts stage 3 review 1, operator rule "ALL goes to the outbox ... but never blocks the UI"): a match's lineup is an entry of that MATCH, sent strictly in its order with the match's score writes, decisions and the rest, and a team's starting lineup an entry under its own `lineup:` base; a save joins the base's last entry when that is a save of the same lineup (team, and match or round), so a later save can never land before an earlier one and lose to its replay (see the outbox paragraph in `.claude/rules/match-writes.md`). The three writers take what they sent as saved at once (the sheet's name box shows the pick on the lineup held and is never disabled; the panel and the Lineups page `confirmSaved` the form they sent), read the server's whole lineup from its `lineup-updated` announcement, say "Lineup saved" or the identity warning once `settled` resolves, and claim a refusal through `onRefusal`, said where the save was made, then read the lineup again (`write.read`, `form.retry`) so what showed as saved goes. Both lineup editors share `useLineupForm` and `LineupSourceLine` (`lineup_draft.jsx`): a lineup is saved only after it was read (`loadedKey`), `lineupToSave()` is the form with `changed` and reads nothing, and `confirmSaved` adopts the answered lineup, so a position another device changed shows once the save lands. Removing a match's own lineup (`deleteMatchLineup`, kind `lineup-remove`, a 404 being the outcome asked for) is an entry of that match too, after any save of it queued before, so it never waits for one; the form reads what the match carries once the removal has landed (bc-evts stage 3 review 2, R1). The team score sheet's name box sends `changed: [posKey]` on the lineup it holds for that side (`write.held()`), which the duplicate check and the rows need. A pick on a side it never read (the first read still out, or failed) is refused at once (`LINEUP_NOT_READ_NOTICE`) and reads that side in the background, so the next pick goes (nothing waits for the read, R1): with every save now landing only its own position, the reason is no longer an overwrite but that the rows of a lineup never read would show empty positions that may not be, which the operator would then fill over fighters they cannot see; such a side is read again when the connection returns, and a write of the side, sent or queued, counts as the side's latest read, so a read still out from before it never puts the old lineup back. Both lineup editors follow a `lineup-updated` naming their team (one naming no team counts for every team; one naming another is ignored), once a read of the lineup still out has shown it: the lineup is read again and shown while the form has no unsaved change, and the team's members are read again either way, since the list is not the operator's edit (reads begun in the same tick share one `fetchSquads`, `requestMembers`). A Save makes no read: a member another device adds is announced, so the editors' lists hold it. If this device missed that event, a name typed for that member resolves against the stale list, the server refuses a second member of that name (`squadDuplicateNameCheck`), and the position saves by name with the identity warning (accepted, weighed 2026-10-07: a bounded read at every Save added a second wait on a link that does not answer, against a rare race that ends visible).
- **Team members carry a server stamp** (operator decision 2026-10-07): `TeamMember.ModifiedAt`, set by every member write (see the team-members paragraph under Common Pitfalls in CLAUDE.md). `mergeMembers` (lineup_draft.jsx) is the ONE client rule: the union by member id (no screen removes a member), each member's copy with the larger stamp (the arriving copy on a tie), in member number order. Every list that reaches an editor or the sheet (a read's answer, the host's `teamMembers` copy, the viewer payload) and every member write (`addTeamMember`, `renameTeamMember` and `clearTeamMember`, each an outbox entry under the team's starting-lineup base, answered at once, `_memberWrite`, bc-evts stage 3 review 2, R1: the add mints the member's id, a lowercase UUID v4 the server takes, `AddTeamMemberAs`, and a match's lineup save is queued `after` the team's last member write, so the member is added before the lineup that places it; each returns the member as this device shows it, stamped now in server time, with `settled` carrying the server's stamped copy and a refusal's `revertMember` the member as it was, stamped later) goes through it, so an older list can never put back an older name and a later change made elsewhere always shows. The editors' own changes go through `useLineupForm.changeMembers`/`memberRenamed(member)`, the sheet's through `wroteSideMembers` and its lists through `takeSideMembers`; none of them reads again, since every member write is announced. A member object built by hand carries no stamp and loses to every list: an own write's member is the API's (stamped now, so it stands over the list's older copy until the server's own copy comes; an add's carries none, since no list holds it yet). A list or an answer made for a team the editor has since left lands nowhere (`teamKey` against `squadTeam`). Nothing waits for the team's members (R1): a name typed while their read is out is not resolved (`newMembersWait`, lineup_draft.jsx, the one owner of whether that read is over: `useLineupForm.membersReadOver()` for the panel and the Lineups page, the sheet's per-side state for its name boxes), since against no members a new name would be minted where the position's seeded slot is free, and the name of a member the team has would be refused by the server as a second one: the panel's Save and the sheet's name box save it by name alone, with no id and the members-unavailable warning, the Lineups page's add row refuses it at once and keeps the typed name, and a typed representative is refused at once. Only a READ's list ends the read, even an empty one, never an own write, and so does the read made as an editor opens failing or not being answered by `FETCH_TIMEOUT_MS` (stage 3 review 3, F1: a read that never answers left every typed name unresolved for the editor's life; a list arriving after the deadline is still shown). Once a read has failed or timed out the name is resolved without the members, as it always was, with the members-unavailable warning. The refusal of a name typed while the read is out is worded once, `membersNotReadNotice` (lineup_draft.jsx), for the Lineups page's add row and the sheet's typed representative. A member add the server refuses (any 4xx but `member_id_conflict`, which says the id is held), or one an operator discards that never went out, leaves its minted id naming nobody (stage 3 review 3, F2), and both ends take it out: the outbox (`_dropMemberThatNeverWas`, api_client.jsx) takes the id off every queued lineup save before that save goes (the position keeps its name), and off every queued score write's bout rows (a numbered row keeps its fighter's name, a representative pick is cleared; stage 3 review 4, G1), and off every queued tap (a fighter or representative pick's `memberId`, which a tap naming a minted member follows the add on too, `_payloadMemberIds`; stage 3 review 5, H4), another tab holding copies of those writes takes the id off its own when the add leaves storage with the stored copies stripped (which tells a refused add from one that landed, whose id stays on them) and raises the event there too (`_onStoredQueueChanged`, `_stripMemberId`, stage 3 review 5, H3), and such an add also leaves a short-lived note in browser storage (`bc_dropped_member_ids_v1`, `_noteDroppedMember`) that every tab applies to its own entries before each pass, to the entries it takes up and to the stored list as it is written, so the strip does not depend on which copies a tab held when the add left (J5, stage 3 review 6; pruned once nothing names the id and it is ten minutes old). Nothing else takes an id off (stage 3 review 7, K1, `_memberAddLeftUnlanded`): an add that went out (`sent`, set and stored as it goes, or `attempts`) and is then discarded, or refused `member_id_conflict`, may be one the server kept (a 500 can be `state.ErrTxCommitted`, a request given up on may have landed), so the team's members are read again with the add's password (`_checkMemberAdd`), every write of this tab naming the member waits for that read as on a queued `after` (`_waitsOnMemberCheck`, the read's end reruns the flush; another tab's copies go as they were made), and only a list without the id proves the add never landed (then the strip, the note and the event above); a list with it, or a read that fails, takes nothing off, and those writes go as they were made for the server to judge. Accepted: a self-run participant's add carries no password, so its read is refused (the members GET is main-gated) and a discard of it takes nothing off.
