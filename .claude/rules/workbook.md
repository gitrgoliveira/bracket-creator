# Excel workbooks

Moved from CLAUDE.md "Key Algorithms" and "Excel workbook construction". Read before changing any workbook output.

- **Excel Layout**: Uses an **8-column per court** layout. Columns A and G (and their court-shifted counterparts) are 30 units wide; others are 5 units wide. A blank row separates pools vertically.
- **Team block bout rows** (`state.Competition.TeamBoutRows`, with `domain.KachinukiMaxBouts`): the ONE owner of how many numbered bout rows a team match's block has in any workbook: 0 for an individual competition, TeamSize for a team match, 2 x TeamSize - 1 for kachinuki (the most bouts a winner-stays-on encounter can take). `RenderCompetitionWorkbook` passes it to the renderers (the Pool Matches and Elimination Matches blocks, the 3rd-place block, their IV/PW formula ranges and page heights) and `BuildResultsWorkbook` to the overlays, which skip a bout Position past it rather than write into the next block. **The app's "Download blank template" is always `ExportCompetitionXlsx`**, through the admin-gated `GET /api/competitions/:id/export` (`API.exportDrawTemplate`), the source of the Export PDFs too, so the template, the prints and the matches the app runs are one draw. The mobile-app router mounts no `/create` (the CLI's `serve` keeps it, and `TestNewRouter_MountsTheExportDoorAndNoStatelessCreate` pins the app's side). Once there is a draw (any status but setup, the negation of `state.CanGenerateDraw`) the export prints the STORED draw: its pool counting formulas are live (`AttachPoolMatches` points each match's sides into its own pool's Players slice, the pointer `helper.PrintPoolMatches` links a player's formulas by; pinned by `TestExportCompetitionXlsx_PoolCountingFormulasAreLive`), it prints no result on the main sheets, and it carries /create's finish (`finishTemplate`: the Time Estimator filled in, `helper.ProtectAllSheets`); a knockout-only competition's empty Pool Draw and Pool Matches sheets are deleted in `RenderCompetitionWorkbook`, as /create's knockout deletes them. `TestStoredDrawTemplateMatchesCreate` (cmd) pins the two templates to one shape for every format. **With no draw yet the export is the blank layout** (`blankLayoutXlsx`, internal/engine/blank_layout.go; operator decisions E2 and E3, 2026-11-18): the layout the draw would print for the same number of places with every place empty, no name, dojo, seed or number, and no Names to Print or Tags sheet (nobody to name). `blankPlaceCount` sizes it by the schedule estimate's count rule (`countForEstimate`: the larger of the expected number of participants and everyone registered, check-in ignored); fewer than 2 is `ErrBlankLayoutTooFew`, and a competition whose settings cannot form a draw for that many is `ErrBlankLayoutUnbuildable`, both `IsUnexportable` sentinels, so the door answers 422 with a sentence naming the fix and Export PDFs leaves the competition out with it. The places go through the draw's OWN generators, in memory and stored nowhere: `formPools`, `createPoolMatches` and `layoutPoolMatches` (internal/engine/pools.go) are the pool phase `generatePools` runs, refusals included, and `knockoutDrawFromLeaves` the knockout's, so the template cannot drift from the draw it prints; never restate a pool refusal or the court spread in the blank path. The places carry stand-in names the generators need (they refuse a blank name or dojo and read an empty bracket side as a bye), and `helper.BlankCellsHolding` then blanks every cell that printed one: on the Data sheet it becomes the empty-text formula (`=""`, the one form a referring formula reads as blank where a truly empty cell reads 0), and a literal stand-in on any other sheet (a knockout tree's first round, a Kachinuki Detail section's team names) becomes a reference to its Data cell, so a name typed on the Data sheet shows on every sheet. A competition with no draw has no numbered roster (`KnockoutNamesToPrint` answers nothing unless `DrawSourceFor` is `DrawInBracket`), so the results workbook of one prints no Names to Print and no names on its Data sheet either. The main sheets' team block skips the representative bout (position -1), so its height and IV/PW ranges stay `TeamBoutRows`' alone; that bout is on the Representative Bouts sheet (see Workbook owners). An encounter with more bouts (reserves fielded) keeps them all on the Kachinuki Detail sheet, which lists a match's recorded bouts, or that many empty numbered rows for one with none, in every workbook (`helper.BlankKachinukiSections` for `/create`'s own draw, which leaves that sheet unprotected, and for the blank layout), so it can be filled in by hand (operator decision 2026-09-27, bc-kdsc). The blank layout's detail sheet lists the skeleton the Elimination Matches sheet printed (the same rounds, through `helper.BlankKachinukiSections`), so the two sheets have one source. `helper.breakBeforeEliminationBlock` is the one page rule for every block on the Elimination Matches sheet, the 3rd-place block included, so a block that fits on one page never prints across two. A block taller than a page (a team of 17 or more, which only the CLI or API allows; the app caps teams at 9) still does. Never restate 2n-1 for a workbook, in Go or JS; the one other use is the score editor's own cap on manually added kachinuki bouts (`kachinukiMaxBouts`, admin_scoring_team.jsx), which is taken from `MAX_TEAM_SIZE`, not from a team's size. `TestCreateHandler_WithoutTeamMatchTypeMatchesTheExamples` reproduces four committed example workbooks byte for byte through `/create`, so a rendering change must regenerate them (`make examples`).
- **Workbook owners.** `engine.AttachPoolMatches` is the ONE Pool Matches source for both engine exports (the results workbook, and the stored-draw export `ExportCompetitionXlsx` behind `GET /api/competitions/:id/export` and the Export PDFs prints): never rely on a cached `pool.Matches`, since pools.csv records membership only and a restart empties it (the stored-draw export printed no match block after a restart until bc-kdsc). `engine.PrintedBracket` is how those exports name a stored bracket match: its block title (`helper.EliminationMatchTitle`, or `helper.ThirdPlaceLabel` for the bronze) and its sides, a side not decided yet as `helper.MatchRefLabel`'s "M n", never an internal id such as "Winner of r2-m1". The results overlay, the Kachinuki Detail sheet and the Representative Bouts sheet all name through it, so a detail section and the "M n" that points at it read alike. `/create` has no stored bracket; `helper.BlankKachinukiSections` names its draw's matches through the same owners (`helper.EliminationMatchTitle`, `helper.MatchRefLabel`, `helper.ThirdPlaceLabel`, `helper.PoolMatchLabel`).
- **Representative Bouts sheet** (`helper.WriteRepresentativeBoutsSheet`, `helper.SheetRepresentativeBouts`): a fixed-order team competition's workbook carries it exactly when a stored match holds a representative bout (a -1 row); kachinuki never has one. `engine.RepresentativeBoutMatches`/`collectRepresentativeBouts` (representative_export.go) walk the draw in the Kachinuki Detail sheet's order (`detailDraw.sections`) and take each bout's score, marks and centre from that sheet's own `boutFigures`, so the two sheets cannot disagree on a bout; the row is labelled `helper.RepresentativeBoutRowLabel` ("DH"). Both engine exports carry it (the stored-draw export and the results workbook); `/create`, the four committed examples and the Export PDFs prints do not (the PDF groups select sheets by name and list neither detail sheet). The row keeps the TEAM names by rule, so a representative is printed only from a member id that resolves in that side's team (`representativeOf`), never from the stored name; otherwise the bout prints its label alone.

## Excel workbook construction


The workbook is built entirely from code in `internal/excel/template.go` (`NewFileFromScratch`). Each sheet (data, Time Estimator, Pool Draw, Pool Matches, Elimination Matches, Names to Print, Tree) is created and styled programmatically. Layout constants (rows-per-page, spacing, max bracket size) and sheet name constants (`SheetData`, `SheetPoolDraw`, etc.) live in `internal/helper/constants.go`. Use these constants everywhere rather than string literals.

**excelize is pinned to a master commit, not a release** (`v2.11.1-0.20261010030226-066c84b8f7de`, operator decision 2026-10-10, PR #463): v2.11.0 carries fifteen advisories that fail CI's Anchore image scan (`validate`, severity medium and up), each fixed only on excelize's master, and no release after v2.11.0 existed. Move to the first tagged release that contains those fixes. `govulncheck` does not see them (it counts reachable code); to reproduce the scan, run grype on the built binary (`docker run --rm -v <dir>:/scan:ro anchore/grype:latest dir:/scan --fail-on medium`; the image is `FROM scratch`, so the binary is all it scans). An excelize version change rewrites the bytes of the committed example workbooks (this one changed only font property order and numbers written to 15 significant digits), so `TestCreateHandler_WithoutTeamMatchTypeMatchesTheExamples` fails: regenerate them with `make examples` and compare the workbooks' XML (cells, formulas, styles, page breaks), not their bytes, before committing.
