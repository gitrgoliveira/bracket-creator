# Match writes: merge, refusal and the clock frame

Moved from CLAUDE.md "Merge changes, never drop" and "Write refusal and the clock frame". Read before changing any match write, its answer, the offline queue, or a score editor's save path.

## Merge changes, never drop (bc-mrgc)


Operator ruling 2026-10-03: "Nothing should be dropped. All events must be ordered." A match write is merged GROUP BY GROUP onto the stored match, ordered by the stamp of when the change was made (`modifiedAt`, server-relative, never arrival order), and what does not apply is kept in the match's history. Each rule below has one owner; change the owner, never a call site.

- **The groups** (`internal/state/match_groups.go`, the ONE owner of which fields each holds): `points` (IpponsA/B, HansokuA/B), `result` (Status, Winner/WinnerID, Decision/DecisionBy/DecisionReason, and the CorrectionReason/ResultSource that describe it), `encho`, `flags` (engi), `rep` (pool rep players), `recorded` (the SERVER's alone, `state.ServerGroups`: which numbered kachinuki bouts Record bout closed, as sorted positions; a client naming it in `changed` is a 400, the merge copies the stored marks over a client's rows, and `bout:N` does not hold the mark, so a point on bout N and Record bout never fence each other), `repPickA` and `repPickB` (each side's representative picked for a team match's representative bout, SideAMemberID and SideBMemberID of the -1 row: each dated apart from the other side's and from `bout:-1`, so two captains picking at the same moment both land, a point on that bout never erases a pick and a pick never erases a point; the row's WinnerMemberID stays with the bout and the merge re-derives it when the two disagree, `ReconcileWinnerMemberID`), and `bout:<position>` per SubResults row (1..n, -1). Sides and ids, court, schedule, round, ReopenPending, IsOverridden and the bracket structure are NOT groups: their own writers keep them. `CopyGroup` moves a group, `GroupDiffers` compares one, `GroupValue` projects one for the history; nothing hand-copies a field list.
- **The stamps**: `GroupStamps map[string]int64` on `MatchResult` and `BracketMatch` (pool-matches.csv: the `GroupStamps` column, index 29, JSON, appended after `ModifiedAt`; bracket.json: `groupStamps`). A match with NO map reads every group as stamped at its `ModifiedAt` (legacy files behave exactly as the whole-match guard did); once a map exists, a group with no entry was never written (0). `ModifiedAt` stays the newest group stamp (recency and `keepNewerMatches` read it). A bout whose row is gone keeps its stamp: a TOMBSTONE, so an older write still carrying the row cannot resurrect it. `stampGroups` (`MatchResult.StampGroups`/`BracketMatch.StampGroups`) is the ONE stamper: it materializes a legacy match's implicit stamps before stamping one group, or every other group would start reading the new `ModifiedAt`, and it never LOWERS a group's stamp (a caller that already holds a later one for a group -- an engi finish let through as a HeldEcho under an older stamp -- must not drag it backwards, or a change genuinely made between the two would wrongly read as applying after a group it never actually followed; mirrors `ModifiedAt`'s own never-lower rule); a stamp the MERGE decided, which may be lower (the displacement of scoring a result closed out moves it out and gives the group the result's own stamp), is written as decided through `ApplyMergedGroupStamps`, never through `stampGroups`. Every writer that changes a group outside the merge stamps it through it: the reopen (`reopenPoolMatch`/`reopenBracketMatch`, server now), the requeue (`RevertMatchToQueue`/`requeueBracketMatch`: the verdict only, the kept score keeps its stamps), override-winner (`result`, and its own comparison is on that group), the engi finish (`result`+`flags`, at the client's stamp once the merge has ordered it, `engiFinishHeld`; server now only for an unstamped writer), the kachinuki advance (the `recorded` mark, and the appended `bout:n` + `result`, at the server's time and strictly after the match's `ModifiedAt`, so every device's `keepNewerMatches` orders the marked copy after the one before it; the Record-bout answer echoes the bout log AND the stamps the advance left, `engine.KachinukiAdvance`, and the team editor adopts the stamp with the log, so its next tap on the new bout is floored by it, bc-hlck), `RemoveTrailingKachinukiBout` (the removed bout's tombstone, and `recorded` when it un-records), the merge itself for `recorded` when a write raises a recorded bout's overtime, and a downstream reopen (`reopenDisplacedBracketMatch`, `bout:-1` with it). Byes auto-completed at draw time carry no stamp, which is right.
- **The wire**: `MatchResult.Changed` (`json:"-"`, request-only, beside `ClearsWithdrawal`) is read from `/score`'s and each bulk entry's `changed`; a name that is not a group is a 400. ABSENT means every group the payload carries (`defaultChangedGroups`; on the pool branch a nil SubResults still names the stored rows, the whole-struct write's old meaning), EXCEPT that a client's running or scheduled write over a COMPLETED match never carries `result` (`effectiveChangedGroups`). Every server-built write names its groups: decision `result`+`points`+`encho` (`decisionChangedGroups`), both-barred hikiwake `result`, daihyosen add `bout:-1`+`result`+`repPickA`+`repPickB` and remove `bout:-1`+`result`+`encho`+`repPickA`+`repPickB` (both date both sides' picks, so a pick made on the previous representative bout is held, never landed on the new one; +`points` when clearing the verdict took a hantei mark out, `daihyosenChangedGroups`), quick-score every group and every stored row (`WholeMatchChangedGroups`), a start (`startOnly`) `result` alone. The rows the server itself changes after the writer sent them (kachinuki merge, the padding a match-level decision adds) are added by `noteServerBoutChanges`; in a kachinuki write, which merges its bout log by position, a stored row the writer left out counts too, so the finish's strip of a trailing unscored pairing is named and not copied back. It and `daihyosenChangedGroups` (mobileapp, the representative-bout add and remove, built from the stored match under the same lock) are the two places the server diffs, each its own values under the write's lock; a CLIENT payload is never diffed against the store, or an echoed stale group with a newer stamp would read as an edit. A server-built door reaching the merge with `Changed` nil is logged as a BUG (`serverBuiltWithoutGroups`). A bracket door that gives a side another team without reopening that match records a `reseat` history line naming the cleared pick group (`recordRepPickClears`, bracket_seat_audit.go: a snapshot of every match's picks before the door's write, diffed after, in the same transaction; `ResolveQualifiedPools`, the resolver run after a pool write or a `DELETE .../overrides`, is such a door, in its own `WithTransaction`); a reopened match's `downstream-reopen` line names the pick instead, and a refused write's restore records nothing. `MatchResult.WriteDoor` names the door for the history.
- **The merge owner**: `mergeMatchWrite` (engine/match_merge.go), called by BOTH branches before anything else judges the write (`applyPoolWrite`; `applyBracketResultIn` for rounds and bronze, ahead of `preserveWithdrawalRuling` and the downstream guard), each after folding the stored pairing into the write (`reconcileSides`; on the bracket branch `sidesBeforeMerge`), so a winner worked out again reads the stored sides, never a payload's omitted ones. An UNSTAMPED write the server orders itself (a completing write, or any write a server door builds: quick-score, an engine caller, a decision with no stamp) takes the server's time there, never older than the stored `ModifiedAt` (`writeStamp`), so it leaves a fence a later stale replay is ordered against; only a client's unstamped running or scheduled write keeps the unstamped bypass. A changed group applies when `domain.ApplyByTimestamp(stamp, storedGroupStamp)` (0 on either side applies) and takes the write's stamp; otherwise the stored value is copied in and the group is HELD (its incoming value goes to `MergeReport.HeldValues`). A group the write does not change always takes the stored value. An applied group whose value equals the stored one is `Unchanged` (an echo); for a write that NAMES NO groups at all (`Changed` nil: bulk-score, an older client, which cannot tell an echo from a change) it keeps the stamp it already had rather than taking the write's, and `ModifiedAt` moves only when some applied group actually changed, so a whole-match echo can never fence out a real, older change made on another device in the gap. A write that NAMES a group takes the write's stamp there even when the group echoes: naming it is a real action taken at that time (an operator re-sends the value their screen showed, or a replayed decision), not a re-send of everything the write happened to carry, and `ModifiedAt` moves with it. A HELD group whose value equals the stored one is no loss (`HeldEcho`, bc-mrgc phase 3: a decision's "no overtime" over a match with none): it is neither listed in `heldGroups` nor kept in `HeldValues`, and its history outcome is `unchanged`. The write is SUPERSEDED only when something is held (or echo-held) and every applied group is an echo (`MergeReport.Superseded`): then nothing is written to the match file, exactly as before. The report rides on `MatchResult.Merge`; `ResultChanged` false (the verdict did not move: held, or applied as an echo of the stored one, e.g. the same withdrawal sent again under a later stamp) skips the eligibility record, since re-recording a stored withdrawal would rewrite its status and undo a reinstatement made since. Corrections get no exemption: a stale correction is held like any other change.
- **The closed-match rule** (operator ruling 2026-10-15, replacing R2, R3, R4, S2 and S3, whose "points scored means the withdrawal was a mistake", "stay finished, add the point" and "it needs a winner" it supersedes): in STAMP order, once a finish or a decision (kiken, fusenpai, fusensho, hantei, daihyosen, hikiwake, a both-barred hikiwake) is recorded, any tap event or scoring write stamped AFTER it is refused and kept in the history, and the device is told the match is finished and to tap Correct. It is the same whichever arrives first: the replay (`closed()` in score_replay.go, `judgeOverFinished`) orders every line by its stamp, so a tap that reached the server before the finish is `applied` and then flips to `matchClosed` when the finish arrives, and a finish stamped before a stored point closes that point out into the history (`MergeReport.Displaced`, door `displaced`, reason `HoldReasonMatchClosed`). Answers: an event `matchClosed` with `reason: match_closed` and `MatchClosedMessage` (engine/match_merge.go, the one sentence both doors use); a score, decision or bulk-score write fully refused is the 200 `{applied:false, reason:"superseded", heldReason:"match_closed", heldGroups}` (`state.HeldReasonMatchClosed`), and one applied in part (a finish that closed out a stored point) adds `displacedGroups` with the same `heldReason`. `default_win_stands`, `needs_winner` and `heldDecision` are gone: one code, one remedy. What is stamped BEFORE the result keeps D5 (contained in the result's basis -> `recorded`, else `beforeBaseline`, worded "Not applied: the result was recorded without this change ... tap Correct"; `contains` also requires the tap to be stamped no later than the baseline, since a server-built write's `Seen` is arrival order). A finish or decision governs EVERY scoring group and the overtime at its stamp, the ones it names and the ones it does not (a fought Finish on a running match names `result` alone): `replayer.closedBefore` (Go) and `closedBefore` in `replayHead` (JS) turn away an event stamped before the first finishing result after it in stamp order (`closingResults`; a start or send back between them shields nothing) that the result's SENT basis does not hold, whichever arrives first; a result that sent no basis (an older build's, or the server's own) is taken to have seen every event stamped before it, since "what had arrived" hangs on arrival order and "nothing" would strip an older build's finish of its scoreline; a group the result itself sets is judged by `absorb` as before (a decision's loser keeps its points: such a tap is `recorded` when the decision held it, or sent no basis, else `applied`, never claiming a decision held what it never saw; the winner's tap, which the decision's circles replace, is `recorded` on the same test and `beforeBaseline` only when a sent basis never held it, so the operator who scored and then recorded the decision on the same device is never told "Not applied", stage 6 review 6; the JS fold has no such branch, a decision being replayed in Go only), a fixed-order team match's bouts a match-level kiken, fusenpai or fusensho leaves open stay open (T1), and the server's own fighter events are never turned away (stage 6 review 4; golden cases "D5: ...", the matrix, `closed_match_before_finish_test.go`). THE FIRST RECORDED RESULT STANDS (operator decision 2026-10-16, I1, replacing "a newer finish or decision over an older one is the newer one"): in stamp order, a later finish or decision from a device that did not see the result in force is a RIVAL (`rivalResult`, score_replay.go) and is refused `match_closed` like scoring, kept in the history, in every arrival order (two finishes from two devices included). It is logged as it was sent (`MergeReport.Baseline`, `recordSupersededWriteHistory`, only once the match's log has begun), and when the first result arrives second the stored one is displaced into the history (`MergeReport.Displaced` names the `result` group; `displacesStoredResult` also stops `preserveWithdrawalRuling` keeping a ruling that was displaced, and the finish pads nothing of its own, `writesAsRival`: a SENT basis that saw nothing is no more a correction than none). A result is NO rival when it saw the one in force: it names a correction (`CorrectionReason`, `ClearsWithdrawal`: baseline `Informed`), sent a `basis` whose `Seen` holds the line of the result (`BasisSent`, `Basis.Seen`; every client door sends one since stage 3, `{seen, own, seq}` with the device's event `session`, which the baseline carries so the seq arm counts the device's own taps), or is the server's own unstamped write (`mergeCtx.serverStamped`); a result that says what the match already holds in every group is an echo, not a rival. Only the score, engi and decision doors can rival: reopen, requeue, override-winner, bulk and quick score and the engine's own callers never do. A kiken that wins by being first bars its competitor; the displaced finish's winner does not advance. A PLAYED OR STARTED NEXT KNOCKOUT MATCH LOCKS THE STORED RESULT (operator decision K1, 2026-10-16, `result_lock.go`): once the match one hop down has a result of its own or is running, a rival that would displace the stored result (`rivalDisplacesResult`: a finished result must be IN FORCE at the end of the log the write found, none after a reopen or a send back to the queue, and the write must displace something, ANY group of it, since the lock covers the whole stored result, scoreline included; baseline neither `Informed` nor carrying a SENT basis that holds the line that set that result. "In force" and "saw" have ONE owner, `ResultInForceAt`/`resultInForceIn` in score_replay.go, which reads the stamp-ordered log exactly as the replay does (`replayer.resultInForce`: `govern[result]` while the match it left is finished) and caps a basis to the lines the log holds (`basisSawLine`; the replay is told the log's own count, `ReplayShape.withLogLines`, so the lines the write mints are never seen); every caller reads the log as the merge does, through ONE owner, `replayLines` (score_log_write.go: the migration baseline of an empty log, else the drift or repair line appended), and a repair line fills ids only: it applies a group only while its value differs from the one the replay holds at that point in filled ids alone (`replayer.repairFillsIDs`, the rule `repairFillsIDsOnly` minted it by) and is skipped otherwise, so stamped at the stored match's stamps it never puts back a result an earlier-stamped one displaced since, and it never moves the line that set the result (`replayer.resultBy`), so a basis that saw the finish still saw it after a load-time winner-id repair; a DRIFT line (a fault: the stored match says what no line explains) that carries `result` is judged by I1 like any result (`rivalResult`: its basis is the lines it was minted over, so a first-by-stamp result logged after it is one it did not see, and it is held as a rival); a legitimate out-of-log result write (e.g. `ReplaceParticipantInDraw` renaming a finished match's winner, replace_participant.go) is recorded as such a drift line, and so is held as a rival if an older result nobody had seen arrives after it (accepted under I1); `rivalResult`, the lock (the merge sets `MergeReport.StoredResultInForce`/`StoredResultSeen`), the padding gate `writesAsRival` and the `/score` handler's reason check all ask it, so none judges a basis against "any completed line") is HELD whole instead of reaching the downstream guard's 409 (which lost it): `holdAsLocked` turns the report into a held one (`MergeReport.ResultLocked`, history reason `HoldReasonResultLocked` (`HoldReasonResultLockedRunning` when the next round is only under way), values kept in the history, once however often it is resent (`recordLockedHoldHistory`: a line with the same door, stamp, reason, groups and values is not added again, anonymous self-run resends included), NO score-log baseline, since a logged older result would replay over the stored one), and the door answers the 200 superseded with `heldReason` `downstream_knockout_played` or `downstream_knockout_running` and `ResultLockedPlayedMessage`/`ResultLockedRunningMessage` ("the next round was already fought ... tap Correct"). The bracket arm is in `applyBracketResultIn`; a rival decision skips `refuseDecisionReachingRunningMatch` so the lock holds it instead of the 409; the pool arm (`requalifyMixedPoolWriteLocked`) runs the requalification WITHOUT force for a rival, whatever the caller sent, and holds it on the refusal after the rollback (`lockedByRequalification`), so force never reopens a played knockout match for a rival. An explicit correction keeps the 409 and its force option; before the next match is played or started I1 applies as above; the engi finish follows I1 (an older finish over a stored FINISH is the first recorded result and displaces it, flags and verdict together; `HoldReasonEngiAtomic` is kept for a stored match that is not completed) and the same lock, before its own downstream guard (`knockoutLockCode` for a knockout match, `requalifyMixedPoolWriteLocked` for a mixed pool). The `/score` handler no longer answers such a finish with the 400 `missing correction reason`, which a queued replay would loop on: `applyCorrectionReason` (given a `seenResultCheck`, score door only) lets a reason-less finish stamped after the stored result through when its basis does not hold the result, and the replay answers 200 superseded `match_closed`; `clearWithdrawal`, a basis holding the result, an EQUAL stamp (unless the write is the exact resend of the recorded finish, which `ExactScoreReplay` answers as recorded) and a write with no stamp still need their reason, while an OLDER stamp needs none (the replay orders it, as above). A score log this build cannot read cannot say whether the basis saw the result: the write is judged as one whose basis did NOT see it (`seenResultCheck.sawResult` logs an ERROR naming the file and line and answers false), never the 400, and goes on to the engine (which reads the same log as empty), so it ends match_closed with a line in the match's history rather than being dropped unrecorded; only the score-events door answers `score_log_unreadable`. A baseline-minted mark's id is `b:<pos>:<side>:<letter>:<n>` (`markID`), a function of what the mark is and never of the baseline that introduced it, so an older save of the same mark arriving later cannot change the id a device read from its answer and removes by. Minted ids are a pure function of the stamp-sorted log; a client event id may not start with `b:` (400 for the batch, `ScoreEvent.Validate`), so it cannot collide with one. Accepted: an id can be reused after a removal (a removal from a device that saw the original, stamped after a re-add, removes the new mark), and ids read from an answer can shift when an earlier-stamped line arrives later, because the id names bout, side and letter. A TEAM fixed-order match closed by a match-level kiken, fusenpai or fusensho MERGES BY BOUT (T1, `boutsStayOpen`): the numbered bouts a device that never saw the decision scored (a bout row, a team finish's rows, a tap) keep their scores whichever way they arrive, the decision credits only the numbered bouts still without a result (`padDefaultWin`) and decides the match, and a later team finish's own match-level result is refused as a rival while its bout rows land; a team match closed by a FINISH, and a kachinuki match (bouts are a log with nothing to credit), stay closed whole. A decision's points are worked out by the replay, not copied from the value it carries (`keepLoserPoints`: the circles for the side that did not withdraw, the points the withdrawer struck BEFORE it, FIK Art. 32), and the default-win bout padding is the replay's too (`padDefaultWin`), so the loser's points and the padded rows are the same in every arrival order. A correction (a completed write naming `result`), a reopen, override-winner and a send back to the queue are results or opens in their own right, ordered by their stamp: after a reopen the match is open again from the reopen's stamp. A running or scheduled write over a finished match never carries `result` (`effectiveChangedGroups`); an UNSTAMPED one cannot be ordered and is held whole. The score handler still treats it as a correction (no court gate, no StartMatchTx: `writesOverFinished`) so the answer is `match_closed` and never a court refusal. The client reads it through `writeMatchClosed`/`writeDisplacedForClosedMatch`/`writeResultLocked` (write_result.jsx; `needs_winner`, `default_win_stands` and `heldDecision` are retired, and check-write-result.mjs forbids the two codes); the matrix `internal/engine/match_write_permutations_test.go` pins one outcome per case for every arrival order, with the answer of every write, `ModifiedAt`, the competitor's status and the knockout winner advancing.
- **The history** (internal/state/match_history.go): one append-only file per match, `competitions/<id>/history/<url.PathEscape(matchID)>.jsonl`, one JSON line per write that reached the merge: stamp, server `receivedAt`, door, session, changed groups, per-group outcome (`applied`/`unchanged`/`held`), the held groups' incoming values, any cleared withdrawal, and the `reason` when one rule held the write's groups rather than their stamps (`MergeReport.HoldReason`: `HoldReasonOlderRevision`, `HoldReasonEngiAtomic`, `HoldReasonMatchClosed`, `HoldReasonRepBoutRemoved`; the History view shows it as "Not applied: <reason>"). `StoreTx.AppendMatchHistory` stages the whole small file in the SAME transaction as the write (`LoadMatchHistory` reads it, read-your-own-writes), so an aborted transaction leaves no entry. Written at the point the write can no longer be rolled back (`recordWriteHistory`: after K3/requalification in `RecordMatchResultWithIneligibilityTx`, in `writeMatchResult`, and on the superseded paths), so a write refused by validation, a side mismatch or K3 leaves none; every direct writer above appends its own (`recordDirectHistory`) INSIDE the transaction that makes its write: the doors already in one (the reopens, the kachinuki bout remove, the downstream reopen) pass their `tx`, and the kachinuki advance, `OverrideBracketWinner` and `RevertMatchToQueue` each open a `WithTransaction` for the write and the entry together (`withBracketMatch` takes the store handle, as `withPoolMatch` does), so a process dying between the two leaves no match change without its line; a held override writes nothing and appends on its own. `recordDirectHistory` logs a failed append rather than returning it, so a failure of the append alone still lets the write commit without its entry (accepted). The history directory is created only under an existing competition directory (`ensureMatchHistoryDirLocked`), so a write after `DeleteCompetition` fails rather than resurrecting it; `DiscardDraw` deletes it (`DeleteMatchHistory`), since a regenerated draw reuses the match ids. A fully-held write must COMMIT its transaction for its entry to land: every door returns nil from its closure on `ErrMatchSuperseded` and answers after (the score/decision handlers always did; bulk-score, both daihyosen paths and `RecordMatchResult` were changed to).
- **The answers**: a write applied in part answers applied (the merged result) plus `heldGroups` (`scoreResponseWithReopened`, `withHeldGroups`, bulk-score's top-level `heldGroups`); a fully-held one keeps the 200 `{applied:false, reason:"superseded"}` shape the SPA keys on, plus `heldGroups` (`respondSuperseded`, `SupersededMessage`: "kept in the match's history"). Either answer adds `heldReason: "match_closed"` when the closed-match rule turned the write's scoring away (`MergeReport.HeldReason`; a fully held one then carries `MatchClosedMessage`; bulk-score puts it on the entry), and an applied finish or decision that closed stored later-stamped scoring out into the history adds `displacedGroups` (`MergeReport.DisplacedGroups`) with the same `heldReason` (score, decision, daihyosen, bulk-score's `heldGroups[]` items). `ErrMatchSuperseded` is returned as `*SupersededError` carrying the held groups and that code (`errors.Is` still matches; `HeldGroupsOf`/`HeldReasonOf` read them). A completed write stamped OLDER than the stored `result` group over a finished match is not asked for a correction reason (`applyCorrectionReason`, `matchSnapshot.ResultStamp`): a stale finish is ordered by the replay (its verdict is the older of two results and is held, its other groups by their own stamps), and one that changes nothing is answered superseded and kept in the history. An equal stamp that changes nothing (every group the write changes, `effectiveChangedGroups`, equal to the stored value once read as the write would land it) is the finish already recorded, sent again because its answer was lost: `engine.ExactScoreReplay` (the score counterpart of `exactDecisionReplay`) lets it past the reason check, and the engine answers it as recorded (`answerExactScoreReplay`, in `RecordMatchResultWithIneligibilityTx` after the older-revision hold and before the engi dispatch, so before every refusal): the stored match, with a bracket match's court and schedule filled in, nothing written, and one history line whose groups all read unchanged (none for an anonymous self-run participant's resend, `ForceOptions.NoReplayHistory`, so looping it cannot grow the history file). A same-stamp write that differs still needs a reason. The request-only fields (`Changed`, `WriteDoor`, `Merge`, `ClearsWithdrawal`) never ride on a stored copy: `MatchResult.ClearRequestFields` is the one list, called on the pool write's overwrite and on every pool-match copy the store hands out.

- **The client (phase 2)**: every score write names its groups. `web-mobile/js/match_groups.jsx` is the ONE client owner of the names (pinned against `state.ScalarGroups`/`BoutGroup` by the shared table `internal/state/testdata/match_groups.json`: `TestMatchGroups_SharedTable` and `match_groups_table.test.jsx`), of the comparison (`changedGroups`, on WIRE shapes only: both sides go through `toBackendMatchResult`, the adopted copy via `matchWire` in api_serializers.jsx, so a placeholder slot, an Ht placement or a winner object never reads as a change; a field the write leaves out, e.g. an omitted correction reason or a silent representative bout's ippons, is not compared, and a bout row the write does not carry is never a change), of the union (`unionChanged`: no list on either side means every group and stays so) and of a group's words (`groupLabel`). `useChangedGroups(m)` (admin_scoring_autosave.jsx) is the one hook the three editors call; every patch goes through its `claim` (the individual and team `buildPatch`, a hantei included since bc-htsd, the engi save; on a running match the team sheet agrees every group no pending tap of its own moves, since its board is the server's copy with those taps on it). A group counts against TWO baselines: the server value the editor last AGREED with for that group (seeded at mount, moved on at each build where local equals the prop, and by `claim.agree(group)` when an editor's adopt TAKES the server's value for that group, or when the team editor's withdrawal-removal Undo puts the whole board back to the server's (every bout group and both pick groups); an adopt that takes only PART of a group agrees it only when the editor's whole group then equals the server's (the individual editor's hantei adopt skips `points` while a point of its own is unsaved; a representative-side adopt agrees `rep` only when both sides then hold the server's picks); both baselines are kept per group), NOT the latest prop, or an edit held while another device changed a group the editor kept its own value for would put the old value back; and the last write the editor built, or a tap taken back before the first write's echo would name nothing. A reopen is a write the server makes, not a build, so when the match the editor renders leaves `completed` (a reopen, or a send back to the queue) the editor takes the result it now holds as agreed, that group alone (`useChangedGroups`): without it, ending a reopened match again with the verdict it had named nothing, and the server kept the match running with no error. A single sender per base was weighed and not built: a per-base lease in storage, or only the tab that made an entry sending it while that tab is alive, needs a liveness signal between tabs (a heartbeat and a lease that expires and is taken over), and the shared outbox's "any live tab sends" is exactly what keeps a closed tab's writes alive; the cost is out of proportion to a case that needs two tabs of one device changing one match's court, time or lineup within one flush pass, under one operator per court. The results are not affected: they are ordered by their stamps, whatever the arrival order. Do not report it as a new defect.
  - **Override-winner** stamps and orders the `result` group (phase 1); a held assertion is answered `respondSuperseded(["result"])` (reason `superseded`, `heldGroups`), the client returns `heldGroups`, the Resolve feeders toast says it was kept in the history (`OVERRIDE_HELD_NOTICE`, write_result.jsx), and a queued one the server held counts into the pass's superseded alert as well as asking for a bracket resync.

Nothing is lost (the held values are in the match's history as always).

## Write refusal and the clock frame (bc-lww1 / bc-cse)


A match write can be REFUSED by the server, and a refusal is always **HTTP 200** carrying `{"applied": false, "reason": ...}`, never a 4xx/5xx, because the SPA's offline write queue retries 5xx forever (the mp-q8c6 poisoned-queue pattern) and a refused write can never win a retry. Two reasons exist on the write doors (`/score`, `/decision`, `/override-winner`, both daihyosen paths); a third, `score_log_unreadable`, is answered only by the score-events door (`POST .../score-events`, per event, when the match's score log cannot be read), never by `/score`:

- `superseded`: the merge held every group the write changes (bc-mrgc): a NEWER change to each is already stored. Nothing of it was applied, and it is NOT lost: its values are in the match's history and the answer names `heldGroups`. The operator must **not** blindly re-enter: a fresh entry is stamped now and would overwrite the newer change.
- `clock_skew`: the write's `modifiedAt` was more than 5s in the server's future (`modifiedAtRefuseSkewMs`, handlers_match.go), so it is provably wrong. Nothing was stored, the client resyncs its `/api/time` offset, and re-entering IS the remedy. The copy for the two cases is deliberately opposite; do not merge them.

**Which endpoints compete on timestamps**: `/score`, `/override-winner`, `/decision` (since mp-jnvl) and both daihyosen paths (since bc-dhas) each carry the client's stamp, so any of them can be refused for either reason. Quick-score alone still builds its result with NO stamp; the merge gives it the server's time, never older than the stored stamp (`writeStamp`, bc-mrgc review), so it still always applies and now leaves a fence a stale replay is ordered against; it maps the refusal shape defensively anyway. The daihyosen add and remove are stamped so the match they write is newer than a copy read before them, which is what lets `keepNewerMatches` keep the post-add copy over a stale refetch. Both take an optional JSON body `{"modifiedAt": N}` (the DELETE too; an empty body is unstamped and always applies), judged by `daihyosenWriteStamp` through the same `clientClockSkew`/`clampClientModifiedAt` pair as `/decision`; the stamp rides on the match the handler writes, so the ordinary write guard decides. `recordDaihyosen`/`removeDaihyosen` hand a refusal back as the refusal body (`_daihyosenOutcome`), and the team editor reports it through `notLandedBanner` and adopts nothing. A decision is stamped because it is the write that CLOSES a match, and a match closed while still `scheduled` (a queue row's Record fusensho) has no earlier write to inherit a stamp from, so the result carried no time at all and nothing downstream could order it. A stale decision is answered `superseded` before any of the decision's refusals judges it (`recordDecisionTx` asks the merge on a copy, `decisionHeldByMerge`: already barred, a running later match), since each of those would otherwise read as something to resolve and send again; an EXACT replay of the recorded decision is answered as recorded, before them too (`exactDecisionReplay`), from the prior and without a write; for a bracket match that prior is `bracketMatchAsResult`'s projection, which carries no court or schedule, so the replay branch fills them from the bracket (`bracketMatchCourtAndSchedule`, bracket_result.go) as a fresh decision's write echoes them, and the answer and its broadcast keep the court. A held override-winner answers `superseded` with `heldGroups: ["result"]`. The stamp reaches the engine through a VARIADIC parameter on `RecordDecision`/`RecordDecisionTx`: the engine-internal caller and the suite's decision tests omit it, and the handler is the one caller that must always pass it.

**`web-mobile/js/write_result.jsx` owns that whole rule**: `writeDidNotLand` (queued OR refused), `writePending` (the outbox holds the write, `{pending: true, settled}`: `writeDidNotLand` is false for it, so every host closes or advances on it at once and reads `settled` or its `onRefusal` later, never waiting; Two distinctions that look like details and are not:

- **`writeDidNotLand` vs `writeWasSuperseded`.** Both mean "not stored", but a QUEUED write lands on reconnect, so an offline court must still advance its local bracket; a REFUSED one never lands, so anything derived from it is wrong. Gate optimistic UI on the stronger predicate and general "did it save" checks on the broader one.
- **Client clock stamps are server-relative**, learned from `GET /api/time` (retried until it first succeeds, relearned on SSE connect, on `'online'`, on any refusal, and when the 15s heartbeat's `nowMs` diverges by more than 3s). The heartbeat value is a divergence TRIPWIRE only, never an offset source: a one-way push has no RTT to correct, so a late frame would drag the device's clock frame backwards. A payload is stamped when the client builds it (a tap at the moment it is made, see the bc-sync paragraph below) and a queued one replays verbatim; a replay refused for skew is re-stamped once, by `_restampFor`, which computes TWO reconstructions and keeps the OLDER: `enqueuedAt + fresh offset` (wrong if the OS stepped the wall clock mid-outage) and `serverNow - monotonic age` (wrong if `performance.now()` froze during suspend). Taking the older is a safety rule, not a tie-break: an over-old stamp only makes this write lose a comparison it might have won, which is recoverable and announced, while an over-new one is the silent overwrite bc-lww1 exists to stop. The monotonic anchor is stamped at the one enqueue chokepoint and **stripped on persist**: it is measured from a per-document time origin, so a rehydrated reading (or one written by another tab) subtracts two different zeros and yields an age unbounded in BOTH directions, which is exactly what `min()` cannot defend against. A rehydrated entry therefore falls back to wall-clock only, so a clock step spanning a reload still ends in a drop. Retried exactly once either way.
- **A write is never stamped older than the match it was made against** (bc-hlck, operator request 2026-10-03). Two devices' server-time estimates can differ by up to the 5 s the server accepts, so a device running ahead stamps its write later than real time, and a change made a moment later on another device that SAW that write was stamped earlier than it and kept in the history instead of applied. `_stampAfterSeen` (api_client.jsx) is the ONE rule, a hybrid logical clock: this device's stamp, or the seen match's `modifiedAt + 1`, whichever is later, the floor capped at this device's time + 4 s (`HLC_FLOOR_MAX_AHEAD_MS`) so it never draws a `clock_skew` refusal. The server is unchanged: the match's `modifiedAt` is already the newest stamp it holds. What was "seen" is the caller's: the match handed to `recordScore`, `seenModifiedAt` in a decision body (stripped before sending, so `recordDecision` keeps its 4-argument call shape), the trailing argument of `overrideBracketWinner` (omitted by `recordOverrideWinner` when the feeder has no stamp, so that call is as it was) and of `recordDaihyosen`/`removeDaihyosen` (the team editor passes the shown match's stamp, 0 when it has none). The direct clock-skew resends of a score and of a hand-set winner re-stamp through the same floor. A TAP is floored by the match as it was when tapped: every editor's taps (individual, engi, and team since bc-evts stage 5) carry the match their board was made against (`recordTap`'s `baseMatch`), so a change another device made AFTER the tap never moves it (the 2026-09-27 ruling); the team sheet also floors a tap by the stamp the last Record bout answer gave the match (`recordBoutStampRef`), so a tap on the pairing the advance appended orders after it. A queued entry records the floor (`seenModifiedAt` on the descriptor, persisted, the later of two when one write takes another's place) and the skew re-stamp keeps it. Accepted residual: there is no per-device counter, so two writes floored by the same seen stamp share the stamp `seen + 1` and the later arrival wins an equal-stamp tie; across two devices (three on one match within about 4 s, against one operator per court) a local counter could not order them anyway, and on one device the server already does (the running rev guard's strict `<=`).

**A representative-bout add or remove is the outbox's, and the sheet shows it at once** (bc-dhas, bc-evts stage 3). The add and remove go through `_daihyosenRequest` (api_client.jsx) as entries of the match like every rule-bound write: `settled` resolves the stored match (`_daihyosenOutcome`: a refusal body when it was held) or rejects with the not-added/not-removed sentence (`_doorRefusal`). The hold that kept the old autosave back (`hold()`/`release()`, `daihyosenBusy`) and the bounded pre-save are gone. The sheet shows the change at once (`matchOverride`: the row added or taken off, the match running, and a remove clearing the team match's overtime as the server's does) and adopts the server's answer when it comes, through `settled` (`adoptServerSubs`); a later change outdates an earlier answer (`repChangeTokenRef`), so a stale answer never overrides a newer local state. A discard from the held-writes list puts the server's sheet back, and so does a refusal, with its sentence beside the change, claimed through `onRefusal` so the outbox does not say it again. The override goes once the prop holds the answer (`holdsAnswer`). Add and Remove stay disabled while a typed representative is being named (`repTyping`). Since the button is replaced at once, the bounce of the tap that pressed it would land on its replacement: Add and Remove representative bout, and Record bout and Remove this bout, each pair sharing one place, take the tap through `acceptTap` on `boutChangeTapRef` keyed by that place ("rep", "bout"; tap_guard.jsx, bc-dtfn), so a double tap adds, records or removes once. The admin hosts' refetch after a write is bounded (`refreshCompsBestEffort` asks `fetchCompetitions({ bounded: true })`), and one given up on at that deadline says nothing: `_fetchJson` rejects past its deadline with the one `timedOut` error however the abort surfaced, and `refreshFailureToast` (admin.jsx) returns no toast for it, because the hosts refresh after every write and on a slow link the toast would follow every few taps while the write reaches the page by push anyway. The outbox reads every answer through `_fetchJson` too, so a body that stalls past the deadline is a network failure: the entry stays and is sent again with the stamp it was sent with, safe if the server did store it because an exact resend of a recorded finish or decision is answered as recorded (`engine.ExactScoreReplay`, `exactDecisionReplay`), with no correction reason asked; a running write's equal stamp re-applies.

**The persisted outbox is shared by every tab** of this build: it is stored under `bc_write_queue_v2` (`QUEUE_STORAGE_KEY`, stage 3 review 3, F4), never under `bc_write_queue`, the key older builds use, since an older tab open across the upgrade read this build's entries (tap events it does not know), rewrote them into its own score writes and pruned the key on a 4xx. What an older build stores under the old key is taken over (`_takeOverLegacyQueue`: on load, after this build's own queue, and on every `storage` event of the old key) and the old key is handed back as `[]`, never removed, because an older tab drops each entry of its own that the stored list no longer holds (it reads it as sent by another tab), so the new owner is the one sender; a removal would only make it drop what it took up from other tabs. An entry the older tab has out at that moment can be sent by both, a resend the server answers as recorded; an entry this tab already took over is never taken over again (`_takenFromLegacy`, by key and `enqueuedAt`, so a newer write an older build stores under the same key still is; stage 3 review 4, G5). A bare `_writeQueue.delete` leaves the stored copy for the merge to keep, and the write is replayed on the next load. A write two tabs hold can be sent by both, which is harmless (last-write-wins). A revoked password is scrubbed from every stored entry, another tab's included (`_parkStoredEntries`).

**A superseded write leaves NO FOOTPRINT on the match, on either branch; its one footprint is its match history entry** (bc-mrgc). `UpdatePoolMatchByID`'s mutate returns an `error` and the store skips the save when it does, the contract `UpdateBracket` has always had, so `applyPoolWrite`'s superseded verdict aborts rather than re-serializing the untouched row and bumping the standings-cache version. Two rules come with it. The abort is reported through the ERROR and NEVER through `found`: `found` stays true because the match WAS there, and signalling `(false, nil)` would make `writeToPoolOrBracket` read a rejected pool write as "not a pool match" and go hunting for it in the bracket. And BOTH `storeTx` branches must honour it, the WAL-staged one included, or a drop leaves no trace outside a transaction and a WAL entry inside one. Pinned across all six cells of `superseded_matrix_test.go`, which asserts the file bytes AND `Store.FileVersion` are unchanged after a drop; reverting the abort reddens exactly the two pool cells.

**On the client a live score never goes back in time under a score editor.** A refetch can read the data just before a write commits and answer after a newer push or a newer refetch has landed; taken whole, it put the older scoreline back, and an open score editor that had caught up adopted it, so its next save wrote the lost point away. The refetch sinks a score editor reads from therefore merge through `patch.jsx`'s `keepNewerMatches` (`keepNewerCompetitions` for a list, `keepNewerDetail` for a competition detail, `keepNewerTournament` for the tournament): the court console's feed, the admin competition view, the public competition page (`selectedCompData` in app.jsx, every refetch through `takeCompDetail`, since self-run gave that page a score editor), and the tournament's competitions (the Scores tab's source, fed by the admin's refreshes and by the app's `load()` outside display mode). A held match is kept only when BOTH copies are RUNNING and the fetched one is older: by the server's `scoreVersion` when both carry one (the match's score-log line count, which only grows and reads no device's clock; `olderByScoreVersion`, data.jsx, the ONE reading of the field, asked by `mergeMatchPatch` for a push and by `isOlderRunningCopy`, patch.jsx, for a refetch and for the individual editor's board), else by stamp (the fetched one stamped and older). Stamps come from two clocks: a client write carries the device's estimate of server time (accepted up to 5s ahead), a reopen, requeue or send-back the server's own, so a newer server stamp can read older; every server-stamped change moves the status, so running-against-running never weighs one clock against the other. An unstamped fetched copy (a draw discarded and drawn again reuses the match ids) always replaces. The display takes a refetch whole: no editor reads it, and its reload must discard its optimistic broadcast overlay. Accepted residual: a holder that never saw a match leave running (the Scores tab's list, which takes no pushes) can keep a running copy stamped by a device whose clock runs a few seconds ahead over the server-stamped running row of a reopen made within those seconds (e.g. a mistaken withdrawal reopened at once). Both show the match live; the held copy can still show the winner's letters that the withdrawal replaced with its circles, until the next write to that match replaces it.

**A display on the same device shows the operator's board; one on another device shows a tap once the server has it** (operator decision S1 a, bc-evts stage 3).
