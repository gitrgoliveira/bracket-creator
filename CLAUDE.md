## Git / Worktree Rules

- **Edit only inside the correct worktree, never the main checkout.** This repo uses a git worktree per PR, under `.claude/worktrees/`. Before the first edit or git operation, confirm the checkout with `git rev-parse --show-toplevel` and the branch with `git branch --show-current`. Edits landing in the wrong worktree (or the `main` checkout) force costly patch-and-revert recovery.
- The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing.
- **Never `cd` inside a Bash command to reach a repo.** Address the worktree explicitly (`git -C <abs-path>`, `make -C <abs-path>`) or run from its root. A `cd` in a chain has sent git to the wrong checkout and left the shell there for later calls.

## Tool selection (read before every tool call on a code file)

This project uses Serena, an MCP server exposing semantic, symbol-aware tools. **Serena's tools are the PRIMARY tools for code work here.** The built-in Read, Glob, Grep and Edit are SECONDARY and must not be used on code files when a Serena equivalent exists.

**Serena only serves the languages `.serena/project.yml` lists**, so check that file rather than assuming coverage. It IS tracked in git as of PR #439 (`.gitignore` ignores `.serena/*` and re-includes that one file) and carries `language_servers: [go, typescript, scss]`. Tracking was the only available fix: Serena generates the file per project DIRECTORY (`project_serena_folder_location: "$projectDir/.serena"`) and this repo uses a worktree per PR, so before #439 every new worktree auto-detected `[go]` alone, and editing the main checkout's copy propagated to nothing. **But the active set is bound when a session activates the project, not when the file appears**, so a worktree predating #439 stays Go-only until a session starts with the file — measured here, where a mid-session fast-forward brought the file in and `get_symbols_overview` on a `.jsx` still failed with `Active language servers: ['go']`. When it matters, ask Serena rather than the file: the error names the active set. For any source that set does not cover there is no language server, the symbol tools below cannot work, and you should use the built-in Read/Edit/Glob/Grep on it directly instead of spending a Serena call that cannot succeed. On `.jsx` the JS server reads and edits symbols correctly, and `web-mobile/jsconfig.json` gives it a project, so `find_referencing_symbols` follows ES `import`s across modules, tests included. Without that file it saw only the symbol's own file (`resultSlot` missed its real importer, `match_scoreboard.jsx`), so a reference search from a checkout that lacks it proves nothing. It still cannot follow wiring that has no import to follow: about a third of the top-level `js/*.jsx` modules carry no ES `import` at all, cross-module wiring leans on `window.*` globals (`window.API` alone has over 200 references outside the tests), and Preact is a vendored UMD global rather than an npm dependency. Treat a reference search there as a lower bound and grep as well for anything reachable through `window.*`. Keep that jsconfig to the options it has: esbuild reads it too, and the Makefile passes only `--jsx-factory`/`--jsx-fragment`, so an option those flags do not override changes the shipped bundle (`"jsx": "react-jsx"` there makes the compiled JSX import `react/jsx-runtime`, which the page does not load).

The built-in tool descriptions in your context say things like "use Read for a known path" and "prefer dedicated tools (Read, Edit, Write, Glob, Grep)". Those are written for projects without Serena and are SUPERSEDED here; when they conflict with this section, this section wins. Do not rationalize the built-in tools with "the file is small", "I already know what I need", "this is one call versus three", or "the path is known" — those rationalizations have produced incorrect behaviour before and are explicitly disallowed.

## Project Overview

A Go CLI and web application for generating kendo tournament brackets as Excel spreadsheets. Supports multiple competition formats: **Knockout** (direct elimination), **Mixed** (round-robin pools then knockout), **League** (full round-robin), and **Swiss** (Swiss-system across N rounds). Input is CSV, output is Excel with formula-linked cells for bracket visualization. The web API is documented via an OpenAPI specification in `specs/openapi.yaml`.

- **`internal/helper`**: Where the actual logic lives. Types here include Excel coordinates (`sheetName`, `cell` fields) tightly coupled to output generation. This is the primary implementation.
- **`internal/domain`**: Clean domain models (Player, Pool, Tournament, Match, Seed) being phased in gradually. Don't confuse these with the helper types.

### Key Algorithms

- **Binary tree brackets** (`helper/tree.go`): `Node` struct with `Left`/`Right` children, recursive subdivision for multi-page output. `helper.MaxPlayersPerTree = 16` (constants.go).
- **Seeding** (`helper/seed.go`): `StandardSeeding()` uses `generateBracketOrder()` for placement. `ApplySeeds()` handles collisions by swapping seed values. Seed names are title-cased with cases.Title(NoLower) and then looked up exactly by (name, dojo) in domain.RosterIndex; accents and non-initial capitals must match (NormalizeParticipantName is NOT on this path). `delayDojoMeetings` (same file) then delays dojo-mate meetings across the unseeded slots; its acceptance is SUM-DRIVEN by operator ruling (2026-08-31): a swap may pull an already-deep dojo's first meeting one round earlier to push the draw's earliest meetings later. Do NOT add a per-dojo never-earlier veto here: that rule belongs to the POOL exchange pass (`improveDojoMeetings`), and a finding that reports the deep-dojo trade as a regression is re-litigating the ruling.
- **Pool creation** (`helper/pool_distribution_tree_aware.go`): members are placed ONE AT A TIME in the roster's pre-shuffled order (no re-sorting -- shuffling is upstream's job), each descending the knockout skeleton tree by recorded per-node dojo counts (fewer of my dojo, then more room, then left); seeds are placed first on their EKC/D7 slots and recorded. A single pairwise exchange pass follows with a strictly tiered objective: per-pool spread-cap excess, winner-path round-1 count, winner-path meeting sum, then the all-qualifier crossing best effort -- each tier only resolves what the tier above left tied. No rotations. A crossed 2nd-place meeting a dojo-mate is ACCEPTED chance (operator ruling); never "fix" it beyond the tie-break tier. The old greedy fill's `assignPlayersToPools`/`discoverPool` survive only for `CreatePools` direct callers (estimator, goldens), where unique-dojo rosters make them identity-equal; `leastConflictedPool` is NOT one of those retirees -- it is load-bearing in the tree-aware distributor itself, called from three sites (`pickDojoTreeAwarePool`'s two fallbacks plus `poolUnderDojoCap`) as the descent's own least-conflicted fallback when the dojo tree has nothing to say. Pools distributed contiguously across shiaijo. **Competitor numbers belong to draw positions, never to people before a draw exists** (operator ruling 2026-09-06): once the entrant count fixes the pools and the tree, the positions are numbered pool by pool (`helper.NumberPools`, K1-K4 the first pool) and seeds and everyone else are placed into those positions; nothing is shown before the draw is generated (the earlier provisional registration-order numbers were removed as confusing). A knockout-only competition follows the SAME rule down the bracket instead of pool by pool (bc-pnum ruling 2, 2026-09-07): `helper.StandardSeeding`'s own placement order is recorded as `state.Bracket.DrawOrder` (participant ids, top of the tree to the bottom) when the draw is generated, and `engine.NumberKnockoutParticipants` composes each competitor's number from their position in it at read time; a competitor excluded from the draw (e.g. not checked in), or a bracket generated before this field existed, carries no number -- there is no participant-order or name-based fallback. **Changing any of this reddens a test that names a docs file**: the pool-draw page carries an interactive walk-through (`docs/assets/javascripts/pool-draw-animation.js`) that replays this descent in JS, and its example rosters' drawn pools are a fixture between markers in that same file, pinned by `TestPoolDrawDocWalkthroughMatchesTheDraw` (`internal/helper`) re-running them through the real distributor. That is deliberate: a recorded outcome rots silently otherwise. Update the fixture, then re-check the JS descent against it in a browser, since the test pins the recorded pools and not the JavaScript.
- **Tree-aware seeding** (`helper/seed.go`): `placeSeedIndices`, called from `buildPoolPhaseTreeAwareCore` (`helper/pool_distribution_tree_aware.go`; `PoolSeeding` itself was removed as dead code, bc-drwx item 11), places seeds so the top seeds land in different halves/quarters of the knockout TREE (D7, enforced via tree paths in seed_warnings.go); the EKF rank-to-court order is that tree contract's sheet encoding, since courts own contiguous chunks of the tree. Courts are NOT an overlay here: `numCourts` is the modulus `seedPoolRank`/`seedCourtOrder` compute the seed spread against, so a wrong court count places seeds in the wrong quarter. (Courts genuinely are an overlay for the SEPARATE dojo-tree descent that places the unseeded -- see the Pool creation bullet above -- which reads a court index only to derive `drawCourts` up front and to reorder for courts at the very end, never in between.) **Wrapped seeds** (rank beyond `numPools`, e.g. rank 5 over 4 pools -- reachable from a contiguous seeding with more ranks than pools, or from check-in dropping a mid-sequence seed and leaving a gap, `TestGenerateDraw_SeedGapFromCheckInKeepsD6Placement`): the extra seed takes the next pool (in the same rank-priority order the natural arithmetic defines) with room holding NO seed; failing that, the next with room holding no DOJO-MATE; only once both fail does it fall through to D6's unconditional placement. Once placed, a wrapped seed is never moved by anything downstream -- not the pool exchange pass (`improveDojoMeetings`, which excludes every seeded slot from both sides of a swap) and not `delayDojoMeetings` (which only ever moves unseeded slots, via its own `occupied` guard). `seed_warnings.go`'s halves/quarters/shiaijo checks are scoped to ranks `<= maxSeedRanks` for the same reason: a wrapped seed has no half/quarter home in D6's structure, so scoring it against those checks by its COUNT position in the placed-seeds list (rather than by its rank value) produced a spurious "could not be split into halves" warning for a wrapped seed that had landed cleanly in its own seed-free pool (bc-pnum operator ruling; restores what an earlier review round had narrowed to the dojo-mate case alone).
- **Pool Scoring & Tie-breaking**:
    - **Individual Tournaments**:
        1. Higher number of fights won.
        2. Lower number of fights lost.
        3. Higher number of hikiwake (Matches Tied).
        4. Higher number of points scored.
        5. Lower number of points lost.
    - **Team Tournaments**:
        1. Higher number of team matches won (W).
        2. Lower number of team matches lost (L).
        3. Higher number of draws in team matches (T).
        4. Higher number of individual winners (IV).
        5. Lower number of individual losses (IL).
        6. Higher number of individual draws (IT).
        7. Higher number of points scored (PW).
        8. Lower number of points lost (PL).
- **Team default-win credit**: when a completed, non-kachinuki team match is decided by a match-level default win (`domain.IsDefaultWinDecisionStr`: kiken/kiken-voluntary/kiken-injury/fusenpai/fusensho), every numbered bout with no result of its own is credited to the OTHER side, one individual victory and two points, the same figures a fusensho bout scores. `state.DefaultWinCreditSide(status, decision, decisionBy, att)` decides which side is credited (from `decisionBy` when set, else `domain.AttributeWinnerSide`); `state.SubBoutEffectiveResult` fills a credited bout's `Winner`/ippons (maru) without touching its `Decision`, so a credited bout carries no per-bout Kiken/Fus. mark of its own. These two functions are format-agnostic; kachinuki is excluded one level up, at WRITE time, not inside them: `state.NeedsDefaultWinBoutPadding`/`PadDefaultWinBoutPositions` (which synthesize the empty placeholder rows the credit functions act on) are gated on `!comp.IsKachinuki()` in `RecordMatchResultWithIneligibilityTx` (`engine/scoring_tx.go`), so a kachinuki encounter is never padded and so is never credited in practice. The same rule feeds the wire summary (`MatchResult.TeamResult()`/`BracketMatch.TeamResult()`), standings accrual (`accrueTeamSubResults`, `engine/scoring.go`), and the Excel export (`internal/export/builder.go`); the JS mirror is `web-mobile/js/team_default_credit.jsx`, consulted only when the server's own `teamResult` is absent. A score-sheet correction (`incoming.Decision` empty or `hikiwake`) over a stored default-win ruling keeps it: `engine.KeepsWithdrawalRuling(storedStatus, storedDecision, incoming)` was widened from the old withdrawal-only check (`domain.IsWithdrawalDecisionStr`) to `domain.IsDefaultWinDecisionStr`, so a stored fusensho survives a correction exactly as a kiken/fusenpai does.
- **Operator match labels** (`internal/engine/match_label.go`): `OperatorMatchLabel(comp, bracket, matchID)` is the ONE Go owner of how a match is named back to the operator -- in refusal messages, the `court_busy`/`downstream_knockout_running` `label` fields, and `reasonHuman` sentences. A pool/league row reads e.g. `"Pool A · Match 1"` (`"League table · Match N"` for a league; the middle dot is the literal separator, `supplementaryOrNumberedLabel`); a knockout row (`MatchLabel`) reads e.g. `"Match 2 (Final)"`, `"knockout Match N"` (no round recorded), or `"the 3rd-place match"` (bronze). Pinned against the JS side by the shared golden fixture `internal/engine/testdata/match_labels.json`: `TestOperatorMatchLabel_GoldenTable` (Go) and `web-mobile/js/__tests__/match_labels_golden.test.jsx` (JS, `scoreRowMatchLabel`/`matchLabel` from `pool_ids.jsx`/`write_result.jsx`) load the SAME file.
- **Team Match Winning Criteria**: An encounter between two teams is decided by:
    1. Highest number of individual winners (Victories).
    2. Highest number of points scored.
    3. If both are equal, it's a draw (Tie) in pools, or requires a play-off (Encho) in elimination matches.
- **Tie-marking Rule**: A match (individual or sub-match) is a tie when the operator enters **'X'** (or 'x') in the "vs" column or when both sides finish with the same total score (equal character-count after stripping spaces/zeros/dashes). For auto-detection, at least one score cell in that row must be non-empty. A team match is automatically a draw (T=1) when both IV and PW totals are equal.
- **Match Colors**: White (Shiro) is always the left column and Red (Aka) is always the right column (this is fixed and not configurable). In pool matches the first-listed player (SideA) is Red; in elimination matches the upper-bracket player (`node.Left`) is Red. **A TINTED surface does not carry a SHIRO/AKA badge as well** (operator ruling 2026-09-20, bc-sccl, which SUPERSEDES bc-dnst's "named once in text, by the header badge"): where a side has a background tint, the tint plus Shiro's 45° hatch carry it, and the badge is redundant. Every side badge in the app went with that ruling: the score editors' header pill (`.sb-side__badge`), the engi card's (`.engi-side__badge`), the scores list and court console's (`.se-color-badge`) and the compact schedule's 14×14 `A`/`S` squares (`.tw-match__badge`). Bout rows and foul counters were already tint-only, so do not re-add per-bout SHIRO/AKA chips or "SHIRO Fouls" prefixes either. A tinted surface still names the side in TEXT for a screen reader — that is the one thing that must never be dropped with a badge (DESIGN.md §4: colour is never the only signal). - **Store Transactions** (`internal/state/transactions.go`): `Store.WithTransaction(compID, fn)` holds the per-comp lock once across multiple load/save operations. Use the `StoreTx` handle inside `fn`. Do NOT call public Store methods (they would deadlock the non-reentrant mutex).
- **Cache invalidation: never key a cache on mtime alone** (`internal/state/store.go`): filesystem mtimes come from the kernel coarse clock (~1ms granularity), so two writes inside one tick are indistinguishable and an mtime-keyed cache serves pre-write data (mp-n6ke: stale standings vs fresh matches injected a phantom tiebreaker bout and stalled bracket advancement; mp-p7n was the same class). Each `fileCache` therefore carries a monotonic `version` counter, exposed as `Store.FileVersion(compID, filename)`; `engine.CalculatePoolStandings` requires BOTH version and mtime to match (the counter catches same-millisecond in-process writes, mtime still catches out-of-process edits). **If you add a writer for a file some cache derives from, call `s.bumpFileVersion` AFTER the bytes land**: an extra bump only costs a recompute, a missed bump serves stale data, and bumping before the write lets a reader stamp OLD bytes with the NEW token. Existing bumps sit at the chokepoints every writer funnels through (`savePoolMatchesLocked`, `saveOverridesLocked`) plus draw deletion and transaction abort. Two further rules follow from the counter being the cache key: **every read path must validate it, not just the fast path** (the `CalculatePoolStandings` single-flight loser returned the winner's entry unvalidated, and the winner stamps *pre-compute* tokens, so it could predate the loser's own write), and **the counter must stay monotonic for the life of the process, including across a competition being deleted and recreated** (IDs are name slugs, so `DeleteCompetition` calls `discardCompCacheBodies` to clear the cached bodies while leaving the counters climbing, rather than `compCache.Delete`, which reset them to 0 and let a recreated competition match its predecessor's stale entry). Prefer a deterministic counter over a sleep, which only hides the race.
- **Only `saveCompetitionChangedLocked` may create the competition directory** (`internal/state/overrides.go`, `competitor_status.go`, `team_lineup.go`): `saveOverridesLocked`, `saveCompetitorStatusLocked` and `saveTeamLineupsLocked` each used to `os.MkdirAll` before writing, so a write landing after `DeleteCompetition` rebuilt `competitions/<id>/` around a lone `overrides.json` / `competitor-status.yaml` / `lineups.yaml`. That orphan survives the delete (`ListCompetitions` returns every directory under `competitions/`) and, because IDs are name slugs, a same-named recreation adopts the dead competition's data. **Locking cannot fix this**: the write does not have to interleave with the delete to resurrect the directory, only to run after it (the two status/lineup writers take the very lock `DeleteCompetition` holds, so they cannot interleave at all, and still resurrected it). `atomicWriteFile` opens its temp with `O_CREATE` but never creates the parent, so once the `MkdirAll` is gone a write to a deleted competition correctly fails with ENOENT. Creating the directory is competition *creation*'s job and `saveCompetitionChangedLocked` is the sole legitimate `MkdirAll` site (plus `Store.init` for the root/WAL folders); do not strip that one, and do not reintroduce the pattern in a new per-competition writer. The interleaving half is closed separately: `overrides.json` is the one competition file whose writers serialize on the store-wide `s.mu` rather than the per-competition lock, so `DeleteCompetition` takes **both**, in the order compLock then `s.mu` (`s.mu` is a sink: nothing holding it acquires a comp lock, so the edge cannot close a cycle). **Do not "tidy" this by moving overrides onto the per-competition lock**: `computeStandingsFrom` runs inside `WithTransaction`, which already holds that lock, and reads overrides via `e.store.LoadOverrides`, so it would self-deadlock the live scoring path on a non-reentrant mutex.

### Match results and marks

The rules below were settled by operator rulings and are pinned by tests. Each has one owner in code; do not restate any of them at a call site.

#### Decision types

`internal/domain/decision.go` defines the canonical wire values: `""` (none), `"fought"`, `"hikiwake"` (draw), `"kiken"` (legacy withdrawal, maps to kiken-voluntary on YAML load), `"kiken-voluntary"` (FIK Art. 31, permanent), `"kiken-injury"` (FIK Art. 30, reinstateable), `"fusenpai"` (no-show), `"fusensho"` (a per-bout default win within a team encounter, AND the match-level default win an operator records via `POST /decision` to close a barred competitor's remaining scheduled match -- `domain.IsWithdrawalDecisionStr` deliberately excludes it, since it is a default win awarded on someone ELSE's withdrawal rather than a withdrawal of the match it is recorded on; `domain.IsDefaultWinDecisionStr` includes it. `decisionBy` on either usage names the side that withdrew, did not appear, or is barred -- the LOSING side -- never the side the decision favours; the write then makes the OTHER side the winner (`scoring_tx.go`)), `"daihyosen"` (rep bout), `"kachinuki-exhaustion"`, and `"ippon-shobu"`. The last one is accepted by `Decision.Valid` but has no writer in the tree: supplementary pool tie-break bouts are identified by their match id (`Pool X-TB-N`, see `engine/tiebreaker.go`), not by this decision. Use `domain.IsKikenDecision(d)` / `domain.IsKikenDecisionStr(s)` to check any kiken variant. Legacy YAML `decision: true` migrates to `"hikiwake"`, `false` to `"fought"`, `"kiken"` to `"kiken-voluntary"` (`Decision.UnmarshalYAML`).

#### The middle is a closed set

Visual marks follow the score sheet's layout, split into two kinds. MIDDLE marks occupy the centre "vs" cell (the score-string centre): exactly one of `X` (tie), `(E)` (overtime, always bare: `periodCount` is recorded but never displayed), `(DH)` (rep bout). They are mutually exclusive by rule: a match that went to encho cannot end tied, so X beats (E); a daihyosen is one-point sudden death, so DH bouts have no encho. RESULT marks ride beside the competitor they name: `Ht` (hantei winner), `Kiken` (withdrawer), `Fus.` (no-show, and also the winner of a fusensho match-level default win; `sideMarks` in bracket.jsx and `SideMarks` in internal/export/suffix.go agree on this, so a fusensho match reads identically on every surface and in the exported workbook).

Web score strings read `[left cell] [middle] [right cell]` with `vs` as the plain middle and `–` (or empty) meaning no points. Never digits: ippon renders as waza letters only, e.g. `M vs –`, `M (E) K`, `M Ht (E) K`. The dash is a CELL value only. The middle never shows a dash, so unplayed and pending match rows read `vs` too.

A default win (kiken/fusenpai/fusensho) awards the WINNER its points as maru, one `○` per point per FIK Regulations Art. 32 and the Score Board appendix p.15 (`["○","○"]` in regulation, one `○` in encho). This is the rulebook's score-board marking, not a house style; it lives in `domain.DefaultWinIppons`. Per the same Article ("Any point scored by the shiai-funo-sha shall remain valid") the LOSER is NOT zeroed: `preserveLoserScore` (engine/scoring.go, called by the one `RecordDecision` body) keeps the withdrawing side's already-struck ippons and preserves the encounter's prior `SubResults`, so a team withdrawal never wipes the sub-bouts already fought (they keep counting in IV/PW standings). It is guarded on a side-matching prior so a drifted prior can't mis-attribute points. `state.EnchoMetadata.On` and `enchoOn` (bracket.jsx) are the single "did this happen in encho" predicate (non-nil AND positive periodCount), shared by the (E) label, the maru count, and decision validation, so a degenerate `{periodCount: 0}` block can never split the surfaces. Display fallbacks (`DefaultWinMaruAB` in suffix.go, `formatIpponsScore`, the scoreboard win slots) render `○○` for winners whose recorded cells are empty (byes, pre-fill/legacy data).

The middle-value rule lives in ONE place, `boutMiddle` (bracket.jsx), which returns exactly `vs`/`X`/`(E)`/`(DH)`; `matchMiddleMark` (the chip variant), `matchStateCell`, and the scoreboard separators all derive from it. (`formatIpponsScore` composes the same `isDrawResult`/`middleMark` primitives directly rather than calling `boutMiddle`: its empty-middle-vs-`""` distinction is load-bearing for callers' fallbacks.)

**The middle is a CLOSED SET and there must NEVER be a centre `Ht`** (operator ruling, absolute). Those four values are the only things that may ever occupy the centre, in either language and on every surface. `Ht`/`Kiken`/`Fus.` name ONE competitor, so they ride in that competitor's cell and can never take the shared cell. This is enforced, not just documented: `web-mobile/js/__tests__/middle_closed_set.test.jsx` and `internal/export/middle_closed_set_test.go` sweep every decision × encho × score (including `decidedByHantei`) and fail on a fifth value OR a side mark in the middle, both mutation-verified. The ruling settles what used to look like an inconsistency: the `loose` path (both slots full) renders `Ht` INBOARD of that side's slots, inside `.msb-slots`, never in `.msb-vs`, so it complies; and an unattributable winner correctly gets NO mark, because "no mark" is the only alternative to a forbidden centre mark. Adding a fifth middle value, or a centre fallback for an unattributable result, is out of bounds. Do not propose either.

A surface that renders the FIK row must show the mark ONLY in that row's centre (operator ruling: the TV header and lobby chips were duplicates and were removed). A surface that renders NO such row (`MatchCard`'s meta strip, the OBS lower-third) keeps its chip, because there the chip IS the one home.

#### Where a mark lands

**A middle mark belongs ONLY in the middle of an individual fight** (operator ruling), and a team bout's score is displayed the same way in every format, kachinuki or not: cells either side of a centre, on that bout's row. This governs the WHOLE set (`X`, `(E)`, `(DH)`), i.e. ANY mutating middle, not just one of them.

- In an INDIVIDUAL competition the match IS the fight, so its own row centre carries the mark (`IndividualScore`, whose synthesised sub threads the match-level `decision`/`encho`/`score`). A tied individual match fought on in overtime shows `(E)` there, e.g. `[M][ ] (E) [K][M]`.
- **Encho is NOT team- or kachinuki-specific.** Any tied match may be fought on, in either competition type.
- In a TEAM match the encounter is not itself a fight, so each mark lands on the row of the bout it describes. **Kachinuki** fights on in overtime on the SAME numbered bout, so `(E)` lands in that bout's middle. **Regular (fixed-order)** teams settle a tie with a daihyosen, which is an EXTRA appended bout (position -1, knockout only: `AddDaihyosen` returns `ErrPoolMatch`, a pool tie is simply a draw), so `(DH)` lands in the middle of THAT extra row. A drawn bout carries `X` in its own middle under either format.
- `TeamScoreboard` gates the extra DH row on `showDH && tied`, and `showDH` additionally requires every regular bout to be FINISHED. That is correct, since a daihyosen only follows a completed tied encounter, so a fixture that appends one while a numbered bout is still unscored will (rightly) not render it.
- `TeamScoreboard`'s §277 summary row is an AGGREGATE (IV/PW), not a fight, so its centre is a deliberately empty spacer and NO mark ever goes in it. That holds even when the aggregate itself is tied: a team encounter drawn on equal IV and PW displays no `X` at the encounter level, and if no individual bout was drawn then no `X` appears at all. This is correct because the mark describes a fight, not a standings figure (the draw is carried by the T column and by each drawn bout's own centre). That row RENDERS only on `variant="card"`: on the TV board (`variant="tv"`) it is suppressed and the headline team-name row in display_scoreboard.jsx carries the pairing plus each side's IV/PW instead (operator decision 2026-09-19, bc-lbty -- the team name was being shown twice, and the summary row was the redundant copy). Both surfaces derive those four figures from the one exported `teamIVPWFrom` (match_scoreboard.jsx), so the headline and the row can never disagree about which source won. Do NOT suppress it on the card: viewer_match.jsx has no separate name row, so there that row is the only thing showing the pairing. Two rejected fixes, both reverted, both verified in the browser: threading the match-level mark into the summary spacer (a review round claimed removing the TV header chip left it homeless) put a second `(E)` directly above the bout's own; and placing the encounter tie there was proposed and refused for the same reason. #### Hantei is recorded as an ippon

The centre NEVER carries `Ht`: a hantei always names a winner and is decided from a TIED scoreline. `validation.go` requires a winner plus `domain.HanteiTiedScoreline`, the one owner of the tie test, shared with the engine's `preserveSubHantei` exactly as `IsHanteiCompatibleDecision` is, and counted through `domain.CountScoringIppons` so an "•"/empty cell cannot read tied to one enforcer and untied to the other; `hanteiTied` mirrors it in JS. Encho is NOT a precondition. In a TEAM match `validateSubBout` additionally restricts hantei to the daihyosen bout, position -1; a tied numbered bout is simply a hikiwake.

`Ht` IS recorded as an ippon-slice entry (operator ruling 2026-08-21: "Ht should be recorded as just another ippon"). The mark in the WINNER's `IpponsA`/`IpponsB` is the record itself, exactly as the FIK sheet writes it: non-scoring (`IsScoringIppon` drops it, so points/PW/standings/the tie test never count it; `realIppons` is the JS mirror) but first-class in the data. Pool CSV cells and bracket.json ippon arrays hold it verbatim (`domain.ParseScore` still consumes `Ht` as its ONE two-rune token by the no-lone-`t` argument, but only inside the legacy read fold of pre-array bracket files), and the wire carries no `decidedByHantei` field in either direction. The SPA DERIVES that property in `normalizeMatch` for its read sites and `toBackendMatchResult` converts the editors' armed boolean into mark placement (`placeHt`), while the server folds legacy flags into the mark at every read boundary (`state/legacy_hantei.go`; the three `DecidedByHantei` struct fields are LEGACY READ-ONLY, never written).

Placement follows the point rule: the mark fills the winner's next FREE slot in outside-to-inside order (0-0 → the outer slot, 1-1 → the inner one, giving `[K][ ] vs [Ht][M]`), which in array terms is `domain.AppendHantei` (fill a placeholder slot, else append), so the mark's array position IS its slot. Through normal play sanbon-shobu ends at 2, so 0-0 and 1-1 are the only reachable scores and a free slot always exists. 2-2 is IMPOSSIBLE under the rules and closed on both sides: the editors' ippon entry stops each side at 2, and `validateIppons` caps each side at 2 AND rejects 2-2 outright on every sub-bout and on the bulk path. The `loose` return exists solely for hand-edited files. No point is ever overwritten, and each consumer then applies ITS OWN policy: the read-only scoreboard renders the mark beside the slots; both editors drop it because each has a second always-mounted channel for the verdict (see result_slot.jsx's header for the enumeration).

**Which completed bout is the most recent RESULT has ONE owner too**, `web-mobile/js/result_recency.jsx` (`resultRecencyDesc`, a leaf with no imports). Two surfaces answer that question and used to answer it differently (mp-jnvl): the court console's context strip ("the bout just played") and the public viewer's Recent results both read SCHEDULE order as recency, so a court running out of schedule order had them name different bouts. Recency is the `modifiedAt` write stamp, which is the time of the last WRITE and not of the result: STARTING a bout is a stamped write, and an unstamped write inherits the stored stamp, so a started-then-withdrawn bout keeps its start stamp. A bout is unstamped only when nothing ever stamped it (a file predating the field, or a match closed while still `scheduled`), and those fall back to scheduled time, so an all-unstamped list keeps exactly the ordering both surfaces had before. The console applies it in ONE place, `partitionShiaijoMatches`, which orders the COMPLETED group by play time (oldest first) while running and scheduled keep schedule order. That makes the newest result the TAIL, so the strip's anchor and the Completed preview are both plain tails: the preview is a contiguous window and "Show all" EXTENDS the list upward instead of inserting rows into the middle of it (operator ruling 2026-09-19; the earlier top-N-by-recency pick left visible holes). An all-unstamped list falls back to scheduled time and reads exactly as it did before the stamp existed.

The strip's heading names what it is showing whenever that is not the live bout: "Up next" before the court's first bout (the highlight there means "play this next"), "Just played" when it fell back to the last result, "Correcting" when the operator opened that result to fix it. With no such qualifier the lead names the panel's CONTENT - "Standings" for a pool, "Bracket" for a knockout fragment. The word "Context" was removed as meaningless (operator ruling 2026-09-19).

The slot rule has ONE owner, `resultSlot` in web-mobile/js/result_slot.jsx (a small leaf; the dependency reasoning is stated once in that file's header). Its three consumers are `resultCells` in match_scoreboard.jsx, `hanteiSlot`/`ptSlots` in admin_scoring_team.jsx, and the individual editor's slot grid in admin_scoring_individual.jsx (display-only `Ht` chip via `hanteiWinnerKey`). Change the contract and ALL THREE surfaces must be re-checked.

Score strings TRAIL loose marks as an unattributable-winner degradation, but the scoreboard has no centre-`Ht` equivalent: an unattributable winner gets no mark rather than one in the shared centre cell. ACCEPTED no-mark classes (all drifted/legacy data; the centre is forbidden by the operator ruling and no side is attributable): (i) same-name-no-id pairs; (ii) rename-drifted winner names (note the old centre fallback DID fire for these whenever the middle was empty, which a no-encho hantei makes normal, so this IS a regression there, accepted); (iii) winner-less legacy `decidedByHantei` rows (previously centre `Ht`); (iv) untied legacy `decidedByHantei` rows written before the tied-scoreline validation existed (letters still convey the winner; the judges'-decision marker is dropped).

Two related deliberate divergences. Score strings (`sideMarks`) and the Excel export (`SideMarks`) still mark `Ht` UNCONDITIONALLY: the mirrored pair stays consistent with itself and gains no tie gate. And a winner naming BOTH sides resolves defensively to AKA everywhere in JS (`subWinnerSides`, aka-first) to match Go's `isWinForSide`/`SideMarksLR` order, so rows, summaries, standings and the export agree on the same arbitrary side. That aka-first rule is scoped to the MATCH level, where a team name is unique by rule and a winner naming both sides is therefore drifted or hand-edited data. It does NOT hold for a SUB-BOUT, where two opposing fighters may legally share a display name and the same order would be a coin flip on ordinary valid data: such a bout is attributed by the row's MEMBER IDS and counts for NEITHER side when no id can decide. **`domain.SubBoutAttribution` owns that rule** and its doc comment is the statement of it; every consumer builds its attribution there, and the JS mirror is `subBoutAttribution` (result_slot.jsx). Do not re-add a name tier that runs when `SideA == SideB`, and do not restate the mechanism here: an earlier copy of it named a function by its unexported name and went stale one commit after that function was exported. Stored sub names stay frozen after a rename (nothing rewrites `SubMatchResult.SideA`/`SideB` on disk or on the wire): every DISPLAY instead resolves the CURRENT name by member id at render time, through `resolveBoutSideDisplayName` (web-mobile/js/lineup_resolver.jsx) and its Go twin `resolveKachinukiDisplayName` (internal/engine/kachinuki_export.go) for the Excel export (bc-dnst), so a rename shows on bouts already fought, on every surface, without touching the stored record. Mirrored helpers: `middleMark`/`sideMarks` (bracket.jsx) ↔ `MiddleMark`/`SideMarks` (internal/export/suffix.go); `enchoLabel` pinned in both languages via `internal/export/testdata/encho_labels.json`.

#### Writing `SubResults`

The verdict travels IN the ippons, atomically with the scoreline it rests on: verdict-silence and scoreline-silence are the same thing. `HanteiDecided()` (both result types) reads the mark; `SubMatchResult.DecidedByHantei` is a legacy read-only field that request/load normalization folds away. Never set it.

Every forward replacement of a `SubResults` slice must still call `engine.preserveSubHantei(stored, incoming)` first. It carries a stored daihyosen outcome (winner plus the marked scoreline) onto a scoreline-silent row: the copied prior ippons carry the verdict themselves and no flag is raised. It is deliberately narrow in two directions: it PATCHES an existing position -1 row but never RE-APPENDS a dropped one (`DELETE /daihyosen` removes that row on purpose through this same path), and it refuses any `Decision` outside validateSubBout's allow-list because it runs AFTER validation and its output is never re-checked.

The bracket writes call it via `preserveDaihyosenOutcome` inside **`applyBracketMatchResult`**, the one per-match bracket write shared by `recordBracketMatchResult` and the bronze (3rd-place) fallback. `recordBracketMatchResult` is one body taking an `h state.StoreTx` handle, which `*state.Store` satisfies, so the same `UpdateBracket` dispatch around the shared `applyBracketResultIn` serves the tx and non-tx doors. Do not split it into per-door copies: hand-copied bodies here drifted (the bronze copy missed the LWW guard the round copies had).

Pool writes get it from **`applyPoolWrite` (engine/scoring.go), the single owner of what a stored pool match contributes to an incoming one**. It replaced a block hand-copied into each write closure, after those copies drifted twice in the direction that hurts: the preserve reached three of the writers and missed the live `/score` path, and the `CorrectionReason` inherit reached only the Tx twin, so a team quick-score after a kachinuki reopen blanked the operator's audit justification. It also performs the whole-struct `*stored = *result` overwrite itself, so the overwrite is unreachable without the merge; a new field that must survive it goes there and nowhere else. Note the scope: that covers ENGINE-side preservation, while server-owned flags a client must not be able to clear (`ReopenPending`) are re-stamped at the HTTP boundary in `handlers_match.go` instead.

#### Write policy and the rollback snapshot

Both primitives take a `matchWritePolicy`: `matchWriteForward` for a client payload (inherit omitted context, restore a verdict-silent daihyosen), `matchWriteRestore` for the K3 rollback replaying a trusted snapshot (inherit NOTHING: a nil or empty field means "this was empty", and a side mismatch is not a client error to reject).

**That policy makes the snapshot PRODUCER load-bearing.** Because an omitted field is read as an instruction to clear, a partial projection is silent data loss, not a missed optimisation. `bracketMatchAsResult` (engine/bracket_result.go) once omitted the score: a bracket match THEN persisted each side as one rendered string while `MatchResult` carries ippon arrays, so a rollback wrote a blank over a real scoreline. bc-bmsc removed that last dual representation. `BracketMatch` now stores the same ippon arrays + hansoku counts as every other result; its `ScoreA`/`ScoreB` strings are LEGACY READ-ONLY (folded into the arrays and cleared by `BracketMatch.NormalizeLegacy`, `state/legacy_hantei.go`, which folds the score strings FIRST and the hantei flag second; arrays win when a hand-edited file carries both; never written, omitempty so the wire never carries them). The projection is a direct field copy, and it carries `ResultSource`/`CorrectionReason` so the restore both puts back the note the match held and clears one the rejected write added (matching `applyPoolWrite`'s whole-struct overwrite, which always did).

The ONE field it does NOT project is `ModifiedAt`, and the reason is narrower than it looks. `applyMatchWrite` returns true for `matchWriteRestore` BEFORE reading any stamp, so a restore can never lose the LWW comparison and the omission cannot be what makes the rollback apply. What it decides is the stamp LEFT behind by the whole-struct overwrite: omitting it zeroes the stored stamp, so the next write takes `ApplyByTimestamp`'s unstamped bypass rather than being fenced against the restored result's real time. The pool snapshot differs (`lookupExistingResult` copies the stored `MatchResult`, restoring the true prior stamp), so this is a branch asymmetry, not a property of restore; completing the projection is a behavioural change, not a tidy-up. All three are pinned by mutation in `TestBracketRollbackRestoresTheScore`. `domain.FormatScore` was deleted with the strings; `domain.ParseScore` remains solely as the legacy fold's decoder, pinned parse-direction-only by `TestParseScore_PinnedLegacyBytes` because old files hold those bytes forever.

**The policy must reach BOTH branches.** A match id resolves to a pool or a bracket match at run time and the caller cannot know which, so `writeToPoolOrBracket` threads it through the `errMatchNotFound` fall-through as well. `writeToPoolOrBracket` is ONE body: the store handle `h state.StoreTx` (which `*state.Store` satisfies) is how a caller says whether the per-comp lock is already held, and the non-tx entry points `RecordMatchResult`/`RecordMatchResultWithIneligibility` are `WithTransaction` shims. Never compensate for one branch in a caller (e.g. by pre-converting the snapshot's nils into explicit clears): that makes one function enumerate another's nil-preserve fields, and the next such field silently breaks rollback. The policy differences are pinned by mutation in `pool_write_merge_test.go`, `sub_hantei_preserve_test.go` (`TestBracketRollbackDoesNotReapplyTheWrite`) and the pair `TestRollback_BracketSubResults_Cleared`/`_ClearedTx`, which pins both entry points into the one rollback body.

#### Editors adopt the server's verdict

**A match has ONE result and every surface asking for it shows the same one** (operator ruling), and the score editors are such surfaces. While one is open, the viewer card, the bracket, the TV board, the lobby and the export are all already showing whatever the server holds, so an editor showing something else is a divergence whatever its reason. Both editors therefore ADOPT a verdict recorded on another device: `useEffect` keyed on the VALUE (`hanteiRecorded` in admin_scoring_individual.jsx; `daihyosenHanteiRecorded` + `recordedDaihyosenSide` in admin_scoring_team.jsx), never on the `m`/`match` object, which SSE re-creates on every broadcast and which would fight the operator's every tap. Keying on the primitive means a local arm/pick/cancel stands (it does not move the server value) while a real server change is followed in either direction, and only the verdict is touched, so an edit in progress survives. `isDirty` compares the verdict against the SERVER's value, not a mount-time snapshot, so adopting is not an "unsaved change" and does not fire the discard prompt on an untouched editor.

Because an editor can now never rule on something it did not display, an explicit `false` is always the operator's decision and always reaches the wire as what it now IS, a markless scoreline: `daihyosenEnchoFields` still states the local boolean unconditionally, and the serializer chokepoint converts it (true → mark placed on the winner's side, false → arrays stay markless; `realIppons` strips echoed marks first so placement never doubles). Two earlier designs are recorded in `web-mobile/js/__tests__/render/individual_editor_live_hantei.render.test.jsx` and must not be reintroduced: recomputing the baseline from the live prop while freezing the local armed state (which erased the verdict on the next write), and freezing at mount with a `hanteiKnown` silence guard (which stopped the erase by accepting the divergence; the guard was deleted with it).

#### Silence on the wire

Silence still means "no opinion" on the wire. It is now OMITTED IPPONS (nil, not `[]`) rather than an omitted flag, and the distinction is load-bearing: an explicit `[]` is the operator saying ZERO (a 0-0 withdrawal), a missing key is a writer with nothing to say, whose stored verdict `preserveSubHantei` restores. The team editor IS one of those writers: `buildPatch` (admin_scoring_team.jsx) has a `daihyosenSilent` branch that OMITS the daihyosen row's ippon arrays when the operator has not touched that row this session AND nothing about it is known locally. That branch is the only reason the nil case is reachable from a real client at all, so do NOT "fix" it into an unconditional write. Any touch, or any locally-known verdict or scoreline, falls through to the explicit-array path, so a deliberate withdrawal still withdraws. Scope note: the restore protects a stored HANTEI verdict only; `preserveSubHantei` bails when the stored row carries no mark, so a rep bout decided by a strike is not restored by this mechanism.

Accepted compat gap (documented in `legacy_hantei.go`): a pre-ruling client re-scoring a hantei match with markless ippons inside the offline queue's 12h replay window (`QUEUE_TTL_MS`, api_client.jsx) clears the verdict, because a markless scoreline is now the writer's word.

#### A write answers for what it introduces, not for what it inherited

The engine-side contradiction guard is `stripInvalidHantei` (replaced `preserveMatchHantei`): forward writes on both branches strip a mark whose preconditions fail (`hanteiStillHolds`) or that sits on a non-winner's side, and LOG the drop (it discards an operator-visible verdict on an otherwise successful write). It strips rather than rejecting BECAUSE the mark is one the write INHERITED: the reachable producer is `handlers_daihyosen.go`'s add path, which copies the stored match wholesale (`u := *match`) and moves Status to running, so a valid stored verdict fails `hanteiStillHolds` on status alone and a 400 would blame the operator for state already on disk (same rule as `applyHansokuIppons`' fold scoping; pinned by `TestStripInvalidHantei_InheritedMarkIsStrippedNotRejected`). A CLIENT-sent bad mark is rejected instead, at the boundary that can still tell whose fault it is (`mobileapp.validateHanteiMarkPlacement`, which the handler's `backfillMatchIdentityForHantei` feeds the stored sides/ids so it attributes by the same triple the engine will). The decision twins are NOT a producer: `preserveLoserScore` filters through `struckIppons` and `domain.IsScoringIppon` drops the mark, so a kiken over a stored hantei arrives with the mark already gone (`TestPreserveLoserScoreDropsTheHanteiMark`).

`applyHansokuIppons` folds each row and immediately judges what THAT fold rewrote. It is count-compared: a row whose award is already reflected is left untouched, slots and all, and reports NO change; a shortfall is awarded through `domain.AppendIppon`, filling a free `•` slot before growing the slice, so a wire-legal placeholder row stays wire-legal after the award; a surplus H over the count is the operator's own strike (the editors keep hansoku as the OUTSTANDING count and land the H themselves, `applyFoulIncrement`) and is NEVER removed. It applies both checks, hantei-untied and the best-of-3 overflow, at match level and sub level through the one shared `checkFoldedRow`. The check lives inside the producer rather than in a separate function the call sites chain by hand, so a new write path cannot fold without checking. Unscoped, it rejected rows the decision twins had just inherited wholesale via `preserveLoserScore`, so an over-cap row already on disk 400'd an operator's kiken that carried no sub rows at all, with no endpoint able to repair it; unmirrored at match level, the identical fold wedged a match on disk instead. This narrows the engine guard on purpose: a payload that ALREADY carries a bad row is damage `mobileapp.validateIppons` can see and rejects at both levels, so only the post-award state needs checking here. `applyKachinukiMerge` running AFTER the check is the same rule; when you add a guard downstream of an inherit, ask which actor it will blame.

### Write refusal and the clock frame (bc-lww1 / bc-cse)

A match write can be REFUSED by the server, and a refusal is always **HTTP 200** carrying `{"applied": false, "reason": ...}`, never a 4xx/5xx, because the SPA's offline write queue retries 5xx forever (the mp-q8c6 poisoned-queue pattern) and a refused write can never win a retry. Two reasons exist:

- `superseded`: the timestamp last-write-wins guard dropped it; a NEWER result is already stored. The operator must **not** blindly re-enter: a fresh entry is stamped now and would overwrite the result that won.
- `clock_skew`: the write's `modifiedAt` was more than 5s in the server's future (`modifiedAtRefuseSkewMs`, handlers_match.go), so it is provably wrong. Nothing was stored, the client resyncs its `/api/time` offset, and re-entering IS the remedy. The copy for the two cases is deliberately opposite; do not merge them.

**Which endpoints compete on timestamps**: `/score`, `/override-winner` and, since mp-jnvl, `/decision` each carry the client's stamp, so any of them can be refused for either reason. Quick-score and the two daihyosen paths still build their result with NO stamp and take `ApplyByTimestamp`'s unstamped bypass, so they always apply; they map the refusal shape defensively anyway. A decision is stamped because it is the write that CLOSES a match, and a match closed while still `scheduled` (the withdrawal panel's default win) has no earlier write to inherit a stamp from, so the result carried no time at all and nothing downstream could order it. The stamp reaches the engine through a VARIADIC parameter on `RecordDecision`/`RecordDecisionTx`: the engine-internal caller and the suite's decision tests omit it, and the handler is the one caller that must always pass it.

**`web-mobile/js/write_result.jsx` owns that whole rule**: `writeDidNotLand` (queued OR refused), `writeWasSuperseded`, `writeWasRefusedForClock`, `notLandedBanner(res)`, and every operator-facing string. It is a leaf with no imports, and **every consumer ES-imports it directly**; there are no `window` mirrors and re-adding one fails `make js/check-imports` (see `web-mobile/check-write-result.mjs`, which also forbids hand-rolled `.applied` comparisons outside the owner and `api_client.jsx`; its walk, comment stripper and line scan are `web-mobile/check-helpers.mjs`, shared with the competitor-number gate below, and its `FORBIDDEN` rules are exported so `rule_gates.test.jsx` can pin them). This exists because the question was originally spelled `res.queued` inline at ten call sites, and when a second not-landed shape appeared the conversion reached five of them.

Two distinctions that look like details and are not:

- **`writeDidNotLand` vs `writeWasSuperseded`.** Both mean "not stored", but a QUEUED write lands on reconnect, so an offline court must still advance its local bracket; a REFUSED one never lands, so anything derived from it is wrong. Gate optimistic UI on the stronger predicate and general "did it save" checks on the broader one.
- **Client clock stamps are server-relative**, learned from `GET /api/time` (retried until it first succeeds, relearned on SSE connect, on `'online'`, on any refusal, and when the 15s heartbeat's `nowMs` diverges by more than 3s). The heartbeat value is a divergence TRIPWIRE only, never an offset source: a one-way push has no RTT to correct, so a late frame would drag the device's clock frame backwards. Queued payloads are stamped at ENQUEUE and replay verbatim; a replay refused for skew is re-stamped once, by `_restampFor`, which computes TWO reconstructions and keeps the OLDER: `enqueuedAt + fresh offset` (wrong if the OS stepped the wall clock mid-outage) and `serverNow - monotonic age` (wrong if `performance.now()` froze during suspend). Taking the older is a safety rule, not a tie-break: an over-old stamp only makes this write lose a comparison it might have won, which is recoverable and announced, while an over-new one is the silent overwrite bc-lww1 exists to stop. The monotonic anchor is stamped at the one enqueue chokepoint and **stripped on persist**: it is measured from a per-document time origin, so a rehydrated reading (or one written by another tab) subtracts two different zeros and yields an age unbounded in BOTH directions, which is exactly what `min()` cannot defend against. A rehydrated entry therefore falls back to wall-clock only, so a clock step spanning a reload still ends in a drop. Retried exactly once either way.

**A dropped write leaves NO FOOTPRINT, on either branch.** `UpdatePoolMatchByID`'s mutate returns an `error` and the store skips the save when it does, the contract `UpdateBracket` has always had, so `applyPoolWrite`'s drop verdict aborts rather than re-serializing the untouched row and bumping the standings-cache version. Two rules come with it. The abort is reported through the ERROR and NEVER through `found`: `found` stays true because the match WAS there, and signalling `(false, nil)` would make `writeToPoolOrBracket` read a rejected pool write as "not a pool match" and go hunting for it in the bracket. And BOTH `storeTx` branches must honour it, the WAL-staged one included, or a drop leaves no trace outside a transaction and a WAL entry inside one. Pinned across all six cells of `superseded_matrix_test.go`, which asserts the file bytes AND `Store.FileVersion` are unchanged after a drop; reverting the abort reddens exactly the two pool cells.

Engine side: `state.IsTransactional(h)` lets a caller whose correctness depends on a live transaction check what handle it was given; `recordIneligibilityFromDecision`'s K2 check-and-set logs if handed the bare store, which is what pins the entry-point `WithTransaction` shims. `applyMatchWrite` is pure timestamp LWW for every write **including corrections** (the old `correctionReason` exemption was a workaround for refusals being silent, and it let a replayed offline correction overwrite newer results). The remaining unstamped-bypass overwrite is logged rather than silent.

### The competitor-number search rule (bc-nsrc)

A picker that FILTERS A LIST by what the reader typed asks ONE rule for the competitor number, `matchesCompetitorNumber` in `web-mobile/js/competitor_search.jsx` (composed into `competitorMatchesQuery` for a record and `matchMentions` for a match), and never re-derives it (operator rulings 2026-09-21 and 2026-09-23). Two arms over the record's own competition prefix: the query EQUALS the whole number, or the query BEGINS the competition's `numberPrefix`. So "k" lists every K draw (K and an auto-minted K02 alike), "k02" lists the K02 draw, "k1" is K1 alone (not K12), and bare digits find nobody. The prefix has to be a FIELD on the record, because the number string cannot say where its prefix ends ("K021" is K02's first competitor or K's twenty-first): `buildRoster` (`viewer_watchlist_core.jsx`) stamps `numberPrefix` on every roster record and `buildPlayerMap` (`api_serializers.jsx`) on every resolved match side, `prefixOf` (`competitor_identity.jsx`, beside `numberOf`, trimmed as Go's `EffectiveNumberPrefix` trims) reads it back, and a competitor only carries a number when their competition carries a prefix (`handlers_viewer.go` `numberingApplies`), so there is no fallback arm. Names and dojos stay substring matches. Two admin surfaces are ruled OUT and carried as data in the gate: `admin_participants.jsx` does not search numbers, and `admin_registration_desk.jsx` keeps its fuzzy ranked search (it still finds K12 from a bare "12"); do not "unify" them. The gate is `web-mobile/check-competitor-search.mjs` (a `.number`, `numberOf(` or `prefixOf(` read on the same line as `.includes(`/`.startsWith(` outside the owner fails the build); it shares `check-helpers.mjs` with `check-write-result.mjs` and exports `FORBIDDEN`, and `rule_gates.test.jsx` pins both gates. The one call site the gate cannot see, the admin Scores filter, is pinned by a render test instead (`score_editor_filter_finds_a_number.render.test.jsx`).

**`safeGo` convention.** Any goroutine spawned inside a request handler MUST use the `safeGo` helper in [internal/mobileapp/safego.go](internal/mobileapp/safego.go). Gin's Recovery middleware only catches panics on the request goroutine; a panic in a spawned goroutine crashes the entire process. The helper guarantees `wg.Done()` on panic and captures the recovered value into a shared `atomic.Pointer[recoveredPanic]` so the handler can return a single HTTP 500 without leaking internals. Pattern:

```go
var wg sync.WaitGroup
var panicRef atomic.Pointer[recoveredPanic]
safeGo(&wg, &panicRef, func() { /* spawned work */ })
wg.Wait()
if p := panicRef.Load(); p != nil {
    c.JSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
    return
}
```

## Participant CSV Schema (canonical)

`participants.csv` stores one participant per line. Two formats are supported:

**With UUIDs (new format)**: first field is a UUID v4 (lowercase hex).
```
<uuid>, Name[, Zekken/DisplayName], Dojo[, DanGrade][, source]
```

**Without UUIDs (legacy format)**: detected automatically when first field is not a UUID.
```
Name[, Zekken/DisplayName], Dojo[, DanGrade][, source]
```

- The zekken/display-name column is only present when `withZekkenName=true` for the competition.
- `DanGrade` is optional; omit or leave empty.
- `source` is the last column when present and must be one of: `manual`, `registered`, `transfer`. This is the registration provenance (admin-only). It is distinct from the competitor's "tag" (their assigned competitor number, which is the `Number`/`number` field, optionally prefixed via `numberPrefix`, e.g. "A1").
- Seeds are stored separately in `seeds.csv` and merged at load time. Do **not** include seed ranks in `participants.csv`.
- **Engi (kata-competition) pairs**: an engi competitor is a PAIR (two member names, one shared dojo) but is a SINGLE participant on the Go side. Both member names are COMBINED in the `Name` field, joined by `" - "`: a paste row is `Name1 - Name2, Dojo`. Engi does NOT alter the column layout (`EffectiveWithZekkenName()` returns `WithZekkenName` only), so an engi roster parses byte-identically to any non-engi roster with the same zekken setting; when zekken is on, the zekken column holds the combined pair zekken (`ZEKKEN1 - ZEKKEN2`). Display surfaces split the combined name on the FIRST `" - "` via `window.engiPairParts` (ui.jsx); Go keeps the name whole. A pair is one row in standings and one side in a match; the two names are presentation only and never split the entity for scoring.
- The Go parser lives in `internal/state/participants.go`; the JS parser in `web-mobile/js/data.jsx:parseParticipantLines`. Keep both in sync with this schema when changing column layout.

## Common Pitfalls

- **A team's people are its "team members", never its "squad"** in UI strings, in `docs/`, and on disk (operator ruling 2026-09-16, bc-dnst). The store file is `team-members.yaml`, renamed from `squads.yaml` (root key `squads` -> `members`). **A storage change carries a migration path on load covering the last TWO releases** (operator rule 2026-09-17): `upgradeTeamMembersFilenameLocked` (legacy_upgrade.go) adopts v2.0.0's file on first load and removes it once the new one is written, so a tournament recorded by that release keeps its members. v1.1.0 and earlier stored none, so that is the whole history. It converges rather than dual-reading, so only one shape stays live. The route is `GET /api/competitions/:id/team-members` and its payload key is `teamMembers`; both were renamed with the file, with no compatibility shim, because client and server ship in one binary. When you add a route here, add it to `isSelfRunMainGatedConfigRoute` under its NEW path or it becomes publicly reachable in self-run mode. "Squad" survives as a code name only, in identifiers such as `squadMemberLabel`, `squadSlotLabel` and `squadRosterEntries`, and in the client-side `squads` property that `normalizeViewerCompItem` maps the wire key onto (note `normalizeCompetitionDetail` SPREADS the payload instead, so that shape carries `teamMembers`: two shapes, two names, one concept). The Lineups page heading reads "Team members"; write the same in any new operator copy or docs page.
- **Kendo uses NO MATS. Never write "mat" or "mats"** in code, comments, tests, UI strings, docs or commit messages. The fighting area is a **shiaijo** (in prose, a **court**); "shiai-jo" hyphenated on the public `docs/` site. "Mat" is judo/wrestling vocabulary and is simply wrong for this sport. Reaching for it to avoid repeating "court" is how it gets in. (The only legitimate `mat` in the tree is a QR bitmap variable in `web-mobile/js/qr.jsx`, plus the rule's own name inside `docs/check_prose.py`.)
- Excel coordinates matter: changing match generation requires updating cell references and formula links across sheets
- `team-matches=0` means individual tournaments, not team tournaments
- The `errcheck` linter is enabled (test files excepted). Don't introduce `_ =` or bare ignored returns in production code. Wrap and propagate, or log via `handleExcelError`
- Web UI changes (`web/index.html`) should be validated in a running browser, not just by reading diffs. Use `make run`
- Mobile app frontend changes (`web-mobile/`) require rebuilding the binary to take effect. The files are embedded at `go build` time via `//go:embed web-mobile/*` in `main.go`. Run `make run-mobile` which rebuilds automatically, or run `make go/build` then restart.
- Competitor identity is (name, dojo), never the name alone. Two competitors sharing a NAME from different dojos are different people and are allowed everywhere; only same-name AND same-dojo is a duplicate. The CLI/web CSV path rejects duplicate ROWS up front via `helper.CheckDuplicateEntries` and the web handler surfaces them; the tournament app enforces the (name, dojo) rule via `helper.CheckDuplicateEntriesByNameDojo`, with the floor guard in `state.saveParticipantsNoLock` so every persistence path is covered. A blank dojo has TWO floors with TWO distinct sentinels: `state.ErrBlankDojo` refuses every roster save (loading stays tolerant on purpose so the roster can be repaired), and `helper.ErrBlankDojoInDraw` refuses the tree-aware draw over a loaded legacy roster (the draw path never crosses the save floor; the refusal names the offending row and is NOT a bug to relax). They are different errors in different packages; `errors.Is` against the wrong one silently never matches. TEAM names are the exception: they must be unique even across dojos (`helper.DuplicateNamesWithKeys`), because a team name is its identity in results. **A record that carries an id field is resolved by id only** (operator ruling bc-pnum): an empty id resolves to NOTHING, never to a name or (name, dojo) match, and no name/(name, dojo) fallback arm may sit beside an id lookup on the SAME record (`lookupStandingsPlayer`/`resolveWinnerSide` in `internal/engine/engi.go`, `groupMemberIDs` in `tiebreaker.go`, `resolveParticipantIndex` in `internal/state/participants.go`, `matchesParticipant` in `replace_participant.go`, `attachPoolMatches`/`standingMap` in `internal/export/builder.go`, and the pool-rank-override / league-tiebreak selection paths are all id-only end to end). `helper.CompetitorKey(id, name, dojo)`'s (name, dojo) fallback survives for exactly two legitimate uses: duplicate detection over an input list BEFORE ids exist (`helper.CheckDuplicateEntriesByNameDojo`, and an explicit `helper.CompetitorKey("", name, dojo)` comparison for that purpose), and records that carry NO id field at all (`state.SubMatchResult`'s lineup names). A third, narrower carve-out belongs to `state.BracketMatch` (bc-brid): its sides now carry `SideAID`/`SideBID`/`WinnerID`, so it is NOT a no-id record, and an id is present exactly when the side is a resolved competitor. A side legitimately carries no id in exactly three shapes: an empty bye slot, an unresolved feeder (a "Winner of ..." advancement or a "Pool A-1st"-style placeholder before the pool phase resolves it), and a legacy row a repair has not yet reached. For `BracketMatch` the rule is therefore resolve-by-id-when-present, name-fallback ONLY for those three shapes: `buildSideByIDOrName` (`internal/mobileapp/handlers_display.go`), `matchesBracketSide` (`internal/engine/scoring_tx.go`), and pass 2 of `ReplaceParticipantInDraw` (`internal/engine/replace_participant.go`) are the three sites that do it. A pool row has no equivalent unresolved shape: its side ids are stamped when the draw runs, and a legacy row is repaired on load where the name resolves unambiguously, so an id-less pool side is a fault the operator is told about rather than a normal state. That is why its stricter id-only rule above stands unchanged. A fourth carve-out, the same shape as `BracketMatch`'s, belongs to `domain.SeedAssignment` (bc-sdid): it now carries `ID` too, so it left the no-id list above. `state.SaveSeeds` stamps it from the roster on every write, and the legacy-upgrade pass (`upgradeSeedRowsLocked`, `internal/state/legacy_upgrade.go`) backfills it on load where the row resolves unambiguously; an id is present exactly when a resolver has already attached the row to a participant. The one shape that legitimately still carries no id is a row a repair has not yet reached (an ambiguous bare name, or a file predating the id column). `domain.RosterIndex.LookupSeed` is the id-first-then-(name, dojo) resolver every seed matcher (the seeds.csv-onto-roster merge, `helper.ApplySeeds`, `mobileapp.seedsOffRoster`) now calls, so an id, once present, is never re-checked against a possibly-stale Name/Dojo. Anything that keys a competitor with a name/(name, dojo) fallback OUTSIDE those four carve-outs is a bug: use the participant id.
- Chained match navigation in the admin score editor (Prev/Next buttons, Finish + Start Next, ←/→ keys) must stay on the current match's shiaijo. Operators run matches per-court, so hopping courts mid-flow breaks the workflow. See `AdminScoreEditor` in `web-mobile/js/admin_schedule_score_editor.jsx` (`admin_schedule.jsx` only re-exports it): filter to `(m.court || "") === (openMatch.court || "")` so empty/undefined courts share one "unassigned" bucket.
- Docs under `docs/` are PUBLIC-facing: no beads (`mp-xxxx`)/`bd`, no internal-tooling or `CLAUDE.md` references, and NO em-dashes. The PR template gates `make docs/build`; run it before pushing docs changes.
- `mkdocs build --strict` fails on broken cross-file links (WARNING) but only logs missing same-page anchors as INFO (build still passes), so verify anchors by hand. Anchors use pymdownx slugs: lowercase, punctuation dropped, `--`/parens collapsed to single hyphens (e.g. `### Locked mode (--lock-password)` becomes `#locked-mode-lock-password`). Note TWO files named `mobile-app.md` exist (`docs/user-guide/mobile-app.md` guide vs `docs/user-guide/commands/mobile-app.md` reference); a relative link from `commands/` resolves to the sibling, so confirm the target file before trusting a flagged anchor.

## Merge & Rebase

## Refactoring Rules

- **Search ALL call sites, including test files, before removing code or parameters.** Run `grep -r` (or `grep -rn 'SYMBOL' . --include='*.go' --include='*.jsx'`) to find every reference, not just production code. - The DB lives in the local Dolt store under `.beads/` (database `mp`, named in `.beads/metadata.json`). All of `.beads/` is gitignored, so the DB is never committed here.
- **Sync remote:** the PRIVATE Forgejo repo `Ricardo/bracket-creator-beads` over `git+https`, stored as `sync.remote`. Beads push to `refs/dolt/data` there, deliberately NOT to `origin`; this GitHub repo is public and the issue DB is not. Do not add a beads remote pointing at a public repo.
- **`.beads/` is shared by every worktree** (bd walks up from the worktree to the repo root), so concurrent sessions write to one DB. Never swap, restore, or replace the DB while another session may be running.

### Gotchas that have already cost time

- **`store is read-only` means a prefix-ownership problem, not a lock or corruption.** bd routes writes by issue-ID prefix; a prefix this repo does not own is routed elsewhere (see `routing.*` in `.beads/config.yaml`) and rejected. Run the write where that prefix lives, or fix the routing. Diagnose by comparing a native-prefix write against the failing one.
- **`bd config set` / `unset` are unreliable on nested keys.** `set` can rewrite flat `a.b:` keys into a nested `a:` block; `unset` can report success while leaving the key in the file. Always confirm with `bd config get <key>` AND by re-reading `.beads/config.yaml`, and hand-edit when they misbehave.
- **`bd where` reports the wrong prefix here.** It reads `issue_prefix` from `.beads/config.yaml` (which says `bc`), but ID generation uses the value stored in the DB (`bd config list` → `issue_prefix = mp`). The file value is inert. Trust `bd config list`, not `bd where`.
- **`bd export` JSONL is lossy: it carries `dependency_count` but no dependency edges, and no comment bodies.** Never migrate or restore a beads DB via export/import; it silently drops blocker relationships. Copy the Dolt database directory instead.
