# Match writes: merge, refusal and the clock frame

Moved from CLAUDE.md "Merge changes, never drop" and "Write refusal and the clock frame". Read before changing any match write, its answer, the offline queue, or a score editor's save path.

## Merge changes, never drop (bc-mrgc)


Operator ruling 2026-10-03: "Nothing should be dropped. All events must be ordered." A match write is merged GROUP BY GROUP onto the stored match, ordered by the stamp of when the change was made (`modifiedAt`, server-relative, never arrival order), and what does not apply is kept in the match's history. Each rule below has one owner; change the owner, never a call site.

- **The groups** (`internal/state/match_groups.go`, the ONE owner of which fields each holds): `points` (IpponsA/B, HansokuA/B), `result` (Status, Winner/WinnerID, Decision/DecisionBy/DecisionReason, and the CorrectionReason/ResultSource that describe it), `encho`, `flags` (engi), `rep` (pool rep players), `recorded` (the SERVER's alone, `state.ServerGroups`: which numbered kachinuki bouts Record bout closed, as sorted positions; a client naming it in `changed` is a 400, the merge copies the stored marks over a client's rows, and `bout:N` does not hold the mark, so a point on bout N and Record bout never fence each other), `repPickA` and `repPickB` (each side's representative picked for a team match's representative bout, SideAMemberID and SideBMemberID of the -1 row: each dated apart from the other side's and from `bout:-1`, so two captains picking at the same moment both land, a point on that bout never erases a pick and a pick never erases a point; the row's WinnerMemberID stays with the bout and the merge re-derives it when the two disagree, `ReconcileWinnerMemberID`), and `bout:<position>` per SubResults row (1..n, -1). Sides and ids, court, schedule, round, ReopenPending, IsOverridden and the bracket structure are NOT groups: their own writers keep them. `CopyGroup` moves a group, `GroupDiffers` compares one, `GroupValue` projects one for the history; nothing hand-copies a field list.
- **The stamps**: `GroupStamps map[string]int64` on `MatchResult` and `BracketMatch` (pool-matches.csv: the `GroupStamps` column, index 29, JSON, appended after `ModifiedAt`; bracket.json: `groupStamps`). A match with NO map reads every group as stamped at its `ModifiedAt` (legacy files behave exactly as the whole-match guard did); once a map exists, a group with no entry was never written (0). `ModifiedAt` stays the newest group stamp (recency and `keepNewerMatches` read it). A bout whose row is gone keeps its stamp: a TOMBSTONE, so an older write still carrying the row cannot resurrect it. `stampGroups` (`MatchResult.StampGroups`/`BracketMatch.StampGroups`) is the ONE stamper: it materializes a legacy match's implicit stamps before stamping one group, or every other group would start reading the new `ModifiedAt`, and it never LOWERS a group's stamp (a caller that already holds a later one for a group -- an engi finish let through as a HeldEcho under an older stamp -- must not drag it backwards, or a change genuinely made between the two would wrongly read as applying after a group it never actually followed; mirrors `ModifiedAt`'s own never-lower rule); a stamp the MERGE decided, which may be lower (the displacement of scoring a result closed out moves it out and gives the group the result's own stamp), is written as decided through `ApplyMergedGroupStamps`, never through `stampGroups`. Every writer that changes a group outside the merge stamps it through it: the reopen (`reopenPoolMatch`/`reopenBracketMatch`, server now), the requeue (`RevertMatchToQueue`/`requeueBracketMatch`: the verdict only, the kept score keeps its stamps), override-winner (`result`, and its own comparison is on that group), the engi finish (`result`+`flags`, at the client's stamp once the merge has ordered it, `engiFinishHeld`; server now only for an unstamped writer), the kachinuki advance (the `recorded` mark, and the appended `bout:n` + `result`, at the server's time and strictly after the match's `ModifiedAt`, so every device's `keepNewerMatches` orders the marked copy after the one before it; the Record-bout answer echoes the bout log AND the stamps the advance left, `engine.KachinukiAdvance`, and the team editor adopts the stamp with the log, so its next tap on the new bout is floored by it, bc-hlck), `RemoveTrailingKachinukiBout` (the removed bout's tombstone, and `recorded` when it un-records), the merge itself for `recorded` when a write raises a recorded bout's overtime, and a downstream reopen (`reopenDisplacedBracketMatch`, `bout:-1` with it). Byes auto-completed at draw time carry no stamp, which is right.
- **The wire**: `MatchResult.Changed` (`json:"-"`, request-only, beside `ClearsWithdrawal`) is read from `/score`'s and each bulk entry's `changed`; a name that is not a group is a 400. ABSENT means every group the payload carries (`defaultChangedGroups`; on the pool branch a nil SubResults still names the stored rows, the whole-struct write's old meaning), EXCEPT that a client's running or scheduled write over a COMPLETED match never carries `result` (`effectiveChangedGroups`). Every server-built write names its groups: decision `result`+`points`+`encho` (`decisionChangedGroups`), both-barred hikiwake `result`, daihyosen add `bout:-1`+`result`+`repPickA`+`repPickB` and remove `bout:-1`+`result`+`encho`+`repPickA`+`repPickB` (both date both sides' picks, so a pick made on the previous representative bout is held, never landed on the new one; +`points` when clearing the verdict took a hantei mark out, `daihyosenChangedGroups`), quick-score every group and every stored row (`WholeMatchChangedGroups`), a start (`startOnly`) `result` alone. The rows the server itself changes after the writer sent them (kachinuki merge, the padding a match-level decision adds) are added by `noteServerBoutChanges`; in a kachinuki write, which merges its bout log by position, a stored row the writer left out counts too, so the finish's strip of a trailing unscored pairing is named and not copied back. It and `daihyosenChangedGroups` (mobileapp, the representative-bout add and remove, built from the stored match under the same lock) are the two places the server diffs, each its own values under the write's lock; a CLIENT payload is never diffed against the store, or an echoed stale group with a newer stamp would read as an edit. A server-built door reaching the merge with `Changed` nil is logged as a BUG (`serverBuiltWithoutGroups`). A bracket door that gives a side another team without reopening that match records a `reseat` history line naming the cleared pick group (`recordRepPickClears`, bracket_seat_audit.go: a snapshot of every match's picks before the door's write, diffed after, in the same transaction; `ResolveQualifiedPools`, the resolver run after a pool write or a `DELETE .../overrides`, is such a door, in its own `WithTransaction`); a reopened match's `downstream-reopen` line names the pick instead, and a refused write's restore records nothing. `MatchResult.WriteDoor` names the door for the history.
- **The merge owner**: `mergeMatchWrite` (engine/match_merge.go), called by BOTH branches before anything else judges the write (`applyPoolWrite`; `applyBracketResultIn` for rounds and bronze, ahead of `preserveWithdrawalRuling` and the downstream guard), each after folding the stored pairing into the write (`reconcileSides`; on the bracket branch `sidesBeforeMerge`), so a winner worked out again reads the stored sides, never a payload's omitted ones. An UNSTAMPED write the server orders itself (a completing write, or any write a server door builds: quick-score, an engine caller, a decision with no stamp) takes the server's time there, never older than the stored `ModifiedAt` (`writeStamp`), so it leaves a fence a later stale replay is ordered against; only a client's unstamped running or scheduled write keeps the unstamped bypass. A changed group applies when `domain.ApplyByTimestamp(stamp, storedGroupStamp)` (0 on either side applies) and takes the write's stamp; otherwise the stored value is copied in and the group is HELD (its incoming value goes to `MergeReport.HeldValues`). A group the write does not change always takes the stored value. An applied group whose value equals the stored one is `Unchanged` (an echo); for a write that NAMES NO groups at all (`Changed` nil: bulk-score, an older client, which cannot tell an echo from a change) it keeps the stamp it already had rather than taking the write's, and `ModifiedAt` moves only when some applied group actually changed, so a whole-match echo can never fence out a real, older change made on another device in the gap. A write that NAMES a group takes the write's stamp there even when the group echoes: naming it is a real action taken at that time (an operator re-sends the value their screen showed, or a replayed decision), not a re-send of everything the write happened to carry, and `ModifiedAt` moves with it. A HELD group whose value equals the stored one is no loss (`HeldEcho`, bc-mrgc phase 3: a decision's "no overtime" over a match with none): it is neither listed in `heldGroups` nor kept in `HeldValues`, and its history outcome is `unchanged`. The write is SUPERSEDED only when something is held (or echo-held) and every applied group is an echo (`MergeReport.Superseded`): then nothing is written to the match file, exactly as before. The report rides on `MatchResult.Merge`; `ResultChanged` false (the verdict did not move: held, or applied as an echo of the stored one, e.g. the same withdrawal sent again under a later stamp) skips the eligibility record, since re-recording a stored withdrawal would rewrite its status and undo a reinstatement made since. Corrections get no exemption: a stale correction is held like any other change.
- **The closed-match rule** (operator ruling 2026-10-15, replacing R2, R3, R4, S2 and S3, whose "points scored means the withdrawal was a mistake", "stay finished, add the point" and "it needs a winner" it supersedes): in STAMP order, once a finish or a decision (kiken, fusenpai, fusensho, hantei, daihyosen, hikiwake, a both-barred hikiwake) is recorded, any tap event or scoring write stamped AFTER it is refused and kept in the history, and the device is told the match is finished and to use Correct result. It is the same whichever arrives first: the replay (`closed()` in score_replay.go, `judgeOverFinished`) orders every line by its stamp, so a tap that reached the server before the finish is `applied` and then flips to `matchClosed` when the finish arrives, and a finish stamped before a stored point closes that point out into the history (`MergeReport.Displaced`, door `displaced`, reason `HoldReasonMatchClosed`). Answers: an event `matchClosed` with `reason: match_closed` and `MatchClosedMessage` (engine/match_merge.go, the one sentence both doors use); a score, decision or bulk-score write fully refused is the 200 `{applied:false, reason:"superseded", heldReason:"match_closed", heldGroups}` (`state.HeldReasonMatchClosed`), and one applied in part (a finish that closed out a stored point) adds `displacedGroups` with the same `heldReason`. `default_win_stands`, `needs_winner` and `heldDecision` are gone: one code, one remedy. What is stamped BEFORE the result keeps D5 (contained in the result's basis -> `recorded`, else `beforeBaseline`; `contains` also requires the tap to be stamped no later than the baseline, since a server-built write's `Seen` is arrival order). A NEWER finish or decision over an older one is the newer one in either arrival order, and the older is not dropped: it is logged as it was sent (`MergeReport.Baseline`, `recordSupersededWriteHistory`, only once the match's log has begun), so a tap stamped between the two is closed out by the older one and the newer one derives from it. A decision's points are worked out by the replay, not copied from the value it carries (`keepLoserPoints`: the circles for the side that did not withdraw, the points the withdrawer struck BEFORE it, FIK Art. 32), and the default-win bout padding is the replay's too (`padDefaultWin`), so the loser's points and the padded rows are the same in every arrival order. A correction (a completed write naming `result`), a reopen, override-winner and a send back to the queue are results or opens in their own right, ordered by their stamp: after a reopen the match is open again from the reopen's stamp. A running or scheduled write over a finished match never carries `result` (`effectiveChangedGroups`); an UNSTAMPED one cannot be ordered and is held whole. The score handler still treats it as a correction (no court gate, no StartMatchTx: `writesOverFinished`) so the answer is `match_closed` and never a court refusal. The wire fields and the client's `writeNeedsWinner`/`writeDefaultWinStands`/`writeHeldDecision` are stage 3's to retire; the matrix `internal/engine/match_write_permutations_test.go` pins one outcome per case for every arrival order, with the answer of every write, `ModifiedAt`, the competitor's status and the knockout winner advancing.
- **The history** (internal/state/match_history.go): one append-only file per match, `competitions/<id>/history/<url.PathEscape(matchID)>.jsonl`, one JSON line per write that reached the merge: stamp, server `receivedAt`, door, session, changed groups, per-group outcome (`applied`/`unchanged`/`held`), the held groups' incoming values, any cleared withdrawal, and the `reason` when one rule held the write's groups rather than their stamps (`MergeReport.HoldReason`: `HoldReasonOlderRevision`, `HoldReasonEngiAtomic`, `HoldReasonMatchClosed`, `HoldReasonRepBoutRemoved`; the History view shows it as "Not applied: <reason>"). `StoreTx.AppendMatchHistory` stages the whole small file in the SAME transaction as the write (`LoadMatchHistory` reads it, read-your-own-writes), so an aborted transaction leaves no entry. Written at the point the write can no longer be rolled back (`recordWriteHistory`: after K3/requalification in `RecordMatchResultWithIneligibilityTx`, in `writeMatchResult`, and on the superseded paths), so a write refused by validation, a side mismatch or K3 leaves none; every direct writer above appends its own (`recordDirectHistory`) INSIDE the transaction that makes its write: the doors already in one (the reopens, the kachinuki bout remove, the downstream reopen) pass their `tx`, and the kachinuki advance, `OverrideBracketWinner` and `RevertMatchToQueue` each open a `WithTransaction` for the write and the entry together (`withBracketMatch` takes the store handle, as `withPoolMatch` does), so a process dying between the two leaves no match change without its line; a held override writes nothing and appends on its own. `recordDirectHistory` logs a failed append rather than returning it, so a failure of the append alone still lets the write commit without its entry (accepted). The history directory is created only under an existing competition directory (`ensureMatchHistoryDirLocked`), so a write after `DeleteCompetition` fails rather than resurrecting it; `DiscardDraw` deletes it (`DeleteMatchHistory`), since a regenerated draw reuses the match ids. A fully-held write must COMMIT its transaction for its entry to land: every door returns nil from its closure on `ErrMatchSuperseded` and answers after (the score/decision handlers always did; bulk-score, both daihyosen paths and `RecordMatchResult` were changed to).
- **The answers**: a write applied in part answers applied (the merged result) plus `heldGroups` (`scoreResponseWithReopened`, `withHeldGroups`, bulk-score's top-level `heldGroups`); a fully-held one keeps the 200 `{applied:false, reason:"superseded"}` shape the SPA keys on, plus `heldGroups` (`respondSuperseded`, `SupersededMessage`: "kept in the match's history"). Either answer adds `heldReason: "match_closed"` when the closed-match rule turned the write's scoring away (`MergeReport.HeldReason`; a fully held one then carries `MatchClosedMessage`; bulk-score puts it on the entry), and an applied finish or decision that closed stored later-stamped scoring out into the history adds `displacedGroups` (`MergeReport.DisplacedGroups`) with the same `heldReason` (score, decision, daihyosen, bulk-score's `heldGroups[]` items). `ErrMatchSuperseded` is returned as `*SupersededError` carrying the held groups and that code (`errors.Is` still matches; `HeldGroupsOf`/`HeldReasonOf` read them). A completed write stamped OLDER than the stored `result` group over a finished match is not asked for a correction reason (`applyCorrectionReason`, `matchSnapshot.ResultStamp`): a stale finish is ordered by the replay (its verdict is the older of two results and is held, its other groups by their own stamps), and one that changes nothing is answered superseded and kept in the history. An equal stamp that changes nothing (every group the write changes, `effectiveChangedGroups`, equal to the stored value once read as the write would land it) is the finish already recorded, sent again because its answer was lost: `engine.ExactScoreReplay` (the score counterpart of `exactDecisionReplay`) lets it past the reason check, and the engine answers it as recorded (`answerExactScoreReplay`, in `RecordMatchResultWithIneligibilityTx` after the older-revision hold and before the engi dispatch, so before every refusal): the stored match, with a bracket match's court and schedule filled in, nothing written, and one history line whose groups all read unchanged (none for an anonymous self-run participant's resend, `ForceOptions.NoReplayHistory`, so looping it cannot grow the history file). A same-stamp write that differs still needs a reason. The request-only fields (`Changed`, `WriteDoor`, `Merge`, `ClearsWithdrawal`) never ride on a stored copy: `MatchResult.ClearRequestFields` is the one list, called on the pool write's overwrite and on every pool-match copy the store hands out.

- **The client (phase 2)**: every score write names its groups. `web-mobile/js/match_groups.jsx` is the ONE client owner of the names (pinned against `state.ScalarGroups`/`BoutGroup` by the shared table `internal/state/testdata/match_groups.json`: `TestMatchGroups_SharedTable` and `match_groups_table.test.jsx`), of the comparison (`changedGroups`, on WIRE shapes only: both sides go through `toBackendMatchResult`, the adopted copy via `matchWire` in api_serializers.jsx, so a placeholder slot, an Ht placement or a winner object never reads as a change; a field the write leaves out, e.g. an omitted correction reason or a silent representative bout's ippons, is not compared, and a bout row the write does not carry is never a change), of the union (`unionChanged`: no list on either side means every group and stays so) and of a group's words (`groupLabel`). `useChangedGroups(m)` (admin_scoring_autosave.jsx) is the one hook the three editors call; every patch goes through its `claim` (the individual and team `buildPatch`, a hantei included since bc-htsd, the engi save and autosave builder). A group counts against TWO baselines: the server value the editor last AGREED with for that group (seeded at mount, moved on at each build where local equals the prop, and by `claim.agree(group)` when an editor's adopt TAKES the server's value for that group, or when the team editor's withdrawal-removal Undo puts the whole board back to the server's (every bout group and both pick groups); an adopt that takes only PART of a group agrees it only when the editor's whole group then equals the server's (the individual editor's hantei adopt skips `points` while a point of its own is unsaved; a representative-side adopt agrees `rep` only when both sides then hold the server's picks); both baselines are kept per group), NOT the latest prop, or an edit held while another device changed a group the editor kept its own value for would put the old value back; and the last write the editor built, or a tap taken back before the first write's echo would name nothing. A reopen is a write the server makes, not a build, so when the match the editor renders leaves `completed` (a reopen, or a send back to the queue) the editor takes the result it now holds as agreed, that group alone (`useChangedGroups`): without it, ending a reopened match again with the verdict it had named nothing, and the server kept the match running with no error. It keys on the status, not on `reopenPending`: a reopen without a reason carries that stamp, but one a correction's reason comes with (a downstream reopen, a requalification, a pool-rank override) leaves the match scheduled with its points and no stamp, and an editor that watched only the stamp named no result for it. `startPatch` names `result` alone. The outbox keeps `changed` verbatim (persist, cross-tab, rehydrate, replay); a score write that takes a queued one's place claims the union (`_claimingQueuedGroups` in `_placeWrite`, and the absorb in `recordScore`, both against the one entry `_coalesceTarget` names); `_broadcastPatch` strips it. Answers: `writeHeldGroups`/`writePartlyHeld` (write_result.jsx) for a partial apply, which the editors answer with a quiet note (`useKeptInHistoryNote`/`KeptInHistoryNote`, worded by `heldGroupsNote`) and `editMatchScore` with a toast when the write closes the editor; a superseded write leads "Not applied", never "Not saved" (`SUPERSEDED_LEAD`, `notSavedText`'s `lead`, `supersededAlertText`). The editors' closed-by-default **History** disclosure (`MatchHistoryDisclosure`, match_history_view.jsx, `data-testid="match-history"`, hidden under `selfReport`) reads `GET /api/competitions/:id/matches/:mid/history` (`RegisterMatchHistoryHandler`, stamp order with an unstamped entry at its `receivedAt`, `[]` when none, 404 for an unknown competition or match, main-gated in self-run), readable values through `formatIpponsScore`/`withdrawalLabel`/`sideWord`.

- **Phase 3, the remaining drop sites, each with one owner:**
  - **The running rev guard holds, never drops.** A running write with a lower `rev` than the same `revSession` already sent is held whole by the merge (`mergeMatchWrite`'s `olderRevisionThanLogged`, which reads the baselines in the match's score log: the same session at a higher revision since the match last started running), with `HoldReasonOlderRevision` in the history entry; the answer is `respondSuperseded` with `heldGroups`. `{stale:true}` no longer exists anywhere (server, openapi, client: `_handleOkBody` and the admin toast that read it are gone).
  - **The offline queue keeps, per match, a list of pending writes, each sent on its own** (api_client.jsx). Each pending write is its own entry, keyed `${base}${QUEUE_ENTRY_SEP}${id}` (`_newEntryKey`; the separator is `\u001f`), where the BASE is what the write is about (`_revKey` for a score or a decision, `override:…`, `lineup:…`; `_baseOf`). A key persisted by the previous build has no separator, so it is its own base: an old queue loads and replays unchanged, which is the migration. The ONE coalescing rule is `_coalesceTarget`: a score write takes the place of its match's LAST entry only when that entry is a score write not newer than it and not the page-hide copy of a write still being sent, and a RUNNING write only of a running one (`_placeWrite` then claims the union and carries a pending `kachinukiBoutFinal`); a LINEUP save joins a queued save of the same lineup (`joinQueuedLineupSave`, lineup_save.jsx: the union of `changed`, the later value per position): a lineup PUT carries no stamp the server could order it by, so a direct save could land before the queued one's replay and lose to it on a position both changed; the caller reads `{queued: true}` for the moment until the flush sends it. Nothing else replaces anything, so a running write never replaces a queued Finish or a decision, and a decision and a score are two entries. A pass sends entries in the ONE replay order, `_byEntryOrder` (the payload's `modifiedAt`, else `enqueuedAt`, then the key), but each entry on its own: one that does not settle (offline, 5xx, parked, re-stamped for skew, held by an open fetch) holds back nothing after it, and a new score, decision or override goes straight to the server whatever is queued, because the server merges by stamp, not arrival (bc-mrgc review C2: the old wait-behind rule let one write failing with a 5xx stop every later write for its match). An entry that settles (sent, or refused for good) leaves browser storage at once (`leaveQueue` in `_flushQueue`), not at the end of the pass, so a page that goes away while a later entry is still out does not send it again on the next load. The editors' "Retry now" on a queued Finish therefore sends it at once: landing, it drains the queued copy it claimed; failing, it takes that copy's place. A landed direct score write drains only the entry it claimed (`claimedEntry`), never a queued Finish or decision. The page-hide copy (`_keepInflightRunning`) is an entry of its own (`w.keptKey`); recordScore settles its OWN copy through the record it created (`inflightRecord`), even after a later running write took the map slot, and when it had one and its fetch answered it schedules a flush a microtask later, after the answer has drained its claimed entry. A queued answer says whether the write reached browser storage (`_queuedAnswer`: `persisted: false` only when `_persistQueue` failed, read before the enqueue kicks a flush). A write the server keeps refusing (past `SERVER_REJECTION_NOTICE_THRESHOLD`) can be discarded alone from its match's editor (`HeldWriteDiscard`, admin_scoring_shared.jsx; `API.heldWriteKeepsFailing`/`discardFailingHeldWrites`, that match's failing entries only, after a confirm). `resumeAfterAuth` gives the new password to every parked write AND every queued write still carrying a password the server refused, never to one queued with none (a self-run participant's). Every refusal on replay is reported: a decision's 409 (`already_ineligible` included) goes to the terminal-fail and `rejected` alert channels like any other, because the server answers an EXACT replay of a recorded decision (same decision, side and stamp: a send whose answer was lost) as recorded before any of its refusals (`exactDecisionReplay`, scoring_tx.go). A held finish that lands and moves a later change to the history (`displacedGroups`) counts as sent and raises one `displaced` information alert per pass. Nothing is dropped for its age: `QUEUE_TTL_MS` and the `expired` alert are gone, and an old entry is sent; the server orders it and keeps what loses in the history. Pinned by `queue_ordered_writes.test.jsx` and `sync_queue.test.jsx`.
  - **Override-winner** stamps and orders the `result` group (phase 1); a held assertion is answered `respondSuperseded(["result"])` (reason `superseded`, `heldGroups`), the client returns `heldGroups`, the Resolve feeders toast says it was kept in the history (`OVERRIDE_HELD_NOTICE`, write_result.jsx), and a queued one the server held counts into the pass's superseded alert as well as asking for a bracket resync.
  - **The engi finish** is stamped by `recordScore` like every write, and the server orders it: `engiFinishHeld` (engi.go) asks the merge on a copy built from the stored match (`engiFinishProbe`), BEFORE the downstream guard; the flags and the winner they decide are atomic (either held → both held, `HoldReasonEngiAtomic`, reached when the flags are newer than the stored count but the result is older than the stored one, e.g. after a later reopen; a stale finish over a COMPLETED match is held whole one step earlier, by the same atomic hold) -- the closed-match rule replaces "the newest count decides" (2026-10-04): the finish closes the match, so a count stamped after it, valid or not, is turned away (or closed out into the history when the finish arrives second) in either arrival order (`TestMerge_EngiNewestValidCountDecidesInBothOrders`) -- and an ECHO of the stored flags (same count, under an older stamp) is not a hold at all, so the finish still applies; held → history and superseded; applied → `recordEngiMatch` writes `result`+`flags` with the stamps the merge decided (`engiFinishHeld` carries the probe's `GroupStamps` down, `stampEngiChanges`/`ApplyMergedGroupStamps`), so both arrival orders reach the same stamps after a displacement; an unstamped writer still gets the server's time.
  - **Read-modify-writes are one transaction.** `InjectPoolDaihyosenMatches`, `InjectTiebreakerMatches` (the engi self-heal too), `GenerateLeagueTiebreakMatches` and `AdvanceSwissRound`'s append each read pool-matches.csv, decide, and save under ONE `WithTransaction` (standings through `computeStandingsFrom(tx)`, the tournament read before the tx, `appendWithSlots` for the new slots); a score landing meanwhile waits for the lock and goes on top. `MaybeAdvanceKachinuki` still reads without the lock, and its locked write re-checks (`kachinukiAdvanceStillHolds`: not completed, same status, stamp and bout log) and on `errKachinukiAdvanceStale` reads the match again and works the pairing out from it (`advanceKachinukiOnce`, up to `kachinukiAdvanceAttempts` times, standing down only then: a stand-down answered the operator's Record bout with no next pairing; a finish that landed is final on the re-read, so it is never reopened; the bracket branch uses `UpdateBracket` with `Bracket.MatchByID` so it can abort). `Engine.afterMatchRead` is the test-only seam at each read (`lost_update_window_test.go` lands a real write there).
  - **A rename is not a side mismatch.** `reconcileSides` accepts a payload side whose id equals the stored id whatever name it carries, keeping the stored (current) name on the side, on a winner named by the old name, and on every bout row field that names the side by it (`adoptCurrentSideName`: the representative-bout row, and a fixed-order or id-less kachinuki row whose winner is the team, which `state.SubBoutWinnerSide` would otherwise credit to nobody); only an id disagreement, or a name disagreement no id can settle, is `side_mismatch`. Only an id the CLIENT sent proves a rename: the handler's hantei/winner-id backfill (`backfillMatchIdentityForHantei`) fills a side id only beside the stored name it belongs to, so a payload naming someone else with no ids is still `side_mismatch`.

Accepted as they are: a replayed queued write applied in part tells nobody (the history has it) (a replayed write the closed-match rule turned away is reported like a superseded one). An exact decision replay adds a second history line that reads like the first ("Decision recorded", every group unchanged), and the organiser's exact finish replay likewise (every group unchanged); an anonymous self-run participant's adds none. A queued write the server keeps refusing with a 5xx is retried as long as the page is open and holds back no other write; the editors' **Discard held result** covers a terminal score write, and the admin topbar's held-writes count opens `HeldWritesPanel` (admin_shell.jsx), which lists every held write (`API.heldWrites()`) and discards any one that keeps failing (`API.discardHeldWrite(key)`; both doors go through `_discardIfFailing`, so a write only waiting for the connection is never discarded); a same-session reopen over a write the browser could not store shows the plain held notice. An answer that both held groups and moved a later change (`heldGroups` and `displacedGroups` with one `heldReason`) is read as the move's: the held part gets the plain newer-change note. `unsentWrites().total` counts entries, so two pending writes for one match count two; `terminal` still counts results. `InjectTiebreakerMatches` and `InjectPoolDaihyosenMatches` compute standings uncached, under the competition's lock, on each call. A partial apply on the self-run public sheet's finishing write closes the editor with no note. Every write re-stages its match's whole history file through the WAL, so a long match's history costs a rewrite per autosave; compaction is for a later phase. A correction on a knockout match whose next match was already played is refused like any other knockout correction (`downstream_knockout_played`/`_running`). History entries recorded before phase 3 may still list an echo as held. A lineup save made while a save of the same lineup is queued reads `{queued: true}` until the flush sends it, a moment later when the device is online. A write whose transaction log committed but whose file write then failed (`state.ErrTxCommitted`: a disk that refuses writes) is answered 500 like any internal error, so the device keeps retrying until a write lands (operator decision 2026-10-04): the change is already kept, written on restart or by the next write the disk accepts, and `internalError` (errors.go) logs it as an ERROR naming the disk; a Discard of it does not stop it applying at restart. A completed write whose result is older than the stored one (a stale finish, a correction made on another device before a later one) is ordered by its stamp like every other write: its verdict is the older of two results and is held, and the groups it names land or are held by their own stamps, exactly as the same writes in stamp order give. Nothing is lost (the held values are in the match's history as always).

## Write refusal and the clock frame (bc-lww1 / bc-cse)


A match write can be REFUSED by the server, and a refusal is always **HTTP 200** carrying `{"applied": false, "reason": ...}`, never a 4xx/5xx, because the SPA's offline write queue retries 5xx forever (the mp-q8c6 poisoned-queue pattern) and a refused write can never win a retry. Two reasons exist:

- `superseded`: the merge held every group the write changes (bc-mrgc): a NEWER change to each is already stored. Nothing of it was applied, and it is NOT lost: its values are in the match's history and the answer names `heldGroups`. The operator must **not** blindly re-enter: a fresh entry is stamped now and would overwrite the newer change.
- `clock_skew`: the write's `modifiedAt` was more than 5s in the server's future (`modifiedAtRefuseSkewMs`, handlers_match.go), so it is provably wrong. Nothing was stored, the client resyncs its `/api/time` offset, and re-entering IS the remedy. The copy for the two cases is deliberately opposite; do not merge them.

**Which endpoints compete on timestamps**: `/score`, `/override-winner`, `/decision` (since mp-jnvl) and both daihyosen paths (since bc-dhas) each carry the client's stamp, so any of them can be refused for either reason. Quick-score alone still builds its result with NO stamp; the merge gives it the server's time, never older than the stored stamp (`writeStamp`, bc-mrgc review), so it still always applies and now leaves a fence a stale replay is ordered against; it maps the refusal shape defensively anyway. The daihyosen add and remove are stamped so the match they write is newer than a copy read before them, which is what lets `keepNewerMatches` keep the post-add copy over a stale refetch. Both take an optional JSON body `{"modifiedAt": N}` (the DELETE too; an empty body is unstamped and always applies), judged by `daihyosenWriteStamp` through the same `clientClockSkew`/`clampClientModifiedAt` pair as `/decision`; the stamp rides on the match the handler writes, so the ordinary write guard decides. `recordDaihyosen`/`removeDaihyosen` hand a refusal back as the refusal body (`_daihyosenOutcome`), and the team editor reports it through `notLandedBanner` and adopts nothing. A decision is stamped because it is the write that CLOSES a match, and a match closed while still `scheduled` (a queue row's Record fusensho) has no earlier write to inherit a stamp from, so the result carried no time at all and nothing downstream could order it. A stale decision is answered `superseded` before any of the decision's refusals judges it (`recordDecisionTx` asks the merge on a copy, `decisionHeldByMerge`: already barred, a running later match), since each of those would otherwise read as something to resolve and send again; an EXACT replay of the recorded decision is answered as recorded, before them too (`exactDecisionReplay`), from the prior and without a write; for a bracket match that prior is `bracketMatchAsResult`'s projection, which carries no court or schedule, so the replay branch fills them from the bracket (`bracketMatchCourtAndSchedule`, bracket_result.go) as a fresh decision's write echoes them, and the answer and its broadcast keep the court. A held override-winner answers `superseded` with `heldGroups: ["result"]`. The stamp reaches the engine through a VARIADIC parameter on `RecordDecision`/`RecordDecisionTx`: the engine-internal caller and the suite's decision tests omit it, and the handler is the one caller that must always pass it.

**`web-mobile/js/write_result.jsx` owns that whole rule**: `writeDidNotLand` (queued OR refused), `writeWasSuperseded`, `writeWasRefusedForClock`, `notLandedBanner(res)`, `writeKeepsEditorOpen(patch, res)` (bc-plcl: the one rule every score-editor host asks before closing its editor: a write that did not land, or a running write with no winner, keeps it open), `writeWasRefused(res)` (nothing handed back, which is how every host reports a refusal, or `applied: false`: the two-tap commits Finish, Finish + Start Next, End match and the engi Save disarm, because tapping again would re-send the refused write, and a superseded one would win; a held write the operator DISCARDS disarms the same way, bc-cse operator ruling 2026-10-05, via each editor's own one `dropHeldWrite`-style function, passed as `HeldWriteDiscard`'s `onDiscarded` prop for the editor's own Discard held result AND as `useClearPendingWhenNothingHeld`'s callback for a discard made elsewhere, e.g. the admin topbar's held-writes list) and `writeRetryable(res)` (a QUEUED write only: it gates the pending banner's Retry and the kept submit closure, while the not-saved banner never carries a Retry), `queuedNotice(res, { keepsFailing })` (the held-write line: `QUEUED_NOTICE`, or `QUEUED_UNSAVED_NOTICE` "Not sent yet: keep this page open until the connection returns." when the queue answered `persisted: false` because browser storage would not take it, or `QUEUED_REFUSED_NOTICE` once the server keeps refusing it; the editors keep the queued answer in `pendingWrite` and render the line through `HeldWriteNotice`, admin_scoring_shared.jsx, which with the Discard beside it and the banner's own clearing reads ONE hook, `useMatchHeldWrite`: what this device still holds for the match, `held` and `stuck`, re-read on every sync-status change and every held-count change, the counts carrying `failing` so a SECOND write crossing the threshold is published too; the banner goes once the match holds nothing, landed or discarded from anywhere, `useClearPendingWhenNothingHeld`, never "when the whole queue drains"), the two readings of a held answer (the server now sends `heldReason: "match_closed"` for what these two named `needs_winner` and `default_win_stands`; the client wording is stage 3's to retire): `writeNeedsWinner(res)` (this write's OWN change was held because it would leave a finished match without a winner, superseded or applied in part; `supersededBanner(res)`, the partial-apply note and the superseded queue alert then say to correct the result with a winner) versus `writeDisplacedGroups(res)` (the write was RECORDED and moved a later change of the match to the history, an applied answer with `displacedGroups` and no `heldGroups`: the note says "Saved" and what was moved, `displacedAlertText` for a replay); `keptInHistoryNote(res)` (match_groups.jsx) is the one note built from them, for the editors' `useKeptInHistoryNote` and admin.jsx's `closingHistoryToast`, and every operator-facing string. `notSavedText` is the one "Not saved" line every such banner shows (the three score editors, fed by `terminalFailureBanner`, and the barred-match notice): "Not saved: <reason>. <advice, else re-enter>", or the refusal as it is when it is a whole sentence that says what to do (`sentence`, set by `_replayRefusal` in api_client.jsx for a server `message` or `reasonHuman` and for the busy-shiaijo copy, never for a bare code or HTTP status), and `queueAlertMessage` ends its `rejected` alert on that sentence instead of "Re-enter it." for the same reason. Every host also hands the editor back what a write came back with (a refused write throws and returns nothing), which is how the editors' own Start match tells a landed start from a refused one. It is a leaf with no imports, and **every consumer ES-imports it directly**; there are no `window` mirrors and re-adding one fails `make js/check-imports` (see `web-mobile/check-write-result.mjs`, which also forbids hand-rolled `.applied`/`.persisted` comparisons outside the owner and `api_client.jsx`; its walk, comment stripper and line scan are `web-mobile/check-helpers.mjs`, shared with the competitor-number gate below, and its `FORBIDDEN` rules are exported so `rule_gates.test.jsx` can pin them). This exists because the question was originally spelled `res.queued` inline at ten call sites, and when a second not-landed shape appeared the conversion reached five of them.

Two distinctions that look like details and are not:

- **`writeDidNotLand` vs `writeWasSuperseded`.** Both mean "not stored", but a QUEUED write lands on reconnect, so an offline court must still advance its local bracket; a REFUSED one never lands, so anything derived from it is wrong. Gate optimistic UI on the stronger predicate and general "did it save" checks on the broader one.
- **Client clock stamps are server-relative**, learned from `GET /api/time` (retried until it first succeeds, relearned on SSE connect, on `'online'`, on any refusal, and when the 15s heartbeat's `nowMs` diverges by more than 3s). The heartbeat value is a divergence TRIPWIRE only, never an offset source: a one-way push has no RTT to correct, so a late frame would drag the device's clock frame backwards. A payload is stamped when the client builds it (an autosave with the time of the edit it carries, see the bc-sync paragraph below) and a queued one replays verbatim; a replay refused for skew is re-stamped once, by `_restampFor`, which computes TWO reconstructions and keeps the OLDER: `enqueuedAt + fresh offset` (wrong if the OS stepped the wall clock mid-outage) and `serverNow - monotonic age` (wrong if `performance.now()` froze during suspend). Taking the older is a safety rule, not a tie-break: an over-old stamp only makes this write lose a comparison it might have won, which is recoverable and announced, while an over-new one is the silent overwrite bc-lww1 exists to stop. The monotonic anchor is stamped at the one enqueue chokepoint and **stripped on persist**: it is measured from a per-document time origin, so a rehydrated reading (or one written by another tab) subtracts two different zeros and yields an age unbounded in BOTH directions, which is exactly what `min()` cannot defend against. A rehydrated entry therefore falls back to wall-clock only, so a clock step spanning a reload still ends in a drop. Retried exactly once either way.
- **A write is never stamped older than the match it was made against** (bc-hlck, operator request 2026-10-03). Two devices' server-time estimates can differ by up to the 5 s the server accepts, so a device running ahead stamps its write later than real time, and a change made a moment later on another device that SAW that write was stamped earlier than it and kept in the history instead of applied. `_stampAfterSeen` (api_client.jsx) is the ONE rule, a hybrid logical clock: this device's stamp, or the seen match's `modifiedAt + 1`, whichever is later, the floor capped at this device's time + 4 s (`HLC_FLOOR_MAX_AHEAD_MS`) so it never draws a `clock_skew` refusal. The server is unchanged: the match's `modifiedAt` is already the newest stamp it holds. What was "seen" is the caller's: the match handed to `recordScore`, `seenModifiedAt` in a decision body (stripped before sending, so `recordDecision` keeps its 4-argument call shape), the trailing argument of `overrideBracketWinner` (omitted by `recordOverrideWinner` when the feeder has no stamp, so that call is as it was) and of `recordDaihyosen`/`removeDaihyosen` (the team editor passes the shown match's stamp, 0 when it has none). The direct clock-skew resends of a score and of a hand-set winner re-stamp through the same floor. An AUTOSAVE is floored by the match as it was at the TAP: `useDebouncedRunningWrite`'s optional `seenStampRef` (every editor passes the shown match's stamp) is read at each tap beside `editedPerf` and rides on the patch as `seenModifiedAt`, explicitly 0 for a tap that saw no stamp, so a change another device made AFTER the tap never moves it (the 2026-09-27 ruling). A queued entry records the floor (`seenModifiedAt` on the descriptor, persisted, the later of two when one write takes another's place) and the skew re-stamp keeps it. Accepted residual: there is no per-device counter, so two writes floored by the same seen stamp share the stamp `seen + 1` and the later arrival wins an equal-stamp tie; across two devices (three on one match within about 4 s, against one operator per court) a local counter could not order them anyway, and on one device the server already does (the running rev guard's strict `<=`).

**An edit still inside an editor's autosave debounce is unsent work** (bc-sync). `useDebouncedRunningWrite` (admin_scoring_autosave.jsx) registers it with `API.notePendingEdit`, so the sync pill reads "Syncing…" from the first tap, and releases it only once the write is dispatched. On `pagehide` or the tab being hidden it writes a pending edit at once with `durable: true` on the patch, and `recordScore` puts such a running write straight into the persisted outbox (the flag is never sent), because a fetch started then dies with the page. That relies on every score-editor host reaching `API.recordScore` before the page goes, i.e. with no `await` on I/O in front of it (pinned by `score_write_same_tick.test.jsx`: `attemptScoreWrite`, `editMatchScore` and every host's `onSubmit`); do not add one. `api_client` also keeps, on page hide, a running write already SENT but not yet answered (`_keepInflightRunning`, from `_inflightRunningWrites`), because the page going away cancels that request. The copy is an entry of its own (bc-mrgc phase 3): it never replaces a queued entry for the match, nothing coalesces into it, and it replays in its place in the match's order. The copy is dated when the write was sent, the flush skips it while its fetch is still open (`_heldByOpenFetch`), and the fetch's outcome removes or replaces it, so a tab that is only hidden never sends the write twice.

**Every way out of an editor saves a pending edit, and an autosave is stamped with the time of the edit it carries** (operator ruling 2026-09-27). The unmount writes an edit still inside the debounce window whatever caused it: Close, Prev/Next or their keys, another match picked, a correction opened, a court switch, or the court console moving on by itself (`selectedMatch` falls back to `running[0]`, so another device finishing the match re-keys the editor). The write carries the monotonic reading of the last tap (`editedPerf`, never sent), and `recordScore` takes its age off the stamp (`_editAge`). That is what makes the unmount safe: a tap made before another device finished the match is OLDER than that finish, so the server keeps the finish, where a write stamped at send would have reopened it. Discarding is the one way out that saves nothing: the editor cancels the debounce before it closes. Close and Prev/Next share one leave rule (same ruling): whatever autosave does not carry asks "Discard unsaved scoring changes?" first (the individual editor's Tie toggle or hantei side pick on a running match, a kachinuki row the running patch drops, any unsaved change to a match that is not running); everything else leaves at once. So every user edit the running patch carries must call `markDirty`: an edit that arms no timer is not saved by the unmount or the page-hide flush (the overtime counter, the rep-player pickers and the team daihyosen verdict did not, bc-sync). An adopt for a value saved as it is made keeps the operator's value until the server holds it (`keepLocalEdits`), or the save of one tap, coming back, undoes a second tap made before it arrived.

**Self-run participants run the representative bout; a hantei stays the organiser's** (operator decisions 2026-09-28, bc-dhas). An anonymous self-run `PUT /score` may carry the representative-bout row (position -1, sub decision `daihyosen`) and score it like any bout. `POST`/`DELETE .../daihyosen` are public, but an anonymous caller adds or removes only on a RUNNING match (`selfRunDaihyosenRefusal`, handlers_daihyosen.go: 409 `result_finalized` with the `/score` sentence once it has finished, 409 `match_not_running` before it starts). The organiser keeps no status rule there, since an add to a finished fixed-order knockout match may be their correction (no `/reopen` exists for one). The add keeps a recorded kiken, fusenpai or fusensho; the organiser's remove of an unscored representative bout does not: it clears the match's decision and puts it back to running (`clearMatchVerdict`), while the competitor's bar stays recorded. Accepted as it is (operator decision 2026-10-02); do not report it as a new defect. An encounter holds ONE representative bout: a second add is 409 `daihyosen_exists` for every caller, and the add refuses engi, kachinuki and individual competitions and pool matches. `state.DaihyosenSubIndex` is the one finder of that row (the first -1 row).

ONE judge, `holdSelfReportedWriteUnderTx` (handlers_match.go), decides everything a participant's score write is refused or rewritten for that depends on the stored match. The decision allowlist and the Rev/RevSession reset run before the lock, in `enforceSelfRunPolicy`. The judge runs under the write's lock over the stored match the `/score` handler reads ONCE per write for every guard (`matchSnapshot`, whose `Pairing` holds the stored sides and ids; `applyCorrectionReason` reads the same one, and the member judge takes it as the pre-write baseline), and each refusal is a `selfRunRefusal` carrying its own status, code and sentence. Who a write seats is judged on what it LANDS, after the engine write, in the same transaction (`landedMembersRefusal`): the handler reads the match back through `stx`, which sees its own staged bytes, and compares it with the snapshot read before the write. A side member id the stored row now holds and did not hold before must be on that side's team (400 `team_member_not_in_team`: `errBoutFighterNotInTeam` on a participant's numbered row, `errRepMemberNotInTeam` on a representative pick, anyone's), and a winner member id that changed on a participant's numbered row must be one of the row's two fighters (400 `winner_member_not_in_bout`, `errWinnerMemberNotInBout`); the organiser's numbered rows are not judged. A refusal is RETURNED from the transaction closure as a `*landedWriteRefusal`, which ABORTS the transaction (no match write, no history line, no eligibility record), and is unwrapped into `engErr` after `WithTransaction` returns. It is judged only for a write the engine accepted (a superseded or rolled-back write still commits its history and restore) and only when the write, as the earlier judges leave it, INTRODUCES a member id on a judged row against the match as it stood before the write (`introducesJudgedMember`, a pure predicate over the payload rows and the pre-write snapshot; it and the judge, `membersOutsideTeams`, read ONE selection of rows, `judgedRows`: every representative-bout row against the stored one and, for a participant's write, each numbered row against the stored row at its position, `state.SubResultAt`, so a row or field added to one is added to the other): an echo of the stored ids, which the team editor stamps on every row that has a lineup, reads nothing back, because the engine never lands a member id the judge would refuse that the payload did not introduce (pinned from the engine's side by `TestEngineLandsNoMemberIDThePayloadDidNotIntroduce`, over kachinuki bouts on both store branches and a fixed-order team match's representative bout on the bracket, with stamped writes (one older than the group it rewrites, so that group is held and copied back) and both teams' starting lineups and team members saved, whose minted ids no row carries: every member id the write itself lands that the payload did not carry is a STORED one at the same position (`preserveKachinukiMemberIDs`; the merge's copies of the groups it does not apply, held or unnamed, through `CopyGroup`/`SetRepPick`; `keepQueuedScore` on a start, which that test does not send) or a winner id derived from the row's own landed side ids (`ResolveMemberWinnerID`/`ReconcileWinnerMemberID`), and an id taken from those lineups or members inside the write would be a foreign one it refuses; `MaybeAdvanceKachinuki`'s lineup ids are added after the transaction, in the handler, which the test does not reach). It judges the landed match, not the payload, because the engine rewrites a write before its merge (`applyKachinukiMerge` merges stored rows by position and fills member ids; `noteServerBoutChanges` adds the `bout:N` groups it rewrote): a pre-write probe of the payload (`engine.AppliedGroups`, removed) let a participant land another team's member on a kachinuki bout the write left out of `changed`. A group the merge does not land is the stored one in the landed match and is never judged: a stale NAMED group is in `heldGroups` and the history, an unnamed one in neither. Every member-id check (the landed rows, and the lineup PUT's `memberIDsOutsideTeam`) goes through one `memberJudge`, which reads team-members.yaml at most once and only when an id is introduced, and builds each team's member-id set once (`memberJudge.ids`); a file it cannot read refuses the write with 409 `team_members_unreadable` (`errTeamMembersUnreadable`), never a 500 the offline queue would retry forever, and since a refusal is an abort, nothing is written.

A participant's score write never creates a representative bout. A -1 row on a match that has none is one the write INHERITED, from a sheet a moment behind a remove made elsewhere or from a queued write replayed after it. The judge DROPS that row, logs the drop, and writes the rest through the timestamp guard, which decides a stale one. A write that FINISHES the match on such a row is refused instead, 409 `no_daihyosen` (`errRepBoutRemoved`), and nothing is written, since a finish may take its winner from that row. Nor does it ever remove one (only `DELETE .../daihyosen` does): a write listing the bouts without the -1 row the match has comes from a sheet a moment behind an ADD, so the judge KEEPS the stored row, scored or not, and a finish is refused, 409 `daihyosen_added` (`errRepBoutAdded`). Two rows are 400 `duplicate_daihyosen`. The organiser's write is not judged here, except its representative picks, which `landedMembersRefusal` judges on what the write lands, exactly as a participant's (same 400 `team_member_not_in_team` and sentence); a pick the merge holds (stamped older than the stored pick, or carried by a write held whole) is kept in the history and answered in `heldGroups`, never refused (a pick names a SIDE, whose team a correction can change under an open editor), and the match's status is never asked. Once the organiser records the judges' decision on it, a participant's write may send the row back (`sameHanteiVerdict`: same winner, same side names, mark in the same array) or leave its ippons out. The silence test is `engine.KeepsStoredDaihyosenVerdict`, the one `preserveSubHantei` restores by; a row with two or more outstanding fouls is never silent, because the fold would give it an array. Either way the judge REPLACES that row with a deep copy of the stored one, so the write lands with the decided bout exactly as recorded, whatever else the row said. Any of these is 409 `hantei_organiser_only`:
- recording, moving or clearing the decision;
- dropping the row;
- naming a match `winner`/`winnerId` other than the decided side, read id-first against the STORED sides through `domain.AttributeWinnerSide`.

Its two sentences are shared with the JS note (`REP_BOUT_DECIDED_NOTE`) through `internal/mobileapp/testdata/rep_bout_hantei_messages.json`. Every public write throws a refusal's `message` before its code (`_refusalText`, api_client.jsx). `IsSelfRunReportableSubDecision` judges one row's decision only, and takes only `""` or `daihyosen` on the -1 row (a draw, kiken, fusenpai or fusensho there would decide the encounter). Both `/daihyosen` routes resolve the caller before reading the body (a wrong password is 401, never `clock_skew`) and answer with `matchForBroadcast`, as the SSE event does.

The public editor matches:
- under `selfReport` it offers no hantei;
- it offers Add and Remove only while the match is running (`repBoutAddRemoveOpen`);
- once a hantei is recorded, the representative bout is read-only (`repBoutDecidedForParticipant`, overtime stepper included) with the refusal's sentence, and every save sends the verdict back;
- the individual editor hides its whole decision place.

`POST .../bulk-score` and `PUT .../quick-score` write without the participant's checks, so they are main-gated in self-run; bulk-score does judge each entry's representative picks on what the entry lands, in the entry's own transaction (a refused entry stores nothing and reports `reason: team_member_not_in_team`), and quick-score builds its rows server-side.

**A representative-bout add or remove holds the team editor's autosave** (bc-dhas). The add and remove go through `_daihyosenRequest` (api_client.jsx) on `_fetchJson`, which keeps one AbortController armed, on a timer rather than the wall clock, until the body is read. So a request the server never answers, or answers with a body that never completes, fails with the not-added/not-removed sentence instead of holding the write forever. The add and the remove are one sequence, `runRepBoutChange` (admin_scoring_team.jsx). It takes `hold()` before its pre-save. The pre-save is bounded by the same `FETCH_TIMEOUT_MS` (write_result.jsx), past which the change is reported as not answered, nothing is sent and the hold is released. Add and Remove both stay disabled while that save is still out (`submitting`), so no second change starts beside a pre-save given up on. The admin hosts' refetch after a write is bounded too (`refreshCompsBestEffort` asks `fetchCompetitions({ bounded: true })`), and one given up on at that deadline says nothing: `_fetchJson` rejects past its deadline with the one `timedOut` error however the abort surfaced, and `refreshFailureToast` (admin.jsx) returns no toast for it, because the hosts refresh after every autosave and on a slow link the toast would follow every few taps while the write reaches the page by push anyway. Any other refresh failure keeps the reload hint. `recordScore`, `recordDecision`, `overrideBracketWinner` and the queue's replay (`_flushQueue`, single-flight, so one stalled replay stopped every later flush) read their answers through `_fetchJson` too, so a body that stalls past the deadline is a network failure: the write comes back `{queued: true}` (the editor stays open, `writeKeepsEditorOpen`) and is replayed with the stamp it was sent with, safe if the server did store it because an exact resend of a recorded finish or decision is answered as recorded (`engine.ExactScoreReplay`, `exactDecisionReplay`), with no correction reason asked; a running write's equal stamp re-applies. The add saves the sheet first unless the match has finished, so a queued match starts through the score path's gates; the remove saves first only a running sheet with an edit owed. A debounce that fires while held defers its write, and the mounted editor calls `release()` from an effect on `daihyosenBusy`'s true-to-false edge, after the render that adopted the result. The adopt keeps the answer in the override, `{ match, at }`: a stamped answer the prop does not hold yet (`holdsAnswer`) becomes the match the sheet shows, with the answer's bout log, status and team-match overtime (the prop's winner and decision stay, since the client reshapes those), and it goes once the prop's bout log changes or its stamp reaches `at`; a change of the prop's STATUS re-judges it too (an effect on `match.status`, which releases it when the prop holds the same bout log and is not older than the answer), so a finish or reopen made elsewhere is not hidden behind it. `hold()` returns `settle(transform)`, called on every exit (`withServerDaihyosenRow` over the answer's row once landed, or over the last prop's when that prop already holds the answer; bare in `finally`): an edit owed when the editor UNMOUNTS during the request waits for it and is written with the outcome applied (the added row as returned, a removed one left out, unchanged on failure or refusal). A page going away (`pagehide`) meanwhile writes it at once, durably, as it stands, since nothing can wait for it; a tab merely hidden (`visibilitychange`) waits for the request like the unmount does and then writes durably with the outcome applied, since a write at once would put back a removed representative bout or wipe an added one. Accepted residual: a hidden page the system discards before the request answers, with no `pagehide`, loses that one tap. The pre-save (`saveRunningSheet`) repeats while a tap made during it is owed, reading the sheet through the autosave refs: the request is stamped when it is sent, so an edit made before it and written after it would lose the guard silently.

**The persisted outbox is shared by every tab.** `_persistQueue` merges into what storage holds, keeping the newer copy (`enqueuedAt`) where two tabs hold the same ENTRY (the same key; two writes about one match are two entries since bc-mrgc phase 3, and both are kept), and every removal goes through `_dequeue`, which records it so the merge prunes it from storage. A bare `_writeQueue.delete` leaves the stored copy for the merge to keep, and the write is replayed on the next load. Each tab also follows the others' writes (`_onStoredQueueChanged`, on the `storage` event): it takes up an entry it does not hold, or holds an older copy of, after the rehydrate's checks (`_storedEntryProblem`), and drops its copy of one another tab took out of storage, so a write queued in a tab that then closed is still sent. A write two tabs hold can be sent by both, which is harmless (last-write-wins). A revoked password is scrubbed from every stored entry, another tab's included (`_parkStoredEntries`).

**A superseded write leaves NO FOOTPRINT on the match, on either branch; its one footprint is its match history entry** (bc-mrgc). `UpdatePoolMatchByID`'s mutate returns an `error` and the store skips the save when it does, the contract `UpdateBracket` has always had, so `applyPoolWrite`'s superseded verdict aborts rather than re-serializing the untouched row and bumping the standings-cache version. Two rules come with it. The abort is reported through the ERROR and NEVER through `found`: `found` stays true because the match WAS there, and signalling `(false, nil)` would make `writeToPoolOrBracket` read a rejected pool write as "not a pool match" and go hunting for it in the bracket. And BOTH `storeTx` branches must honour it, the WAL-staged one included, or a drop leaves no trace outside a transaction and a WAL entry inside one. Pinned across all six cells of `superseded_matrix_test.go`, which asserts the file bytes AND `Store.FileVersion` are unchanged after a drop; reverting the abort reddens exactly the two pool cells.

**On the client a live score never goes back in time under a score editor.** A refetch can read the data just before a write commits and answer after a newer push or a newer refetch has landed; taken whole, it put the older scoreline back, and an open score editor that had caught up adopted it, so its next save wrote the lost point away. The refetch sinks a score editor reads from therefore merge through `patch.jsx`'s `keepNewerMatches` (`keepNewerCompetitions` for a list, `keepNewerDetail` for a competition detail, `keepNewerTournament` for the tournament): the court console's feed, the admin competition view, the public competition page (`selectedCompData` in app.jsx, every refetch through `takeCompDetail`, since self-run gave that page a score editor), and the tournament's competitions (the Scores tab's source, fed by the admin's refreshes and by the app's `load()` outside display mode). A held match is kept only when BOTH copies are RUNNING and the fetched one is stamped and older. Stamps come from two clocks: a client write carries the device's estimate of server time (accepted up to 5s ahead), a reopen, requeue or send-back the server's own, so a newer server stamp can read older; every server-stamped change moves the status, so running-against-running never weighs one clock against the other. An unstamped fetched copy (a draw discarded and drawn again reuses the match ids) always replaces. The display takes a refetch whole: no editor reads it, and its reload must discard its optimistic broadcast overlay. Accepted residual: a holder that never saw a match leave running (the Scores tab's list, which takes no pushes) can keep a running copy stamped by a device whose clock runs a few seconds ahead over the server-stamped running row of a reopen made within those seconds (e.g. a mistaken withdrawal reopened at once). Both show the match live; the held copy can still show the winner's letters that the withdrawal replaced with its circles, until the next write to that match replaces it.

**A public-page modal never holds a copy of its match.** `useLiveMatch` (viewer_match.jsx, beside `MatchViewerModal`), used by all four doors (the competition page's tabs and Overview, Home, Schedule), keeps only the match's id and competition and reads the row live every render from the page's own `compMatches` list, so a self-run score editor follows a correction made on another device; Home and Schedule look it up by competition as well as id (`matchInList`), because match ids repeat across competitions; Schedule builds only the open match's competition's list, and only while a match is open. The Overview reads `allMatches` alone. Nothing else is taken from the object the opener hands in: an opener may hold an old copy (Home's alert banner keeps the match from when the alert fired), and its scoreline must never stand in for the live one. Only the competition page's Bracket tab declares anything, `open(match, { round, phase, ...competition fields })`, and declared keys win over the row: a preview bracket is not in `compMatches`, so its live row is the raw one (`bracketMatchIn`). A match that leaves the data closes the modal and is forgotten, because a redrawn draw reuses ids.

Engine side: `state.IsTransactional(h)` lets a caller whose correctness depends on a live transaction check what handle it was given; `recordIneligibilityFromDecision`'s K2 check-and-set logs if handed the bare store, which is what pins the entry-point `WithTransaction` shims. `mergeMatchWrite` orders every write by stamp **including corrections** (the old `correctionReason` exemption was a workaround for refusals being silent, and it let a replayed offline correction overwrite newer results). The remaining unstamped-bypass overwrite is logged rather than silent (`logUnstampedOverwrite`).
